# Clanker Yard

Orquestador de agentes de código sobre issues y PRs. Monorepo con npm workspaces (Node 24, TypeScript estricto).

Este archivo lo lee cada agente y ya pasa los 100 KB: agrega reglas, desvíos y trampas que el código no dice, en pocas líneas. La referencia de un módulo (args, outcomes y output de una acción, qué hace cada función) va en su TSDoc, no aquí; si hace falta, una línea con dónde vive.

## El diseño es la fuente de verdad

Vive en `docs/design.html` (260 KB, no lo leas entero ni lo edites). Cita siempre la sección por su id, por ejemplo `docs/design.html#d-data`. Para leer una sección en texto plano:

```
python3 scripts/design-section.py          # lista los ids
python3 scripts/design-section.py d-data   # imprime una sección
```

Ids más usados: `devx` (dev setup), `d-data` (schema, API, monorepo), `stack`, `ui`, `d-ui`, `d-flows`, `d-agents`. Si el diseño no cuadra con la realidad, haz lo más simple que respete su intención y deja el desvío escrito en el PR.

Desvíos ya conocidos: `agentEnv` (`d-agents`) incluye `USER` además de `PATH`, `HOME` y `LANG`, y en modo suscripción nunca hereda `ANTHROPIC_*`, `CLAUDE_CODE_OAUTH_TOKEN` ni `CLAUDE_CODE_USE_*` (ver `docs/claude-subscription.md`).

## Instalar, correr, probar

```
nvm use                # Node 24, fijado en .nvmrc
npm ci
npm run typecheck      # tsc --noEmit en cada workspace
npm run lint           # eslint desde la raíz, más `npm run depcheck`
npm test               # vitest desde la raíz (un proyecto por app y paquete)
```

Los tres deben pasar antes de dar algo por listo; la CI corre los mismos en cada PR y en `main`. Un test de un paquete va junto a su código como `src/**/*.test.ts`.

La suite completa corre en paralelo y bajo carga: un `vi.waitFor` sobre un core, una corrida o un proceso real lleva `timeout` explícito (el default de 1 s no alcanza), un test no cuenta lo que hay en el `tmpdir()` compartido (usa su propia carpeta) y no espera un solo evento de `fs.watch` justo después de empezar a observar (en macOS se pierde; reescribe hasta verlo).

Un comando de shell que el código arma (`sh -c`, `-ilc`) se prueba al menos una vez con una shell real, no solo con un `run` falso: `"$PATH__fin"` expande la variable `PATH__fin` y ningún doble lo ve.

El core es un proceso largo: un callback de timer o de evento (`setInterval`, `.on(...)`) no lanza, porque un throw ahí tumba el core. Atrapa el error y conviértelo en un resultado (abortar un `AbortSignal`, emitir un evento).

Un error que puede llegar a la API (de un adapter, de git, de GitHub) se envuelve en un error de dominio que extiende `NotFoundError`, `BadRequestError` o `UiOnlyError` (`errors/domain.ts`); el middleware de los routers (`server/api-errors.ts`) los traduce a `NOT_FOUND`, `BAD_REQUEST` y `FORBIDDEN` con su mensaje, sin envolver cada handler. Uno que no extiende ninguno es un 500 sin mensaje y la vista no puede decir qué hacer. Lo que solo pide una persona (`origin: "ui"`) lo rechaza el método de dominio con `UiOnlyError`, no el router.

UI sola: `npm run dev -w packages/ui` abre la UI en el navegador (puerto 8890) con datos de ejemplo en memoria.

Para ver la app con datos y corridas que avanzan: `CLANKER_HOME=$(mktemp -d) npm run demo-core -w @clanker/testkit` levanta un core de demo (runtime fake, plantilla `juguete` pasada por `startCore({ builtins })`, un proyecto local con 3 issues, tres repos con receta ausente, válida e inválida, cada corrida dura unos 7 s) y publica su `core.json`; con el mismo `CLANKER_HOME`, `npm run dev -w apps/desktop` se conecta a él en vez de lanzar el core real. Con `DEMO_INBOX=1` suma el proyecto `Bandeja de prueba` (el E2E lo pide), que arranca una corrida por tipo de decisión (flujos `juguete-gate`, `juguete-trabado`, `juguete-tope` y `juguete-nota`, guardados directo en `defs`) y una alerta suelta sin opciones (`openDecision`; `demo-control.json` con `closeAlert: true` la cierra como lo haría un breaker), para ver y probar la bandeja de decisiones. Ciérralo con Ctrl+C. Sus conexiones nunca salen a internet: GitHub es el simulador (acepta el PAT `ghp_demo`), Linear el falso del core y Claude un `query` falso (`createFakeClaude`). Para ver una conexión vencida sin esperar, escribe `<CLANKER_HOME>/demo-control.json` con `{ "clockDays": 40, "claude": "login_expired" }` (el reloj de las conexiones parte del 2026-11-15 y se adelanta esos días; `claude` es `ready`, `login_expired` o `quota_exhausted`). Lo que GitHub hace del otro lado del device flow sale del mismo archivo mientras la clave esté puesta (el demo lo lee cada 200 ms): `githubDeny: true` cancela el código pendiente, `githubRefresh: "rejected"` invalida los refresh tokens y `githubInstalled: false` deja la App sin instalar. Con `DEMO_SCENARIO=summary` importa el fixture del loop (`packages/core/fixtures/legacy`) y le suma corridas de Yard con pasos al mismo proyecto (`Lote demo`, `packages/testkit/src/summary-scenario.ts`; sus métricas las calcula `recordRunMetrics`), para el Resumen. Con `DEMO_SCENARIO=prs` siembra 9 PRs en el simulador (repo `octocat/demo`) con el pack de ejemplo (`packages/testkit/fixtures/packs/example`) activado para `octocat` y `prs.refresh` de cada uno, sin Watch: un stack, riesgo alto, uno en cola, uno con la cola caída, uno en hold y una base combinada (`pr_parents` escritos a mano). Con `DEMO_SCENARIO=lanes` siembra además el proyecto de la vista de Operación (`packages/testkit/src/lanes-scenario.ts`): sus corridas se escriben directo en la base, porque el fake no se queda quieto el rato que dura una captura, y en ese escenario no va la bandeja de prueba.

App de escritorio: `npm run dev -w apps/desktop` construye el core y abre Electron (con `CLANKER_HOME=$(mktemp -d)` delante no toca tus datos; sin él usa los reales). Para capturar la ventana de verdad, arráncala con `npx electron-vite dev -- --remote-debugging-port=9333` desde `apps/desktop` y habla CDP con `http://127.0.0.1:9333/json` (`Page.captureScreenshot`, `Runtime.evaluate`, `Emulation.setEmulatedMedia` para claro y oscuro). Ciérrala con `Browser.close` por CDP, no con `pkill`: hay otras Electron corriendo.

E2E: `npm run e2e` (desde la raíz) construye el core y la app, lanza el core de demo del testkit (runtime fake, plantilla `juguete`, proyecto `demo`) sobre un `CLANKER_HOME` temporal (la app y el demo comparten `isolatedUiKey`) y abre la app con Playwright `_electron` (`apps/desktop/e2e`, `*.e2e.ts`, fuera de `npm test`). Crea un proyecto desde el diálogo, corre `juguete` (que el core de demo instala) hasta que la corrida queda `lista`, conecta GitHub (PAT contra el simulador), Linear (el test recoge el link del IPC `host:open-external` y lo aprueba) y Claude, prueba una receta con su log en vivo y deja los screenshots claro y oscuro de cada vista en `apps/desktop/out/screens` (no se commitean). El core real no conoce el runtime fake, por eso el E2E lanza el core de demo y la app se conecta a él por `core.json`. Necesita el binario de Electron: tras `npm ci` corre `node node_modules/electron/install.js` (los install scripts no corren). En Linux va bajo xvfb (`xvfb-run --auto-servernum npm run e2e`, `--no-sandbox` lo pone el test); la CI lo hace en el job `e2e` y sube `out/screens` como artefacto `e2e-screens`. El harness lanza la app con `CLANKER_E2E=1` (`src/main/e2e.ts`): ventana offscreen que nunca se muestra, fuera del Dock y sin notificaciones, así que no quita el foco; con la ventana solo oculta (sin `offscreen`) no hay frames y el canvas de xyflow no mide sus nodos. El tema se cambia con `page.emulateMedia`, porque Playwright fija `prefers-color-scheme` en la ventana y `nativeTheme` no lo mueve. Cada archivo `*.e2e.ts` elige el escenario del core de demo con `test.use({ scenario })` (`e2e/harness.ts`; `default`, `lanes`, `summary`, `prs` o `learnings`: los PRs de Stacks de PR contra el simulador y el pack de ejemplo, `packages/testkit/src/prs-scenario.ts`; los learnings por revisar (importados, de agentes y a mano) y ya revisados, `learnings-scenario.ts`) y cada escenario corre en su worker. ⌘K y los demás atajos del menú nativo no los dispara Playwright: abre la paleta con el botón del buscador.

## Paquetes y dependencias permitidas

```
apps/desktop      Electron (main, preload, ventana)
apps/cli          comandos `clanker` sobre la API
packages/api      contrato oRPC, esquemas zod, cliente
packages/core     Store, Flows, Agents, Workspaces, Scheduler, servidor
packages/ui       React + shadcn, vistas
packages/testkit  runtime fake, fixtures, repos git temporales
```

- `api` no depende de nadie del repo. `core` → `api`. `ui` → `api`. `desktop` → `ui`, `api`. `cli` → `api`. `testkit` → `core`, `api`, solo como `devDependency`.
- Prohibido: `ui` → `core`, `desktop` → `core` (el core se empaqueta y se lanza, no se importa), `core` → `electron`.
- Las factories del core reciben sus dependencias en un objeto (`createRepos({ store, remote })`), nunca posicionales: así sumar una no cambia todas las llamadas.
- Cada paquete exporta solo su `src/index.ts` (más `@clanker/api/node`, que la UI no puede usar, y `@clanker/core/testing`: los GitHub y Linear falsos de `core/src/testing/` y la plantilla `juguete`, solo para tests y el testkit). Nada de imports a archivos internos de otro paquete. `npm run depcheck` también exige que cada paquete de npm que se importa esté en el `package.json` del paquete y que el código de producción no importe devDependencies.
- `npm run depcheck` lo hace cumplir con dependency-cruiser (`.dependency-cruiser.mjs`) y corre dentro de `npm run lint`, así que la CI lo ejecuta en cada PR. Si agregas un paquete o cambias una dependencia permitida, edita esa config y el test `scripts/depcheck.test.ts`. Que `testkit` use `core` y `api` solo como `devDependency` lo verifica ese test, no dependency-cruiser.

## Base de datos

El schema vive en `packages/core/src/store/schema.ts`. Tras cambiarlo: `npm run db:generate -w @clanker/core` deja una carpeta nueva en `packages/core/migrations/` (se commitea). Para triggers u otro SQL que drizzle-kit no modela: `npx drizzle-kit generate --custom --name <x>` desde `packages/core` y escribe el SQL a mano. No edites una migración ya mergeada. Un evento cuyo payload alguien lee (un `store.events.subscribe` del core, `events.since` o el stream de la UI) declara ese payload en `EventPayloads` (`packages/api/src/event-payloads.ts`): `tx.emit` y `subscribe` lo tipan, y donde llega un `Event` suelto (`events.since`, la UI) `isEventOf(event, tipo)` lo tipa en vez de un cast. Una migración nueva cuelga de la última de `main` (`prevIds` de su `snapshot.json`): si al rebasear entró otra, borra tu carpeta y vuelve a correr `db:generate`, nunca parches `prevIds` a mano; `npm run lint` corre `drizzle-kit check` (`db:check`) y falla con dos migraciones en conflicto.

Lo que ya define `@clanker/api` (ids con prefijo, `EventType`, `Origin`, `SubjectRef`, `Event`, `EventFilter`, `EventPayloads`) se importa de ahí, no se redeclara en el core: en el schema con `.$type<...>()`, que no cambia la migración.

Las columnas que apuntan a `repos` o a `issues` llevan su brand (`$type<RepoId>()`, `$type<IssueId>()`) y las firmas del core piden `RepoId`, no `string`: un id que llega como texto (los `params` de una corrida) se valida con `RepoId.safeParse` (`repoOfRun`), no se castea. `SubjectRef.id` y `runs.subject_id` siguen como texto: el sujeto de una corrida puede ser cualquier cosa (los tests del motor usan `ENG-1`). Los ids de prueba salen de `newId("run")` o son ULIDs válidos (`run_00000000000000000000000001`): `run_1` pasa el tipo, pero el store rechaza el evento.

Si una tx emite el inicio de algo (`lease.acquired`) y el paso que sigue falla, el camino de error emite el cierre (`lease.released`): la línea de tiempo no puede quedar con un lease que nunca se soltó.

## Secretos y conexiones

Los tokens viven detrás de `Secrets` (`createKeychainSecrets` con el comando `security`, `createFileSecrets` para tests y Linux); la base guarda solo la ref y los eventos nunca llevan el valor. `createConnections` (`connections/connections.ts`) es lo único que escribe `connections` y emite `connection.changed`; el token lo lee solo el core. Cómo se conecta y refresca cada proveedor está en el TSDoc de `connections.ts`, `github/pat.ts`, `linear/` y `agents/claude/probe.ts`.

- GitHub: `connections.githubClient(cuenta)` es el único cliente Octokit (pone el token y registra la cuota). Los permisos del manifiesto de la GitHub App (`docs/github-app-manifest.json`, guía en `docs/github-app.md`, sin instalar aún) son los de `PERMISSIONS` en `github/pat.ts` (un test lo comprueba). El `client_id` de la App y el de Linear salen de `<dataDir>/config.json` o de `CLANKER_GITHUB_APP_CLIENT_ID` y `CLANKER_LINEAR_CLIENT_ID`, que ganan (`readCoreConfig`).
- GitHub por la App (CLA-100): `connections.startDeviceFlow` (`github/device-flow.ts`) devuelve el código de usuario y sondea en segundo plano (respeta `interval` y `slow_down`); al aprobar guarda la sesión (`{ accessToken, refreshToken, accessExpiresAt }` en `Secrets`, como Linear) y conecta la cuenta con `auth: "app"` (columna `connections.auth`; `pat` para las pegadas; reconectar con el otro tipo reemplaza la cuenta). El token de usuario vive 8 h y su refresh token 6 meses y rota: `token()` lo refresca 5 min antes con un solo refresh en vuelo por cuenta (mismo mecanismo que Linear, `rotation` en `connections.ts`), y `githubClient` pone `refresh` en su `GitHubTokenSource` para reintentar tras un 401. Un refresh rechazado deja la cuenta `revoked` (`connection.changed`, que abre el breaker `github`, como con el PAT); un fallo de red no cambia nada. Un device flow que falla (cancelado, código vencido, GitHub rechaza algo) no toca la cuenta y emite `connection.login_failed` (`{ provider, reason: "denied" | "expired" | "failed", message }`, el `reason` sale de `GitHubAuthError.reason`) para que la UI lo muestre sin esperar al vencimiento del código. `connections.githubInstallations` (`GET /user/installations` con el token de la App) dice cuántas instalaciones ve la cuenta: con cero conectar funciona pero los repos salen vacíos; `githubApp.slug` del `config.json` (`CLANKER_GITHUB_APP_SLUG`) le da el link de instalación. Se prueba con `startFakeGitHubOAuth` (`testing/github/fake-github-oauth.ts`, con reloj inyectado: `slow_down` real si se sondea antes de `interval`, refresh que rota, `bad_refresh_token`) en `github/device-flow.test.ts` (también `githubInstallations`) y, publicando con push y PR, en `packages/testkit/src/github-app.test.ts`. El device flow y el refresh nunca se probaron contra github.com: lo que hace el código sale de la documentación (`docs/github-app.md`, Referencias).
- Linear: la OAuth app ya está registrada (pública, workspace clanker-yard, redirect `http://127.0.0.1:48721/oauth/linear/callback`; Linear compara la URI completa, por eso el puerto es fijo). Su `client_id` viene incluido en el código (`LINEAR_DEFAULT_CLIENT_ID`): el flujo es PKCE sin client secret, así que no es secreto. Para usar otra app, `CLANKER_LINEAR_CLIENT_ID` o `{ "linear": { "clientId": "..." } }` en `<dataDir>/config.json` (en macOS, `~/Library/Application Support/Clanker Yard/config.json`); precedencia: variable > config.json > incluido. No se probó contra Linear real.
- Claude: la cuenta `claude` es su modo, `subscription` (fila sin secreto: el login lo lee el `claude` instalado, nunca la app) o `api-key` (en `Secrets`; mientras exista, es lo que usan los runs). Nunca guardes aquí el token OAuth de la suscripción (`docs/claude-subscription.md`).
- Los tests no tocan el Keychain real: usan `createFileSecrets` en un directorio temporal, o un `.keychain-db` temporal creado con `security create-keychain` (ver `secrets.test.ts`). Los proveedores tienen falsos locales: `testing/github/fake-github.ts` y `testing/linear/fake-linear.ts`.

## App de escritorio

`apps/desktop` es solo el host (`docs/design.html#remoto`, `#d-data`): `main` lanza y vigila el core (`createCoreSupervisor`), `preload` le pasa la conexión a la ventana y `renderer` monta `@clanker/ui` con un `Host` armado sobre el preload.

- El renderer nunca ve el token ni el puerto: llama a `clanker-core://core/rpc`, un esquema que registra el main (`src/main/core-proxy.ts`) y reenvía al core vivo. Todo lo de Electron que la UI necesita pasa por `Host` (`packages/ui/src/host.ts`), y el main valida cada payload que llega por IPC.
- Cerrar la ventana o la app no detiene el core; "Salir y detener agentes" pide `system.shutdown({ drain: true })`. El supervisor no relanza solo: Reintentar llama a `start()`.
- El core es el bundle `packages/core/dist/main.js` (desktop no lo importa). Electron guarda sus cachés en `<datos>/desktop`, así que con `CLANKER_HOME` un arranque de prueba no toca nada del usuario.
- Los packs de fábrica son `packs/` de la raíz: `packages/core/packs` es un symlink para que el bundle los lea de `../packs` (igual que las migraciones) y `electron-builder.yml` los copia a `core/packs`. `packs.reload()` activa, por id, la versión más alta y a igual versión la instalada en `<datos>/packs`, así que un pack copiado a mano con el mismo id y versión sigue mandando y no crea versiones.
- `@clanker/ui/styles.css` es el único archivo interno de la UI que otro paquete importa; el Vite del desktop apunta el alias `@` al `src` de la UI.
- Los tests de `core-supervisor` lanzan el core real con su propio bundle (`node scripts/build.ts <outfile>` de `packages/core`), sin pisar `dist/`.
- Empaquetado (macOS arm64, sin firma ni notarización): `npm run build:mac` construye core, CLI y app y deja `apps/desktop/dist/mac-arm64/Clanker Yard.app` (electron-builder, `apps/desktop/electron-builder.yml`). `npm run install:mac` además la copia a `/Applications/Clanker Yard.app`, deja el symlink `~/.local/bin/clanker` y la abre. Para probar el `.app` sin instalarla: `CLANKER_HOME=$(mktemp -d) "apps/desktop/dist/mac-arm64/Clanker Yard.app/Contents/MacOS/Clanker Yard"`.
- Dentro del `.app`, fuera del asar (`extraResources`): `Resources/core/dist/main.js` con `Resources/core/migrations` al lado (el bundle las busca en `../migrations`), `Resources/cli/clanker.js` y el lanzador `Resources/bin/clanker`. `coreEntry` (`core-entry.ts`) elige el core según `app.isPackaged`; el core corre con `process.execPath` + `ELECTRON_RUN_AS_NODE=1` (el Node 24 de Electron trae `node:sqlite`). El código de la app va entero bundleado: `files` excluye `node_modules`, así que una dependencia nueva del main o del renderer debe poder bundlearse.
- La CLI instalada es el lanzador `Resources/bin/clanker` (un sh que corre `cli/clanker.js` con el Electron en modo Node y fija `CLANKER_CORE_ENTRY`), así que no necesita `node` en el PATH. El menú Archivo > "Instalar comando clanker…" y `install:mac` lo enlazan en `~/.local/bin`. La entrada `clanker` de `.mcp.json` usa `clanker mcp` si está en el PATH y el checkout si no.
- Una app abierta desde el Dock hereda un PATH mínimo y ningún `LANG`: el main toma los de la shell de login (`login-env.ts`, `LANG` cae a `en_US.UTF-8`) antes de lanzar el core, que necesita encontrar `claude`, `gh` y `git`, y que los checks y agentes no corran en el locale C.
- Si macOS bloquea la app la primera vez (solo pasa si el `.app` llegó con cuarentena, por ejemplo descargado o copiado por AirDrop; `install:mac` la copia con `ditto` y no la marca): clic derecho > Abrir, o `xattr -dr com.apple.quarantine "/Applications/Clanker Yard.app"`.
- Al actualizar la app, el core que quedó vivo del build anterior solo se reemplaza si cambió el `apiMajor` o no reconoce la llave; si no, sigue corriendo el viejo hasta "Salir y detener agentes".

## Trackers

`Tracker` (`packages/core/src/tracker/tracker.ts`) es lo único que el scheduler y los flujos ven de un tracker; las formas normalizadas son de `@clanker/api`. Hay dos adapters, `local` (`createLocalTracker`) y `linear` (`createLinearTracker`, `linear/tracker.ts`); `createIssues({ store })` es el caché `issues` que llena `sync`. Un adapter nuevo implementa `Tracker` y declara sus `capabilities`.

- Linear va por GraphQL directo con `fetch` (`linear/graphql.ts`, sin `@linear/sdk`: una query por operación y su costo a la vista). `claim` y `setStatus` releen después de escribir, porque Linear puede aceptar un `issueUpdate` sin aplicarlo (ENG-9084).
- Limitaciones conocidas: `changesSince` usa `updatedAt` y no ve comentarios; una issue con más de 25 labels o relaciones es un error (no se trunca); `statusMapping` por proyecto no se persiste ni tiene UI.
- Los tests usan `startFakeLinear`, que ejecuta con `graphql-js` el subconjunto del esquema real en `linear/fixtures/schema.graphql`: un campo que Linear no tiene no valida. Si el adapter pide algo más, cópialo del esquema real (`linear/linear` en GitHub, `packages/sdk/src/schema.graphql`).

## Packs

Un pack (`docs/design.html#packs`) es lo propio de una org (señales de PR, bot de review, reglas de CI, estrategia de merge, convenciones, flujos y roles) como JSON declarativo; el core no tiene `if` por organización. El esquema es `Pack` en `packages/api/src/pack.ts` (con `packJsonSchema` y `PackSettings`, que tomado de `{}` es la configuración neutra de un repo sin pack).

- Una carpeta de pack tiene `pack.json` y los `.json` de sus flujos (`FlowDef`) y roles (`Role`) que ese archivo lista, con rutas relativas a la carpeta. El id de un flujo debe ser el nombre de su archivo; el slug de un rol es el nombre de su archivo.
- `createPacks({ defs }).load(dir)` valida todo antes de escribir y guarda el pack (kind `pack`) y sus flujos, roles y paquetes de contexto (`contexts`, cada archivo un `ContextPackage` de referencias) como defs con scope `pack` y source `pack:<id>@<versión>`. Lo que una versión anterior traía y la nueva no se archiva. Dos packs no pueden traer el mismo slug. Un error es un `PackLoadError` con el archivo y la ruta de cada problema.
- `packs.packFor({ githubOrg, trackerWorkspace, projectId })` lee los packs guardados y devuelve el primero (por id) cuyo `activate` cubre el alcance, o los defaults neutros con `id: null`. Para un repo se pasa su org de GitHub; para un proyecto, su id y el workspace de su tracker.
- `defs.resolve` no conoce el alcance: un flujo o rol de un pack es visible para cualquier repo. Quien lance un flujo debe consultar `packFor` antes de ofrecer lo del pack.
- `conventions.context` (`{ <rol o *>: ["skill:commit", "rule:git-safety", "repo:AGENTS.md"] }`) lo resuelve Agents con las fuentes del rol, para el pack de la org del repo del workspace (ver Contexto de los roles).
- `packs/` (los de fábrica) está vacío: el pack de una organización vive en su propio repo y se instala desde Ajustes > Packs o copiándolo a `<datos>/packs/<id>`. `packages/testkit/fixtures/packs/example` es el pack de ejemplo que usan los tests y el core de demo: bot de review (`review-bot`, `/review`), merge por comentario (`/merge`) con la cola `merge-queue`, y la señal de riesgo por label.
- Un pack no trae tests: lo valida el core al cargarlo. Además del esquema, todo rol que se guarda (de pack, de repo o de usuario) tiene que tener un reporte que Claude Code compile (`claudeSchemaError`, `agents/claude/report-schema.ts`, en el validador de `role` de `createAgents`), y un rol de pack con el slug de uno de la plantilla tiene que mantener cada modo de ese rol con sus outcomes, sesión, payload y reporte (`checkOverride` en `packs.ts`): los flujos de la plantilla dependen de eso.

## Contexto de los roles

`createContextResolver` (`packages/core/src/agents/context.ts`, `docs/design.html#contexto`) convierte `Role.context` y el `conventions.context` del pack en `{ native, references, warnings }` en cada lanzamiento y cada `resume`, leyendo siempre el archivo original: una skill o regla editada vale desde el siguiente lanzamiento. Qué fuente va a dónde está en su TSDoc.

- Las skills (`native.skills`) se le piden a Claude por nombre, sin copiarlas; los archivos (`repo:`, `file:`, `rule:`, paquetes `context`) van a `references`.
- Un archivo, paquete o skill que falta no detiene al agente: queda en `warnings` y sale un evento `error` con `scope: "agent.context"`, una vez por rol y fuente en cada corrida (los pasos siguientes no lo repiten). Los roles de la plantilla (`lore`, `commits`, `bug-rubric`, `test-rules`) avisan mientras nadie guarde esos paquetes (nada de la app crea defs `context` todavía).
- Los hooks del usuario siguen apagados salvo `Role.hooks`.

## Git remoto (push y fetch)

Los commits salen con la identidad de git del usuario en ese repo (o su noreply de GitHub), nunca con una identidad del sistema (`createGitIdentityOf`, `packages/core/src/git/identity.ts`).

Solo el core habla con el remoto, y el token nunca llega al entorno de git ni de los hooks del repo: `createGitRemote` (`packages/core/src/git/remote.ts`) corre push y fetch con una URL explícita, sin credential helper y con un `GIT_ASKPASS` que cambia un ticket de un uso por el token a través de un socket del core. Ese git hereda solo `INHERITED_ENV` y el fetch corre sin hooks. Se usa a través de `workspaces.push(lease)` (`--force-with-lease` contra `remote_sha`) y `workspaces.fetch(repo)`. Los tests (`packages/testkit/src/git-remote.test.ts`) usan un servidor git HTTP local con Basic auth: nunca GitHub ni tokens reales.

## Estado de un PR

Un solo módulo lee un PR de GitHub y lo entrega normalizado: `createPrs({ connections, packs }).get({ account, repo, number })` (`packages/core/src/github/`, API `prs.get`) devuelve el `PrState` de `@clanker/api` (`docs/design.html#d-ops`). `pr-query.ts` es la query GraphQL de detalle (`PrDetail`, más `PrThreads` y `PrContexts` para completar las páginas de threads y de checks por el id del PR; los conteos no pueden quedar a medias) y `pr-state.ts` el builder puro `buildPrState(node, { pack, viewer })`.

- Genérico: nada de una organización en el código. El bot de review (`reviewBot`), quién es humano (`actors.ignore`), los checks que cuentan (`ciRules`), el prefijo del council (`conventions.councilPrefix`) y las señales (`signals`, `risk` en el pack de ejemplo) salen del pack de la org del repo (`packs.packFor({ githubOrg })`). Sin pack: sin bot, sin señales y CI = checks requeridos de la branch protection (`isRequired(pullRequestNumber:)` de cada check; sin requeridos es `none`). Con `ciRules` cuentan todos los checks menos `ignoreChecks`; `knownFlaky` marca los flaky conocidos.
- Un LGTM del bot solo vale con la regla del pack (estado, `bodyMatch` y, con `sameSha`, el commit del head); uno de un commit anterior es `bot.state: "none"`. Una review del bot que no cumple la regla es `findings`. `silentReviewBody` se evalúa sin distinguir mayúsculas; `bodyMatch` e `ignore`, sí.
- Cada thread es de quien escribe su primer comentario: council (prefijo) antes que bot antes que humano; lo que escribió la cuenta conectada (`viewer`) sin prefijo no es un humano esperando. `councilOpen` son los `fullDatabaseId` de esos comentarios.
- Lo que los waits necesitan viene en el `PrState`: `bot.at` (ISO de la review del bot), `bot.findings` (solo con `state: "findings"`: sus threads sin resolver, con `id` (el `fullDatabaseId` de su primer comentario), `path`, `line` y texto, o su review misma si no dejó threads) y `ci.flaky` (los de `ci.failing` que el pack declara en `ciRules.knownFlaky`; siguen contando como rojo).
- Waits (`pr-waits.ts`, `prWaits(prs, { headSeen })`, que `startCore` registra): `pr.botReview`, `pr.ci` y `pr.merged` deciden con una función pura sobre el `PrState`, la misma para `probe` (el de `prs.get`) y para `match` (el que Watch da a `flows.signal`, ver `signalPr`). `pr.botReview { pr, after }` solo cuenta una review del bot posterior a `after`; el `id` de cada ítem de `findings` es el `fullDatabaseId` del primer comentario de su thread, que es lo que espera `pr.reply`. `pr.ci` falla apenas falla un check que cuenta y da `ok` con `ci.state === "none"` (repo sin CI, como `ciGreen`) cuando el caché ve ese mismo head hace `NO_CI_GRACE_MS` (5 min, por si el CI aún no registra sus checks; `headSeen` sale de `headChangedAt` de `pull_requests`); lo cierra el sondeo del wait, no un `signal`. Sin `headSeen` no hay "sin CI".
- `talk` es lo que el vigilante cuenta como comentario de un humano: una review que pide cambios o con texto que no es un LGTM solo (un texto de solo espacios es texto; una descartada con texto sigue contando), cada comentario de la conversación y el primer comentario de cada thread humano sin resolver (sus respuestas no); lo que lleva el prefijo del council no cuenta, sea de quien sea. `threads.unresolved` es todo thread abierto, de quien sea: los "hilos sin resolver" de Control, y lo que lee `reviewStatusOf(pr)` (`@clanker/api`), el estado de review (`changes`, `pending`, `approved`, `none`) de `reviewStatus` de Control.
- Un PR sin checks (o con solo merge-queue) da `ci.state: "none"`, y Control y el vigilante lo daban por listo (`every` sobre vacío): `ciGreen` de la estrategia de merge acepta `none` además de `green`.
- Clanker Control y `clanker-loop watch` quedaron deprecados con Yard y no hay tests de paridad con ellos. Dos decisiones que vienen de esa época siguen: el dedupe de Watch es permanente a propósito (decisión de Simón): un conflicto del mismo sha o un thread de council que se reabre no se anuncian de nuevo, porque arriesga relanzar el mismo rebase o council en loop. `github-actions[bot]` no cuenta como el bot de review: si un wait lo necesita, va como un campo aparte, no en `reviewBot.logins`.
- `PrState` trae también lo que la vista dibuja (`title`, `url`, `updatedAt`, `additions`, `deletions`, `comments`) y `merge.command` (solo con `via: "comment"`). Desvío del diseño: `combinedBase` no es de `PrState` (sale solo de GitHub) sino de `CachedPr.parents` (`pr_parents`): con dos o más padres la base es combinada. `pr.publish` escribe una fila de `pr_parents` por cada padre de una base combinada (ver Bases combinadas). Pendiente para la fase 2: los eventos de Watch `pr.overlap` y la notificación de `pr.mergeFailed`. El resto de `PrState` (`approvers`, `merge`, `hold`) ya está: ver Estrategia de merge.
- El GitHub falso no valida la query: `github/graphql-schema.test.ts` valida cada query y mutation contra el esquema público (`github/fixtures/schema.docs.graphql`, de `docs.github.com/public/fpt/schema.docs.graphql`). Un documento GraphQL nuevo se suma a ese test; si GitHub cambia un campo que se usa, se vuelve a bajar el esquema. El falso (`testing/github/fake-pr-graphql.ts`, `prGraphql`, que usa también el simulador del testkit) responde como el real: GraphQL siempre contesta 200, un recurso inexistente trae `data` nulo y un error `NOT_FOUND`, y la cuota primaria agotada es un 200 con `errors` y `x-ratelimit-remaining: 0` (el cliente emite `sync.rate_limited`, ver `rateLimitReset` en `client.ts`).

## Estrategia de merge

`ready`, `offer` y `auto` (`docs/design.html#d-ops`, "Tres niveles de merge") son las listas de `mergeStrategy` del pack, evaluadas sobre el `PrState` por `evaluateMerge` (`github/merge-strategy.ts`, puro) y entregadas en `PrState.merge` (`ready`, `blockers`, `queue`, `offer`, `auto`, `via`), `approvers` y `hold`. Las condiciones y el texto de cada blocker (los de `mergeStatus` de Control) son del core; qué condiciones forman cada nivel, del pack. Sin estrategia, o donde no aplica, rige `GITHUB_BUTTON`: `via: "button"`, ready sin cola, offer sin `auto`: el core ofrece una decisión y la persona mergea con el botón de GitHub.

- `hold` es del core (`pull_requests.hold`, `PrCache.setHold`, que relee el PR): apaga `offer` y `auto` aunque la lista del pack no cite `notHold`, y `auto` siempre implica `offer`. Se marca con `prs.setHold` y desde la UI (ver Acciones sobre un PR).
- `appliesWhen` lo resuelve `MergeScope` (`github/merge-scope.ts`, que `createPrs` consulta al leer el PR): primero el override del repo (`repos.merge_strategy` `on`/`off`, `Repos.setMergeStrategy`, decisión #33) y si no, si el check aparece en los últimos 20 commits de la branch por defecto (`DefaultBranchChecks`, un GraphQL validado contra el esquema público; se recuerda una semana si lo vio y un día si no, en `sync_cursors`). Que merge-queue se vea ahí es una suposición sobre cómo publica merge-queue sus statuses: si un repo la rompe, el override lo corrige.
- La cola (`merge.queue`) sale de un comentario de la cuenta conectada que sea solo el `command` (`/merge`, comparado literal), y `failed` si el check `queueCheck` quedó en FAILURE o ERROR. Un `/merge` viejo sigue contando tras un push nuevo (como Control y el vigilante): un PR cuyo merge-queue falló y se arregló no vuelve a ofrecerse hasta que alguien lo resuelva a mano.
- Watch emite `pr.mergeReady` (`level: "offer" | "auto"`) y `pr.mergeFailed` una vez por head (`mergeFactsOf`, en `watch_marks`); los de merge también salen en la primera lectura de un PR (`emitOnFirstRead`, ver Siembra y debounce), así que lo que ya estaba listo se ofrece o comenta, una vez por head. Con la cola de merge-queue en curso (`queue: "queued"`) Watch pide check-runs y status cada 30 s, porque merge-queue mueve su status sin tocar el PR.
- `startMergeReactions` (`watch/merge-reactions.ts`) escucha esos eventos y solo actúa sobre PRs `owned`, y nunca confía en el evento: relee el PR y reevalúa. `auto` con `onAuto: "act"` comenta el `command` (git-safety: solo el nivel `auto` lo hace sin preguntar; eso lo fija el pack, no el core). `offer` con `onOffer: "gate"` abre una decisión `question` sin corrida (nada espera; `merge_offers` guarda el head ofrecido) y reemplaza la anterior si el head cambió. Aprobarla (opción `Comentar <command>`, resuelta desde la app: un agente puede usar el CLI o el MCP, así que solo `ui` vale: `decisions.resolve` rechaza otro origin con `FORBIDDEN`, y `ui` exige la llave de la app: ver "Origin `ui`") relee el PR y comenta solo si sigue en el mismo head y `offer`; si no, deja una nota. Sin comando la decisión no hace nada: el merge es del botón de GitHub.
- Los tests sobre `startGitHubSim` (`packages/testkit/src/merge-strategy.test.ts`) usan el pack de ejemplo con otro alcance; `sim.defaultBranchCheck("merge-queue")` pone merge-queue en la branch por defecto del simulador.


## Acciones sobre un PR

`createPrCommands` (`github/pr-commands.ts`) es lo que una persona le pide a un PR desde la app: `prs.setHold`, `prs.merge`, `prs.requestReview` y `prs.rebase` (referencia en su TSDoc). Cada pedido relee el PR antes de actuar y rechaza con `PrCommandError` (`BAD_REQUEST`, con qué cambiar). Ninguno sale por el MCP y `merge` solo lo acepta `origin: "ui"` (`FORBIDDEN` para CLI y MCP): mergear es de una persona, como aprobar una oferta. `merge` comenta el comando de la estrategia del pack (`commentOnPr`, `github/comment.ts`) en cualquier PR que el core conozca, no solo los `owned`. `rebase` anota un `pr.conflict` y `startTriggers` arranca el flujo que lo atiende, con sus reglas (solo `owned`, sin council); sin un flujo para `pr.conflict` no pasa nada. Se prueba en `packages/testkit/src/pr-commands.test.ts`.

## Republicar PRs

`prs.republish` (`createPrRepublisher`, `github/republisher.ts`) vuelve a sacar cada PR abierto del sistema con la branch, el autor y los commits de las reglas de hoy: lanza el flujo `republish-pr` por PR, en orden de stack, y vuelve sin esperar; quien llama (la CLI, `clanker prs republish`) sigue `prs.republishProgress`. Las acciones propias del flujo (`pr.replay` y `pr.supersede`, `github/actions/replay-supersede.ts`) y lo que se salta están en su TSDoc. Lo que el código no dice: el PR viejo solo se cierra (`supersede`) después de que el nuevo quedó publicado con el mismo árbol, así que un fallo antes deja todo como estaba, y un PR con base combinada o con contexto que se perdería (threads de council, humanos) no se rehace.

## Watch (polling de PRs)

`createWatch({ store, connections, repos, cache, remote, waitKeys, events, errors, trackers? })` (`packages/core/src/watch/`, `docs/design.html#d-ops`, "CodeHost: polling con ETags") detecta qué PRs cambiaron sin gastar cuota y se enciende con `startCore({ watch: true })` (lo que hace `runCore`; por defecto apagado, para que un test con el GitHub simulado no reciba requests que no pidió). Es código puro: sin slot ni agente. `tick()` es un despertar (cada 2 s con `start()`); los tests lo llaman a mano con un `now` inyectado.

- Qué mira: las filas abiertas de `pull_requests` (las que abrió `pr.publish` y las que descubre la búsqueda `is:pr author:@me is:open` cada 5 min, solo de repos registrados con remoto) más los PRs con un wait esperando (`Engine.waitKeys` + `prOfWaitKey`). Por cuenta, en serie.
- Por PR: `GET pulls/{n}` con ETag cada 30 s (caliente: un wait lo espera o se pusheó hace menos de 15 min), 2 min (en review, fuera de draft) o 5 min (frío); `check-runs` y `status` del head con ETag cada 30 s mientras el CI esté `pending` (o `none` en un PR caliente). Un 304 no gasta cuota (el cliente registra la cuota igual). El detalle GraphQL (`prCache.refresh`) solo se pide si algún ETag cambió, si nunca se leyó o si `mergeable` sigue `unknown` (relee a los 10 s, 3 veces). `git ls-remote --heads` por repo cada 60 s (`GitRemote.lsRemote`, sin cuota) guarda las puntas en `sync_cursors` (`refs:<repo>`) y adelanta la visita de un PR cuyo head se movió. La reconciliación de 10 min es el sondeo de los waits, no un barrido de Watch.
- Los ETags van en `sync_cursors` (`etag:github:<cuenta>:<ruta>`) y se guardan solo después de leer el detalle: un fallo a medias no pierde el cambio. Al cerrarse o mergearse un PR se borran los de su head.
- Cuota (`quota.ts`, `throttleOf`, lee `rate:github:<cuenta>:<recurso>` con `rate_limit`): bajo 25% de REST o GraphQL los intervalos se duplican; bajo 10% solo se visitan los PRs con waits (y no hay búsqueda); sin cuota nada hasta el reset. Las requests de un cliente de GitHub salen en serie (`createGitHubClient`); el segundo entre escrituras lo guardan las acciones que escriben en ráfaga (`pr-feedback.ts`).
- El caché: `createPrCache({ store, repos, prs, onChange })` (`pr-cache.ts`) guarda en `pull_requests.detail` el último `PrState` y llama a `onChange` solo si cambió; el core lo cablea a `signalPr(flows.signal, ref, state)` (un evento por tipo de wait). API: `prs.list` (caché, sin tocar GitHub) y `prs.refresh` (como `prs.get` pero cacheando y avisando). Un PR que el caché no conoce se lee igual y no entra. Cada `CachedPr` trae además `parents` (los `pr_parents`), `signals` (las del pack de la org del repo: nombre, tono y tooltip de cada nivel, y el patrón de sus labels) y `reviewBot`. Si lo guardado cambia, `PrCache` emite `pr.changed` sobre el PR: es lo que la UI sigue en vivo. El router usa el mismo `createPrs` que el core (con `MergeScope`); sin él, `prs.refresh` por la API pisaba el caché con `hold` en falso.
- Un error de una visita no tumba el despertar: se anota con un evento `error` (`scope: "watch.<cuenta> <repo>#<n>"`; `createErrorReporter` en `errors/reporter.ts` es el de todo el core y Watch, sus eventos, triggers y reacciones usan `within("watch")`) la primera vez que cambia su mensaje; un 401 deja la conexión `revoked`.
- Eventos (`watch/events.ts`, `createPrEvents({ store, repos, workspaces, errors })`): `PrCache.onChange(ref, state, row)` llama a `events.observe` (junto con `signalPr` para los waits; `startCore` lo comparte con el caché de la API vía `onPrChange`) y cada despertar termina con `events.flush(at)`. Un evento se emite insertando su marca en `watch_marks(pr_id, kind, key)` (índice único; `github/marks.ts`, `emitOnce`, la usan también las acciones): `pr.botReview` (`sha:reviewId`), `pr.ci` (`sha:estado`, solo verde o rojo), `pr.conflict` (sha de la punta), `pr.comment` (un id por thread de council abierto; el payload trae solo los nuevos en `threadIds`, más `base`), `pr.human` (`autor@fecha` de cada `talk`; en un draft no emite y espera a que salga), `pr.approvedWithComments` (una por aprobación: `approvalEpoch` cuenta cuántas veces el PR perdió la aprobación; también en la primera lectura, como el vigilante), `pr.mergeReady` y `pr.mergeFailed` (el sha del head, ver Estrategia de merge), `pr.merged` y `pr.base_rewritten` (`viejo>nuevo`: la punta nueva no desciende de la vieja; se hace `workspaces.fetch` y `merge-base --is-ancestor`, y si la punta vieja no está en el repo local no se emite). El evento es del PR (`subject`), con el proyecto de la corrida que lo abrió y `origin: "watch"`; el payload lleva `repo` y `number`.
- Siembra y debounce: la marca `head` guarda la última punta evaluada. Un PR sin marca `head` es la primera vez que se ve: se emite lo que el vigilante anuncia en su primer run (los hechos con `emitOnFirstRead`: `pr.conflict`, `pr.comment`, `pr.approvedWithComments`, `pr.mergeReady` y `pr.mergeFailed`) y se siembran sin emitir las claves de lo demás: `pr.human` (el `$first` del vigilante solo calla los comentarios), `pr.botReview`, `pr.ci` y lo ya mergeado. Un PR que se ve por primera vez en draft no siembra `pr.human`: sus marcas esperan a que salga de draft y entonces sale todo lo dicho, como el vigilante (que no avanza su `seen` en un draft). Emitir en la primera lectura no dispara flujos de más: `startTriggers` solo arranca los de PRs `owned`, y `flows.start` es idempotente por (flujo, sujeto). Una punta nueva en un PR abierto espera 20 s (`DEBOUNCE_MS`, desde `headChangedAt`) y solo se evalúa la final; `flush` retoma lo que quedó esperando leyendo `pull_requests.detail`, así que un reinicio no pierde nada. Un PR cerrado no espera.
- Triggers (`watch/triggers.ts`, `startTriggers`): escucha los eventos `pr.comment`, `pr.conflict`, `pr.merged` y `pr.base_rewritten` del store y arranca (`flows.start`) los flujos cuyo `trigger.type` calza, sobre el PR como sujeto, con el carril del flujo (los `pr.*` van a mantenimiento) y el perfil del proyecto que abrió el PR. Solo PRs `owned`; con threads de council no hay rebase por conflicto. Un flujo recibe de sus `params` lo que declare entre `pr` (`PrRef`), `repo` (id del repo registrado), `branch` (la branch del PR), los campos del payload (`sha`, `base`, `from`, `to`, `threadIds`, `files`...) y los `flowParams` del proyecto que abrió el PR (el payload los pisa); el `filter` del trigger compara cada clave con el payload. Un flujo que no arranca deja un evento `error`. Como escucha el store, sirve también a `stack.restack`, que anota `pr.conflict` con la misma clave que Watch.
- Cambios de Linear (`watch/tracker-changes.ts`, `trackers` de Watch): cada 60 s por proyecto activo, `Issues.hasChanges` (`changesSince` desde el cursor sin moverlo) y, si hay algo, `scheduler.tick()` (que trae las issues y lanza). `startCore` no lo cablea con `scheduler: false`.
- Sin implementar todavía: `pr.overlap` (hace falta la lista de archivos de cada PR).
- `updated_at` y las reviews: ver `docs/watch-updated-at.md`.

## Origin `ui` y la llave de la app

`x-clanker-origin` lo escribe quien llama, y el token está en `core.json` (0600, mismo usuario que los agentes): cualquier proceso que lo lea puede declararse `ui`. Como lo que `ui` autoriza no puede ser de un agente (hoy, aprobar la oferta de merge que comenta `/merge`, `prs.merge`, aprobar o reescribir un learning, pegar o borrar una credencial (`connections.setPat`, `setClaudeApiKey`, `disconnect`) y `defs.exportToRepo`, que abre un PR con tu cuenta), el core solo acepta el origin `ui` con una segunda credencial que `core.json` no tiene.

- La llave de la app son 32 bytes aleatorios que genera y guarda solo el main de Electron (`apps/desktop/src/main/ui-key.ts`): cifrada con `safeStorage` (en macOS, un ítem del llavero con acceso solo de la app, así que `security` desde otro proceso pide confirmación en pantalla) para que el core, que sigue vivo al cerrar la app, reconozca la del arranque anterior. El renderer nunca la ve: la agrega el proxy `clanker-core://` (`x-clanker-ui-key`, descarta lo que mande la ventana) y el supervisor la usa en sus llamadas directas.
- Al core solo llega su SHA-256 (`hashUiKey`). `ensureCore({ uiKey })` lo entrega por stdin al lanzarlo (`--ui-key-stdin`), nunca por argv ni env, que otro proceso lee con `ps`, y el core lo guarda en `meta.ui_key_hash` para que un core que relance la CLI siga reconociendo a la app. Un core vivo que no la reconoce (`system.health.uiKey: false`, por ejemplo uno lanzado por la CLI antes de que la app existiera) lo reemplaza `ensureCore` como a uno de otro `apiMajor`.
- `startServer({ uiKeyHash })`: una request con `x-clanker-origin: ui` sin la llave, o con otra, es 403, y sin `uiKeyHash` configurado ninguna es `ui`. Un cliente con solo el token usa `cli` o `mcp`, y lo que resuelve así queda así en los eventos y no vale para la oferta de merge. `/mcp` siempre es `mcp`.
- Con `CLANKER_HOME` (tests, demo, e2e) no hay llavero: la llave es `isolatedUiKey(home)`, sin valor de seguridad. El core de demo (`demo-core.ts`) recibe su hash para que la app se conecte a él en vez de reemplazarlo.
- Modelo de amenaza: un agente con la sesión del usuario que solo lee `core.json` y llama a la API, la CLI o el MCP ya no puede ser `ui`. No se defiende, a propósito, de uno que lea la memoria del main de Electron (con las protecciones del SO para apps firmadas) ni de uno que acepte el diálogo del llavero, escriba `clanker.db` (`meta.ui_key_hash`), apague el core y lo relance con su propio hash (`--ui-key-stdin`) o modifique el bundle de la app: con ese acceso ya puede hacer lo mismo con los datos y los permisos del usuario, y el diálogo del llavero es justo la confirmación humana. Sin cifrado disponible (`safeStorage` no sirve, típico en Linux sin secret store) la llave es nueva por arranque y el core se relanza al abrir la app.
- Qué sigue abierto a `cli` y `mcp` a propósito (decisión de Simón): crear o editar defs (el prompt de un rol, un flujo, un perfil) y `projects.update` (`conventions`, `maxCostUsd` y el resto). Una persona le pide esos cambios a su agente por el MCP y el cambio queda en los eventos con su origin; lo que solo vale desde la app es lo que entra a los briefs sin otra revisión (aprobar un learning o editar uno aprobado), lo que publica con la identidad del usuario sin preguntar (mergear, aprobar la oferta de merge, exportar una def al repo) y las credenciales (pegar un PAT o una API key, desconectar una cuenta).

## Proceso del core

El core corre como proceso propio (`packages/core/src/main.ts`, bundle en `packages/core/dist/main.js` con `npm run build -w @clanker/core`; las migraciones quedan en `packages/core/migrations`, al lado). `--data-dir` (o `CLANKER_HOME`) dice dónde; con `CLANKER_HOME` el core no toca el Keychain (secretos en archivo bajo `secrets/`) y los logs van a `<CLANKER_HOME>/logs`. Lo lanza `ensureCore({ dataDir, logDir, entry, origin })` de `@clanker/api/node`, que también tiene `clankerDirs()` (rutas por SO) y `readCoreJson`/`connectToCore`.

- Orden de arranque: `core.lock` (`wx`; un pid muerto se recupera) → abrir y migrar la base → abrir el puerto → `boot_id` en `meta` → `core.json` (0600). Quien lee `core.json` ya puede llamar a la API.
- Apagado (SIGTERM, SIGINT o `system.shutdown({ drain })`, `Core.close({ drain })` en `core.ts` y `runCore` en `daemon/core.ts`): `scheduler.close()` va primero (el cierre no abre corridas nuevas); `flows.close({ graceMs })` deja de despachar, interrumpe a los agentes de una vez y, con `drain`, da hasta 60 s a las acciones (sin él, o con una señal, las aborta ya); después `procs.stop(10 s)` manda SIGTERM al grupo de cada proceso del core y SIGKILL a los que sigan; cada paso cortado vuelve a `pending` con `deferrals` + 1 (ni intento ni `recoveries`: un apagado limpio no cuenta para el loop de crash) y su sesión marcada para retomarse, como tras un corte; recién entonces se cierra el servidor, `wal_checkpoint(TRUNCATE)`, la base y se borran `core.json` y `core.lock`. El servidor sigue contestando durante el drenaje y `core.json` sigue ahí: otro cliente que llega ve un core vivo que se apaga, no un directorio sin dueño. Una segunda señal mata el proceso sin más (el próximo arranque lo recupera). Un crash deja `core.json`, `core.lock` y las filas de `procs`, y el próximo arranque los recupera.
- `procs` (`createProcs({ store, bootId })`, `packages/core/src/procs/`; `startCore` acepta uno ya creado en `procs` para que el runtime Claude lo comparta): los procesos que lanza el core van en su propio grupo (`detached: true`) y se registran con `track` (los comandos de `workspaces.exec` y de `repos.testRecipe`, el `git` de red de `git/remote.ts` y el proceso de Claude Code, que `createClaudeRuntime({ procs })` lanza con `spawnClaudeCodeProcess` anotando el `stepRunId` de `RunSpec`; el `git` local corto y los `execFile` de Keychain y del probe de Claude no se registran). Todo proceso nuevo y de vida larga que lance el core pasa por `track`. Un proceso solo se mata si su pid sigue con la hora de inicio que el SO le dio (un pid reusado no se toca): `killOrphans()` al arrancar mata el grupo de las filas de otro `boot_id`, y `stop()` solo toca lo que este core lanzó. `workspaces.recover()` renueva y vuelve a latir los worktrees de corridas vivas (mismo token), suelta los de corridas terminadas y deja sin lease los que estaban `creating`; una corrida que ya tiene su worktree lo puede volver a tomar (se re-ejecuta su `workspace.acquire`). Si algo se recuperó, `startCore` emite `core.recovered` con `{ steps, leases, orphans }`.
- `ensureCore` (`@clanker/api/node`) revisa el `apiMajor` del core que contesta tras lanzar: si no es el que lanzó este proceso (otra llamada ganó la carrera) y tiene otro `apiMajor`, lo apaga con drain y lanza el suyo; si se repite, lanza un error. Espera el drenaje hasta 90 s.
- Los tests de proceso (`packages/core/src/daemon/daemon.test.ts`) construyen el bundle y lanzan el core real sobre un `CLANKER_HOME` temporal. A mano: `CLANKER_HOME=$(mktemp -d) node packages/core/dist/main.js`.

## Receta del repo y checks

`Recipe` (`packages/api/src/recipe.ts`) es el esquema de `.clanker/recipe.json` (`docs/design.html#d-ops`). Las variables son solo `{{slot}}`, `{{slot+N}}`, `{{worktree}}`, `{{branch}}`, `{{files}}` y `{{envKeys}}`: una desconocida o una expresión se rechaza al leer la receta. La acción `recipe.check` (`packages/core/src/recipe/recipe.ts`, args, outcomes y output en su TSDoc) corre los `checks` en orden y se corta en el primer rojo.

- Una receta inválida y un `{{slot}}` sin slot son `PermanentActionError`: no se reintentan. Un `requires` que falla es un `EnvironmentError` (abre el breaker del repo), no un check rojo.
- `workspaces.exec` corre `sh -c` en el worktree con un entorno mínimo (`PATH`, `HOME`, `USER`, `LANG`, `TMPDIR`, `SHELL`; nunca `GH_TOKEN` ni `LINEAR_*`); la salida completa va a `<logDir>/runs/<runId>/<stepId>.log`. Un exit distinto de 0 es un resultado, no una excepción.
- Con `startCore({ recipeResults })` (el runtime fake; el `startCore` del testkit lo pasa solo si está entre los runtimes), `recipe.check` no corre nada y consume `run.<check>` del guion, salvo los `requires`: son el entorno real del repo y se prueban igual. Se prueba en `packages/testkit/src/recipe.test.ts` (repos git reales).
- Este repo tiene su propia receta (`.clanker/recipe.json`) para que Clanker Yard se desarrolle a sí mismo: `requires` Node >= 24 y npm, `setup.worktree` es `npm ci`, y los checks son `typecheck`, `lint`, `test:related` (`vitest related {{files}}`, rápido y con los archivos que cambió la issue) y `test` (la suite completa, siempre al final). Las plantillas llaman a `recipe.check` con `scope: "changed"`, así que un check con `{{files}}` se salta si no cambió nada y uno sin `{{files}}` corre siempre. No define `slots`: los tests usan `tmpdir()` y puertos efímeros. Al cambiar un comando de `npm run`, ajústala.

## Slots por carril

`createSlots({ store })` (`packages/core/src/slots/`, `docs/design.html#d-ops`) da los slots de entorno de un repo, compartidos por todos los proyectos que lo usan: `recipe.slots` fija un pool `dev` y uno `maintenance`, y un pool lleno nunca presta ni espera al otro. Leases, latido y fencing funcionan como los de un worktree.

- El slot es del paso, no de la corrida: una corrida estacionada nunca conserva uno. `slots.recover()` suelta al arrancar todos los que tienen dueño.
- `recipe.check` prepara el slot (`setup.guard` y `setup.slot`) solo si está `dirty`, lo preparó otro worktree o cambió el hash de `setup.slotKey`. Un `setup.slot` rojo deja el slot `dirty` y el paso en `fail`. `setup.worktree` corre al crear el worktree, sin slot; si falla, el worktree se borra.
- Falta: `commits.apply` sigue recibiendo `slot` de quien lo llama y los agentes todavía no reciben un slot.

## Circuit breakers

`createBreakers` (`packages/core/src/breakers/`, `docs/design.html#d-ops` y `#nunca-se-congela`) pausa solo lo que depende de una causa de entorno y se cierra solo cuando la causa se va; nunca congela el loop por algo local. Ámbitos: `repo:<id>`, `runtime:<id>` y `github`. Al abrir deja una decisión `alert` en la bandeja; al cerrar la deja `superseded`. Causas, backoff y pruebas (`probes.ts`) en su TSDoc.

- En el motor, un paso cuyo ámbito está abierto sigue `pending` sin gastar intento (un agente depende del `runtime:<id>` de su entrada del perfil y del `repo:<id>` de su worktree; una acción con `needsRepoEnv`, del repo; una con `effects: "remote"`, de `github`). Waits, gates y subflujos no dependen de ninguno.
- Un error de entorno nuevo se lanza como `EnvironmentError(scope, mensaje)`, no como un fallo del paso. Un 401 de GitHub en un fetch o push (la conexión ya quedó `revoked`) es `githubUnauthorized(cuenta, qué)` (`breakers/breakers.ts`) en todos los caminos: el paso espera al breaker `github` en vez de fallar o reintentarse. Linear no abre breakers: sus fallos son por proyecto en el Scheduler.
- `startCore({ breakerBackoffMs })` acorta el backoff de las pruebas (solo para tests: sale de un `setTimeout` real).
- Tests: `breakers/breakers.test.ts`, `breakers/probes.test.ts`, `flows/breakers.test.ts` y `packages/testkit/src/breakers.test.ts`.

## Proyectos, corridas y arranque

`startCore(...)` (`packages/core/src/core.ts`) arma el core sobre un store abierto: cada agente corre con el runtime de su entrada del perfil, entre los `runtimes` registrados (ver Runtimes de agentes; `CORE_RUNTIME` los fuerza todos a uno, y uno que no está registrado hace fallar el arranque), registra todas las acciones y waits, instala las plantillas builtin y los packs, y llama a `flows.recover()` antes de levantar la API. El dispatcher no arranca solo: una acción o un wait nuevo se registra antes de `flows.recover()`, o los pasos pending del core anterior no lo encuentran. `runCore` solo agrega el lock, `core.json` y las señales, y registra `claude-sdk` y `opencode`: el fake vive en el testkit, así que un test levanta el core en proceso con `startCore` (`packages/testkit/src/core.test.ts`); con el binario real `CORE_RUNTIME=fake` todavía no es posible.

- `startCore` usa un solo `createPrs` y unos solos `packs` para los waits y las acciones de PR. Para los tests: `gitUrl(repo)` (por defecto `https://github.com/<repo>.git`) apunta a un bare local o a `startGitHttpServer`, `linearEndpoint` a `startFakeLinear`, y `recipeResults` (el runtime fake) reemplaza los checks de la receta. Un pack roto de `packsDir` (por defecto `<dataDir>/packs`) deja un evento `error` con `scope: "packs.load"` y no tumba el arranque.
- Al terminar una corrida (`run.finished`) el core suelta los worktrees que aún tiene (`workspaces.releaseHeldBy`): `@done`, `@failed` y cancelar no pasan por `workspace.release`, y sin esto el latido del lease seguiría renovándolo. La hija de un subflujo no tiene worktree propio: no suelta nada.
- Brief de los pasos agent: el motor llama a `briefFor` (`createStepBriefs`, `agents/step-brief.ts`, sobre `createBriefs`) y el agente recibe `.clanker-run/` (`issue.md` de la issue del sujeto leída del tracker, `diff.patch`, `hunks.json` y `diff-round.patch`). `diff-round.patch` es lo que cambió desde la última vez que ese mismo nodo miró el worktree: el snapshot de cada paso queda como artefacto de la corrida (ref `snapshot/<nodo>/<visita>/<intento>`) y el paso siguiente del nodo parte del más reciente. Todavía no se escriben `reports/` (los reportes de rondas anteriores): una sesión que se retoma reusa su fila y solo conserva el último reporte, así que habría que sacarlos de los outputs de los pasos, que no traen el `summary`. Los flujos ya pasan lo previo por el payload del brief (`previous: $self`, `plan`...).
- Una issue reclamada queda `in_progress` mientras dure su corrida y al terminar: sale de la cola (ver Cola) y no vuelve. El paso a `in_review` o `done` al mergear es de Watch (fase 2); una corrida fallida o cancelada tampoco devuelve la issue a `todo`.

- `projects` (`createProjects({ store, defs })`, API `projects.list|get|create|update`): `default_flow_id` y `default_profile_id` guardan el slug de la def. Con tracker `local`, `tracker_ref` es el id del proyecto (así se llama el proyecto del tracker local, ver `issues.createLocal`, que exige un proyecto local existente); el `ProjectBinding` de `issues.sync` sale de (`tracker`, `tracker_ref`). Además guarda `repos` (tabla `project_repos`: orden y labels de cada uno), `queue_filter`, `stack_on` (`ready`, `ci_green` por defecto o `any_open`: cuándo una issue se apila sobre el PR de su bloqueante, ver Cola), `status_mapping` (estados del tracker por nombre a categoría; el adapter de Linear lo lee por proyecto en `startCore`, y cambiarlo con `projects.update` borra el cursor de `issues.sync` de ese proyecto), `conventions` (la forma de las del pack; pisan a las del pack) y `max_cost_usd` (`null` es sin tope; hoy solo se guarda, nadie lo aplica). Un cambio de `status` emite `project.paused|resumed|archived`. `runs.project_id` e `issues.project_id` siguen sin FK. `projects.update` recibe los campos planos junto al `id` y rechaza un campo desconocido (`ProjectPatch` es estricto): un `{ id, patch: {...} }` no se ignora. Cualquier entrada inválida llega al cliente con el detalle en el mensaje (`explainInputValidation`, `server/server.ts`). `defs.update` toma el id `def_...` o el slug.
- `repos` (`createRepos({ store })`, API `repos.list|overview|add|detect|testRecipe`; `repos.overview` es lo que muestra Conexiones: cada repo con su receta y su última prueba): `repos.add` registra la raíz de un checkout (nombre, branch por defecto y remoto `owner/name` de GitHub salen de git; `repos/inspect.ts`, junto a `repos/repos.ts`); `createRepos({ store }).add` sigue siendo el insert directo para código y tests. `repos.detect(carpeta)` lista los repos de la carpeta (ella misma, o sus subcarpetas directas) con su receta `found`, `missing` o `invalid` (con el mensaje con la ruta del campo); no registra nada. `repos.testRecipe` (`recipe/recipe-test.ts`) corre `requires`, `setup.worktree`, `setup.guard` y `setup.slot` en un worktree detached desechable (con el `wrap` y el `env` de la receta) y emite `recipe.test_started`, `recipe.test_output` (`{ repoId, phase, text }`, agrupada cada 250 ms) y `recipe.test_finished`. Corre `setup.worktree`, `setup.guard` y `setup.slot` en ese orden, con un slot libre del pool de mantenimiento si la receta define `slots` (con el pool lleno falla sin esperar; sin `slots`, una receta que usa `{{slot}}` es un error de la receta). Al terminar suelta el slot y lo deja sin worktree que lo haya preparado, así el próximo uso corre `setup.slot`. `RepoConfig.remote` sale de la columna `repos.remote` (`owner/name`) con `githubRemote` (`github/remote-config.ts`): la URL `https://github.com/<repo>.git` y la cuenta de GitHub conectada (la de la org del repo si hay varias); sin cuenta conectada el repo no tiene remoto y `pr.publish` lo dice.
- Cola (`projects.queue({ id })`, `scheduler/`): `tickDev(input)` (`scheduler/queue.ts`) es la función pura (`docs/design.html#d-ops`, "Scheduler: la cola") que recibe el caché de issues entero, las corridas raíz del carril dev (`QueueRun`) y los PRs abiertos del sistema de las issues bloqueantes (`QueuePrFact`) y devuelve las `QueueEntry` con su `state` (`ready` con `base` y `dependsOn`, `waiting`, `blocked`) y su `reason`. Elegible: estado en `queueFilter.status` (default `todo`), `queueFilter.labels`, sin `excludeLabels` (default `no-clanker`), sin dueño o de `tracker.viewer()`, sin sub-issues abiertas (los hijos salen del caché por `parent`, de cualquier proyecto) y sin ninguna corrida dev raíz sobre ella, viva o terminada (por eso una issue terminada no vuelve; la de varios repos sigue hasta tener una corrida en cada uno, ver Repo de la issue). Orden: prioridad (0 al final), milestone (con fecha primero, luego sin fecha, luego sin milestone), la que bloquea a más, estimate menor y creación (el id es un ULID). La tabla de bloqueantes está en `judge`: done o canceled no bloquean; un PR abierto del mismo repo que cumple `stackOn` del proyecto (`ready`, `ci_green` por defecto, `any_open`) es la base (`stacked`; dos PRs en cadenas distintas dan `combined`, que el Scheduler arma con `workspaces.combineBase` (ver Bases combinadas)); uno de otro repo deja la base por defecto y `dependsOn` con `repo#n`; un bloqueante con corrida viva es `waiting`; cualquier otro caso es `blocked` con el motivo. Si el bloqueante tiene un PR que no cumple `stackOn`, espera mientras su corrida viva y bloquea cuando terminó. Con `relations` o `subIssues` en `false` en las `capabilities` del tracker no se calculan bloqueos ni hijos. El orden de salida es ready, waiting y blocked, cada grupo en su orden. `createProjectQueue(...)` (`scheduler/project-queue.ts`) arma esa entrada: caché, `runs`, `pull_requests` (owned y open) y `tracker.viewer()`; solo con `stackOn: "ci_green"` mira cada PR para saber si sigue abierto y su CI (el `detail` que dejó Watch y, si no hay, `prs.get`), y un error de lectura queda en el `reason` en vez de fallar. Desvíos del diseño: se clasifican todas las elegibles (sin el corte en 15) y la cola no aplica `conflictsWithRunning`, los breakers ni `parallel`: eso es del lanzamiento (Scheduler, abajo). Una issue saltada con `projects.skipIssue` (`skipped` de `TickDevInput`, tabla `issue_skips`) sale `blocked` con ese motivo. La UI de Proyecto muestra "En cola" desde `projects.queue`.
- `runs.start({ projectId, issueId, flow?, params? })` (`projects/start-run.ts`) reclama la issue con `Tracker.claim` (adapters `local` y `linear`; un tracker sin adapter es `BAD_REQUEST`), la resincroniza al caché, emite `issue.claimed` y lanza el flujo (el `defaultFlowId` del proyecto si no se pide otro) sobre ella; vuelve sin esperar y el progreso se sigue con `events.stream` (`run.finished`) y `runs.get`. Si el flujo no arranca después de reclamar, la issue queda reclamada (reclamar es idempotente). Params: si el flujo declara `repo` y `base`, salen del repo que le toca a la issue (ver Repo de la issue) y de su branch por defecto; los pisan `flowParams` del proyecto (solo con su flujo por defecto; su `repo` solo vale en un proyecto sin repos, para que una issue nunca corra fuera de los repos de sus labels) y luego `params` (`dependsOn`, que pone el Scheduler desde la cola, se descarta si el flujo no lo declara; `techlead-clasico` lo declara y lo pasa a `pr.publish`). Los rechazos del motor (`RunStartError`) llegan como `BAD_REQUEST`.
- Repo de la issue (`projects/issue-repos.ts`, `projects/repo-question.ts`, `docs/design.html#d-ops` y decisión #6): `planIssue` es puro. Los repos de la issue son los de `project.repos` cuyos labels calzan, en el orden del proyecto; si ninguno calza, el que se eligió en la decisión, el único del proyecto o, con varios, la issue es `ambiguous`. Una issue ambigua sale `blocked` en la cola y el Scheduler deja en la bandeja una `question` (`askWhichRepo`, título `¿De qué repo es CLA-N?`, sujeto la issue, opciones los nombres de los repos, una sola pendiente por issue); si dos repos del proyecto se llaman igual la opción es `nombre (id)`; responderla con `decisions.resolve` fija el repo (`chosenRepos` lee la última respuesta y la ignora si ya no es de un repo del proyecto) y el próximo tick la lanza. Con varios repos calzados, la issue corre una vez por repo, encadenadas: el repo de una corrida es su `params.repo` (por eso el flujo debe declarar `repo`, o `runs.start` lo rechaza), la issue sigue elegible tras la primera aunque ya no esté en `todo` (salvo que se cierre), la siguiente espera mientras la anterior vive (`waiting`), queda `blocked` si no terminó `done` (se arregla relanzándola a mano con `params.repo`) y sale sobre la branch por defecto de su repo con `dependsOn` el PR abierto del anterior. `runs.start` sin `params.repo` toma el siguiente repo de la cadena; en una issue ambigua falla con un mensaje que dice qué hacer. Pendiente: el agente barato que decide el repo (hoy solo la decisión).
- Scheduler (`createScheduler(...)`, `scheduler/scheduler.ts`, `docs/design.html#d-ops` y `#nunca-se-congela`; `startCore` lo arma y lo arranca con `scheduler.start()`, y `StartCoreOptions.scheduler: false` lo deja apagado para los tests que lanzan a mano): `tick()` corre al bootear, al terminar o estacionarse una corrida (`run.finished`, `run.parked`), al resolverse una decisión, con `issue.synced`, `issue.queued`, `pr.merged` y cambios del proyecto (`project.created|updated|resumed`), con `system.setLanes` y cada 5 min (`SCHEDULER_TICK_MS`). Los ticks no se solapan (un disparo durante uno pide otro al terminar; los `issue.synced` del propio tick no) y nunca lanzan: lo que falla queda en un evento `error` (`scope: "scheduler.tick"`, una vez por mensaje). Primero `flows.wake()` (admite lo que espera cupo, el mantenimiento primero, y las reencoladas antes que las nuevas) y después, por cada proyecto `active`, trae del tracker lo que cambió (`issues.sync`: Watch solo mira PRs, así que nadie más lo hace; si falla, ese proyecto no lanza hasta el próximo tick) y recorre las `ready` de `projects.queue` en orden mientras `hasRoom` (`flows/lanes.ts`: tope global del carril dev y `parallel` del proyecto) lo permita. No lanza una issue `ready` si: es relacionada (`blocks` o `related`, en cualquier sentido) de otra con corrida dev viva, también estacionada (una bloqueada que la cola ya aprobó apilar sobre el PR de su bloqueante no entra aquí); `repo:<id>` o el `runtime:<id>` de algún rol del perfil del proyecto están en pausa según `breakers` (`Breakers.openReason(scope)`, ver Circuit breakers; `startCore` pasa los reales y `breaker.closed` dispara un tick); o `runs.start` falla (claim perdido con su relectura en el adapter, flujo que falta). Una apilada pasa `params.base` con la branch del PR padre, y una combinada con su branch sintética `clanker/base/<clave>`, que arma antes de lanzar (si los padres chocan no se lanza y queda `waiting`: ver Bases combinadas); una con `dependsOn` los pasa como `params.dependsOn`. Cada issue saltada queda con su motivo: `issue.skipped` `{ issueId, reason }` (solo cuando el motivo cambia) y `scheduler.queue` (lo que sirve `projects.queue`) la muestra `waiting` con ese motivo. `projects.skipIssue({ id, issueId, skipped })` la saca de la cola (tabla `issue_skips`; `false` emite `issue.queued`); El cupo de un proyecto se cambia con `projects.update({ parallel })`.
- Carriles (`flows/lanes.ts`, `scheduler/lanes.ts`): `createLaneSettings({ store })` guarda en `meta` (`lanes`) la capacidad de la máquina (`system.setLanes({ dev?, maintenance? })`, `system.lanes` la lee con el uso): mantenimiento 2 y dev 4 por defecto, y rige al instante porque el motor la lee en cada admisión (`createFlows({ laneCapacity })`; sin ella no hay topes, como en los tests del motor). Una corrida raíz ocupa un cupo mientras está `running`, `waiting` o `paused`; `parked` y `queued` no, y las hijas de un subflujo usan el de su raíz. Mantenimiento nunca usa ni espera el cupo de dev. Sin cupo, una corrida nueva queda `queued` y una estacionada cuya decisión se resolvió sigue `parked` sin decisión abierta (conserva su sujeto, igual que con un préstamo) hasta que `promoteQueued` (cada `wake`) la devuelve a `running` con `run.requeued`; ahí van primero las del carril de mantenimiento y, dentro de cada carril, las más antiguas. Bajar un tope nunca interrumpe lo que ya corre. Los breakers (sección Circuit breakers) pausan los pasos en el dispatcher; la admisión de una corrida `queued` de mantenimiento no los consulta, porque aún no tiene workspace y su primer paso ya queda pausado por el dispatcher.
- Plantilla `juguete` (`packages/core/src/testing/juguete.ts`, `JUGUETE_TEMPLATE`): solo de demo y tests, el core de producción no la instala; se suma con `startCore({ builtins: [JUGUETE_TEMPLATE] })` (el testkit lo hace en `packages/testkit/src/start-core.ts`) y entonces queda como `builtin`: `workspace.acquire` → agente `juguete` → `workspace.release`. Necesita los params `repo` (el id de un repo registrado) y `base`: salen del repo del proyecto, o `repo` se fija en `flowParams`. Su guion para el fake está en `packages/testkit/fixtures/runs/juguete`.
- `workspaces.held(runId)` es el `workspaceOf` de Flows: el worktree que la corrida tiene tomado.
- Archivar y limpiar (`workspaces.cleanup()`, `workspaces/archive.ts`, `docs/design.html#d-ops`; `startCleanup`, `workspaces/cleanup.ts`, lo llama `startCore` al arrancar, cada hora, al terminar un PR por `onPrChange` y en cada `lease.released` de un worktree): el estado sale de `pull_requests` (por repo y `head_ref`), no de eventos, así un PR cerrado sin merge cuenta igual. Un `idle` sin dueña cuyos PRs están todos mergeados o cerrados pasa a `archived` (`archived_at`); si algún PR de la branch vuelve a estar abierto, regresa a `idle`. A los 7 días (`ARCHIVE_TTL_MS`): `worktree unlock`, `remove`, `branch -D` y se borra la fila, salvo que haya cambios sin commitear, un rebase en curso o un HEAD (sin la carpeta, la punta de la branch local) que ni `remote_sha`, ni la punta del PR, ni `origin/<branch>` contienen: ese se conserva archivado (`kept`) sin avisar. Nunca toca un worktree con dueña (viva o estacionada): se archiva en la pasada que sigue a su `release`. La fila se borra primero en una tx que exige `archived`, sin dueña y el mismo token; si git falla, la fila vuelve. `acquire` (y `attach`) de una branch con worktree archivado lo revive (`idle`, `archived_at` NULL): la branch sigue su curso, y el índice único de `path` impedía crear otra fila.

## Configuración que viaja con el repo (`.clanker/`)

`createRepoConfigSyncer` (`packages/core/src/repo-config/sync.ts`, API `repos.syncConfig`) carga `.clanker/flows/<slug>.json`, `roles/<slug>.md` y `profiles/<slug>.json` de `origin/<default>` (o la branch local sin remoto) como defs con scope `repo` y source `repo:<archivo>@<commit12>`. `startCore` la corre al arrancar y cada 5 min (`startRepoConfigSync`; lee lo que Watch ya trajo, no hace fetch), y `repos.add` la corre al registrar. Un archivo inválido sale en `errors` sin frenar a los demás ni tocar lo que ya había; si el archivo desaparece la def se archiva. Lo que se editó o archivó en la app sobrevive hasta que el archivo cambia. Un rol es markdown: el body menos `prompt` va como JSON entre `---` arriba y el `prompt` es el texto (`files.ts`).

- `defs.exportToRepo` (`repo-config/export.ts`): "Exportar al repo" de una def `user`. Worktree desechable en `<dataDir>/repo-config-export` sobre `origin/<default>` recién traído, un commit, push a `clanker/export-<kind>-<slug>-<sha7>` con `GitRemote` y la cuenta de GitHub del repo, PR en draft (REST). El checkout del usuario no se toca. Se prueba contra el GitHub simulado (`packages/testkit/src/repo-config.test.ts`, dos cores sobre el mismo repo).
- `projects.exportConfig` / `projects.importConfig` (`projects/config.ts`, `ProjectConfig` en `@clanker/api`): los ajustes del proyecto con repos por nombre y remoto. Importar se aplica a un proyecto existente (no cambia nombre, tracker ni `trackerRef`), valida todo antes de escribir y con `dryRun` devuelve `changes` y `unmapped` (repo no registrado, flujo o perfil que no existe aquí; se omiten sin frenar el resto). Si ningún repo de la configuración se encuentra, la lista de repos no se toca.

## Commits del plan

`commits.apply` (`commits/apply.ts`), `preparePush` (`commits/prepare-push.ts`) y `pr.pushFixups` (`github/actions/push-fixups.ts`) explican su mecánica en su JSDoc (`docs/design.html#d-ops`, commitPlan y push y squash; `#d-flows`, Fixups). Lo que no se ve ahí:

- Nada toca el worktree hasta que todo está verificado: los commits del plan se arman y se prueban en un worktree de verify temporal, y si algo falla la branch vuelve a donde estaba.
- El mensaje cumple Conventional Commits (o el `messagePattern` del pack) y el core le saca las líneas de atribución a una IA (`cleanMessage`). Un commit que el agente hizo por su cuenta solo se acepta si cumple lo mismo; si no, vuelve a cambio sin commitear.
- Todo `git` del core sale de `packages/core/src/git/git.ts` (`git`, `gitRaw`, `tryGit`, `GitError` con `output`): no definas otro helper. Ese git hereda solo `PATH`, `HOME`, `USER`, `LANG`, `TMPDIR` y `SHELL` más el `env` que le pases (los hooks y el config del worktree los escribe el agente); un secreto nuevo nunca llega por ahí.
- Ese git lee el ~/.gitconfig del usuario: un comando que reescribe la branch (rebase, merge) apaga explícito lo que ese config podría prender y cambie el resultado (`--no-autostash`, `--no-update-refs`).
- Con `council: true` no hay squash y `workspaces.push` nunca fuerza: si el `remote_sha` no es ancestro de `HEAD` lanza sin pushear.
- `routeHunks` (`commits/route.ts`) manda cada hunk al commit dueño de las líneas que quita o cambia (`git blame`; con varios dueños, el más nuevo). Un commit posterior que borró una línea pegada no se ve en el blame: ese `fixup!` choca y deja `squash-failed`.
- Los ids de `unrouted` de `pr.pushFixups` son del diff de `HEAD` contra el worktree, no los de `hunks.json` del brief.
- El motor deja `null` el ref de un nodo que no corrió (el primer `fixups` de `pr-feedback` no tiene `$route`), así que los args que leen un nodo opcional aceptan `null` como ninguno.
- Se prueban en `packages/testkit/src/` (`commits`, `prepare-push`, `pr-push-fixups` y, el guard de council del push, `git-remote`), con repos git reales.

## Sincronizar la base

`workspaces.syncBase(lease)` (`packages/core/src/workspaces/workspaces.ts`) y su acción `workspace.syncBase` (nodo sync de la plantilla, `docs/design.html#d-flows`; rebase sin PR en `#d-ops`). Hace `workspaces.fetch` si el repo tiene `RepoConfig.remote` (sin él no hay fetch y la base nueva es la que ya traiga el checkout; `repos.config` lo llena con la cuenta de GitHub conectada, ver Proyectos, corridas y arranque) y compara la punta de la base con la `base_sha` del worktree.

- Outcomes: `same`, `rebased` (el flujo corre los checks de nuevo) y `conflict` (output `conflicts` y `failures`, lo que va al dev). Solo rebasea una branch que no está en el remoto y sin commits propios; si no, lanza `SyncBaseError` (la acción lo vuelve `PermanentActionError`): eso es el rebase de un PR.
- Antes de mover nada, el árbol completo (cambios sin commit y archivos nuevos, `snapshotTree`) se guarda en `refs/clanker/backup/<branch>`: un commit sobre la base vieja; el siguiente sync pisa el respaldo. Volver: `git reset --hard <ref> && git reset --mixed <ref>^`. Luego `reset --hard` a la base nueva, `clean -fd` (solo lo no ignorado, que el patch recrea) y `apply --3way` del patch del respaldo; el index queda limpio. Un conflicto deja las marcas en los archivos; un archivo que la base nueva borró no deja marcas pero se lista y su versión está en el respaldo.
- La base nueva se guarda en la fila al final. Todo sale del respaldo, así que un corte entre el reset y el guardado se retoma al reintentar.
- `workspaces.baseSha(ws)` es la base vigente. El `baseSha` de `$ws` (output de `workspace.acquire`) no se actualiza: `recipe.check`, `commits.apply` y el brief leen la de la fila. Una acción nueva que haga diff contra la base debe hacer lo mismo.
- Se prueba en `packages/testkit/src/workspaces-sync.test.ts` (repos git reales con `origin` bare).

## Rebasear un PR abierto

Carril maintenance (`docs/design.html#d-ops`, rebasePr, y la plantilla de rebase por conflicto en `#d-flows`): `workspace.attach` → `workspace.rebase` → (agente en modo conflict → `workspace.rebase` con `continue`) → `recipe.check` con `afterRebase` → `pr.pushLease`. Es lo que `syncBase` rechaza (branch ya publicada o con commits propios). La plantilla que arma ese flujo es `rebase-conflicto` (ver abajo, "Plantilla clanker-loop"); el agente de conflictos es el modo `conflict` del rol `dev`.

- `workspaces.attach(request)` (acción `workspace.attach`, mismos args que `acquire`): `workspaces.fetch`, toma el lease (crea el worktree desde `origin/<branch>` si no existe) y avanza la branch local a la punta del remoto con `merge --ff-only`; esa punta pasa a ser el `remote_sha`. Una branch que no está en el remoto, o una local con commits que el remoto no tiene (adelantada o divergida), lanza `AttachError` (la acción: `PermanentActionError`) y suelta el lease. Output: un `$ws` más `fastForwarded`.
- `workspaces.rebase(lease, { council, base?, continue? })` (`workspaces.ts`; la mecánica de git en `rebase.ts`). Precondiciones, o `RebaseError`: sin council (nunca se fuerza), `HEAD` = `remote_sha`, árbol limpio (sin contar `.clanker-run/`) y sin un rebase en curso. No hace fetch: usa lo que `attach` trajo. La base es `base` (`origin/main` y `main` son lo mismo) o la del worktree. `from` solo existe si el PR cambió de base (el de abajo se mergeó, con squash o sin él): es el `remote_sha` del workspace de la base vieja o, sin él, `origin/<base vieja>`, y tiene que ser ancestro de `HEAD`. Con `from`: `rebase --onto <base> <from>`; sin él, `rebase <base>`. Siempre con `--no-autostash --no-update-refs`.
- Outcomes: `clean` (guarda `base_ref`, `base_sha` y `head_sha`; el `remote_sha` no cambia: el push con lease lo compara con eso), `conflict` (el rebase queda detenido con HEAD detached; `conflicts` son los archivos sin mergear, `applying` el commit que se aplica, `failures` el extracto) y `error` (falló sin conflicto: `rebase --abort` y la branch queda como estaba).
- `continue: true` sigue ese rebase, un commit a la vez: si en los archivos que el worktree cambió contra `HEAD` quedan marcas `<<<<<<<` o `>>>>>>>` (aunque ya estén en el index) devuelve `conflict` sin avanzar; si no, `git add --all` y `rebase --continue`, que termina (`clean`) o se detiene en el siguiente commit (`conflict`). Pasados 20 commits con conflicto (`MAX_CONFLICTED_COMMITS`, contados en un archivo dentro de la carpeta `rebase-merge` del worktree, que git borra al terminar) aborta con `error`. Si el agente terminó el rebase por su cuenta, `continue` solo lo registra. Hay que pasar la misma `base` en cada visita.
- La acción `workspace.rebase` (`github/actions/rebase-pr.ts`, args `{ ws, base?, continue? }`) busca el PR abierto de la branch en `pull_requests` (solo `owned`: Watch también guarda ahí tus PRs que el sistema no abrió, y esos nunca se reescriben ni se pushean) y lee `threads.councilEver` de `prs.get`; va en una sola etapa `ctx.once`. Las precondiciones que no se cumplen son `PermanentActionError`.
- `recipe.check` acepta `afterRebase: true`: corre antes de los checks los comandos `afterRebase` de la receta (con slot, `{{files}}` y `wrap` como cualquier check; salen en `checks` con el nombre `afterRebase` y uno rojo da `fail` con `[afterRebase] exit N`). Lo que dejen sin commitear no lo pushea `pr.pushLease`.
- `pr.pushLease` (`{ ws }`): `preparePush` (por si quedó un `fixup!`, sin reconciliar: tras un rebase `HEAD` ya no desciende de lo pusheado) y `workspaces.push` con lease, igual que `pr.publish`; con council no forzaría y lanza. Un PR cerrado o mergeado lanza. Outcomes `draft` y `ready` (por `PrState.state`); output `head` y `pr`.
- Lo que pide la plantilla `rebase-conflicto` además: `pr.rebaseApproval { pr, behavior, policy }` (outcomes `proceed` y `ask`; lee el estado vivo del PR: en draft siempre `proceed`; fuera de draft, `ask` si el agente reportó `behavior` o `policy` es `ask`), `workspace.commitAfterRebase { ws }` (commitea con `chore: update generated files after rebase` lo que dejaron el `afterRebase` de la receta o un arreglo del agente; el commit lo hace el core porque no hay nada que decidir, y sin él `pr.pushLease` no pushea esos cambios) y `workspace.rebaseAbort { ws }` (`rebase --abort` si hay uno detenido; esta y `workspace.commitAfterRebase` están en `workspaces/rebase-actions.ts` porque solo tocan el worktree; sin él, una corrida que termina a medias deja el worktree con un rebase en curso y el siguiente `workspace.rebase` del PR lanza).
- Se prueba en `packages/testkit/src/workspaces-rebase.test.ts` (repos git reales con `origin` bare: base con `origin/`, `--continue` con HEAD detached, padre squasheado, marcas pendientes, tope de 20) y `pr-rebase.test.ts` (las acciones contra el GitHub simulado); el flujo entero, en `rebase-conflict-e2e.test.ts`.

## Restackear la cadena

`stack.restack { pr }` (`packages/core/src/github/actions/restack.ts`, `docs/design.html#d-ops`, restack) rebasea los hijos de un PR del sistema ya mergeado; en un flujo lo dispara `pr.merged` (carril maintenance). `pr_parents(child_id, parent_id)` dice qué PR cuelga de cuál: `pr.publish` inserta la fila al abrir un PR cuya base es la branch de otro PR abierto del repo, y el restack la borra cuando el hijo ya quedó sobre la base nueva. Un hijo con base combinada (varios padres) se recalcula distinto: ver Bases combinadas.

- Verifica y parte de la API: el `merge_commit_sha` y la última punta del padre salen de `prs.get`. `merge.squash` del output compara el árbol del merge con el de fusionar esa punta en lo que había antes (`merge-tree`): `same`, `differs` o `unknown`. Es informativo, porque lo que cuenta es lo que quedó en la base; que el merge no esté en `origin/<base>` sí lanza.
- `workspaces.restack(lease, { council, onto, from, base })` (`workspaces.ts`; la mecánica en `restack.ts`) no usa `rebase --onto`: los commits propios son los de `from..HEAD` por el primer padre, sin los merges cuyo segundo padre ya está en `from` o en `onto` (los de release-bot[bot]); un merge de otra branch da `foreign-merge`. Cada commit se aplica con `merge-tree` sin tocar el worktree, conservando autor, fecha y mensaje, y su patch-id tiene que ser el original (si no, `conflict` sin archivos). La punta nueva se pushea con lease **antes** de mover la branch local (`reset --hard`): un conflicto, un lease rechazado o un fallo del push dejan el worktree y el remoto como estaban, y un reintento sigue siendo posible. Con la branch ya sobre `onto` y sin `from` en su historia es `uptodate`; sin commits propios, `empty`. Las precondiciones son las de `rebase` (`RebaseError`).
- Por hijo, etapas con `ctx.once`: `restack:<n>` (council, `workspaces.attach`, `restack`) y `retarget:<n>`: `PATCH` de la base del PR solo si GitHub no la movió, `pull_requests` y `pr_parents`, y una decisión `review_note` ("Descripción obsoleta") si el cuerpo nombra la branch o el número del padre. Los nietos parten de la punta que el hijo tenía antes (`from`) y de la nueva (`onto`); su base sigue siendo la branch del hijo.
- Un hijo que no se puede restackear no frena a los demás y queda como estaba: `conflict` (outcome `conflict` de la acción, con los archivos, y un evento `pr.conflict` (con `sha`, `base`, `from`, `onto` y `files`, por la clave de Watch) que arranca el flujo de rebase; sus propios hijos no se tocan) o `skipped` con la razón (council, merge de otra branch, lease rechazado, branch local adelantada o divergida, rebase en curso, PR ya cerrado). Un 401 lanza `githubUnauthorized` (ver Circuit breakers).
- Al final relee `mergeable` de todos los PRs abiertos del repo (REST, hasta 3 veces por los que GitHub aún calcula, con `pause`). Output: `merge`, `children`, `changedDrafts` (los restackeados que están en draft, a los que el flujo les pide /review otra vez) y `mergeable`.
- Pendiente: la punta del padre debe estar en el repo local (si no, el hijo se salta).
- `stack.restackRewritten { pr, from, to }` (mismo archivo; referencia en su TSDoc) es este recorrido con la punta vieja de `pr` como `from` y la nueva como `onto`, sin cambiar la base de los hijos. Lo lanza el flujo `restack-rewritten` de la plantilla con `pr.base_rewritten`, y es también lo que restackea a los nietos de un hijo que quedó en conflicto cuando `rebase-conflicto` lo resuelve y pushea. Pendiente: el hijo que `rebase-conflicto` resolvió conserva su fila de `pr_parents` con el padre ya mergeado.
- Review del bot tras el restack: `changedDrafts` son `{ pr, branch, base }` (la branch y la base con que quedó, para que un flujo tome su worktree). Los flujos `restack` (`pr.merged`) y `restack-rewritten` (`pr.base_rewritten`) siguen con un `parallel` con `forEach: $restack.changedDrafts` que llama al subflujo `restack-feedback` (`workspace.attach` de ese PR → `pr-feedback`), uno por draft y con `join: flows.worst` (el join de un forEach de subflujos: el peor `@end`, `done` si no hay ninguna). Sin drafts cambiados la lista es vacía y no corre ninguna rama ni agente; un PR restackeado que no está en draft no pide review (el restack no lo mueve de listo). Con `conflict` de la acción el flujo también sigue a `feedback`: los hijos que sí se restackearon lo necesitan, y el que chocó lo toma `rebase-conflicto`. Se prueba de punta a punta en `packages/testkit/src/restack-e2e.test.ts` (core real, cadena de 3 PRs sobre `startGitHubSim`, remoto git real y los eventos de Watch emitidos a mano con `watch: false`).
- Se prueba en `packages/testkit/src/pr-restack.test.ts` (repos git reales, remoto bare y `startGitHubSim`, cuyo `merge({ sha })` deja un squash de otro como commit del merge).

## Publicar el PR

`prPublishAction({ store, workspaces, recipes, repos, connections, packs })` (`packages/core/src/github/actions/publish.ts`) es la acción `pr.publish` (`args: { ws, plan, draft?, dependsOn? }`; `plan` es el reporte del committer: `commits` como en `commits.apply` y `pr: { title, body }`). Tres etapas con `ctx.once`, así que un reintento tras un corte retoma donde quedó (`docs/design.html#d-flows`, efectos externos):

- `apply` es `commits.apply`, que reconoce sus commits si el corte llegó entre mover la branch y guardar la etapa (mismos mensajes, en orden, y el árbol del worktree); sin eso un reintento fallaba por "la branch ya no está en la base". `push` corre `preparePush` y `workspaces.push` con lease: un lease rechazado es `PermanentActionError` y un 401 lanza `githubUnauthorized` (ver Circuit breakers). `pr` busca el PR abierto de la branch (`GET pulls?head=owner:branch&state=open`) antes de crearlo con `POST pulls`, lo guarda en `pull_requests` (`owned = 1`, con la issue y la corrida de su sujeto) y emite `pr.opened` solo si la fila es nueva.
- Título y cuerpo salen de `plan.pr` (el committer sigue `prompts/pr.md`); el core les quita las líneas de atribución a una IA (`cleanMessage`) y las secciones de `conventions.pr.omitSections` del pack de la org (con su subárbol, sin distinguir mayúsculas). `dependsOn` (`repo#n`) abre el cuerpo con "Depende de ...": `techlead-clasico` lo recibe en sus params (lo pone el Scheduler desde la cola) y lo pasa.
- Outcomes `ok` (output `pr`: la `PrRef` de `prs.get`, más `url` y `head`) y `replan`. Desvío: un hook que rechaza un commit (`hook-failed` de `commits.apply`) también es `replan`, porque el diseño solo le da dos outcomes a `pr.publish`. Un plan sin commits también es `replan`.
- El repo del PR sale de `RepoConfig.remote.repo` (`owner/repo`) y la cuenta de `remote.account`. `startCore` la registra, con askpass, git remoto y recetas cableados.
- `pull_requests` hoy tiene lo que `pr.publish` sabe (repo, número, branches, sha, estado de GitHub, `is_draft`, issue, corrida, `owned`); las columnas del polling llegan con Watch. Si la base del PR es la branch de otro PR abierto, también guarda la fila de `pr_parents` (ver Restackear la cadena).
- Se prueba en `packages/testkit/src/pr-publish.test.ts` contra el GitHub simulado del testkit (`startGitHubSim`, ver Testkit) y un remoto bare de `tempGitRepo`: `POST pulls` rechaza con 422 un PR sin título, con una branch que no existe, sin commits sobre la base o con un PR abierto igual. Los cortes se simulan con un `ctx.once` que muere justo después del efecto de una etapa.

## Stacks locales

Con `projects.stack_mode` en `local` (el default) un PR solo existe en GitHub si su base es la branch por defecto: el resto vive en la máquina como fila `local` de `pull_requests` (sin `number` ni `node_id`, con `title` y `body` guardados) hasta que se mergea su base, para no gastar CI. `pr.publish` lo guarda (outcome `local`), `stack.restack` lo restackea sin push (`promotable` son los que quedaron sobre la branch por defecto) y `pr.promote` lo publica en la misma fila: el id no cambia al publicarse. Nada de un PR local se pushea: el único push es el de `pr.promote`. Un conflicto al restackear emite `pr.conflict` con `local: true` y lo toma `rebase-conflicto-local` (`startTriggers` agrega `local` al payload antes de comparar el `filter`); `prs.publishLocal` (solo `ui`) adelanta la publicación apilado sobre su padre. En la cola, un padre local cumple cualquier `stackOn` si su corrida terminó `done`.

## Bases combinadas

Una issue bloqueada por PRs en cadenas distintas sale de una base sintética (`docs/design.html#d-ops`, "Bases combinadas"). `combined_bases` es única por (repo, issue): una issue de varios repos tiene una base por repo, con la misma branch sintética en cada uno. `workspaces.combineBase` (`workspaces/workspaces.ts`, la mecánica de git en `combine.ts`; la acción `workspace.combineBase` es lo mismo para un flujo, el Scheduler no pasa por ella) deja en la branch local `clanker/base/<clave de la issue>` (`combinedBaseBranch`) la punta de la branch por defecto con un merge --no-ff de cada padre, hechos con `merge-tree` y `commit-tree` sin tocar ningún worktree, y la registra en `combined_bases` (padres con su sha, `head_sha`, `status`: `active`, `conflict` o `dissolved`). No se pushea: sus merges viajan en la branch de la issue. Los merges son deterministas (fecha de la punta por defecto): rehacer la base con los mismos padres da el mismo sha, y de eso depende reintentar un restack cortado.

- Scheduler: antes de lanzar arma la base y pasa su branch como `params.base`. Padres que chocan: la issue no se lanza, queda `waiting` con el motivo y una decisión `note` (una vez por conjunto de padres) hasta que se mergee uno. Una issue que sale a otra base disuelve la que haya dejado un intento anterior.
- `pr.publish`: con `combined_bases` activa para la `base_ref` del worktree, el PR se abre contra la branch del primer padre, el cuerpo abre con "Base combinada: ..." y `pr_parents` guarda todos los padres. Antes de pushear (etapa `base`, `settleBase` en `github/actions/publish.ts`) pregunta a GitHub si esos padres (o la branch del padre de un PR apilado) siguen abiertos: si alguno se mergeó o cerró, recalcula la base con los que quedan (o la branch por defecto) y rehace los commits propios sobre ella con `workspaces.restack`/`restackCombined` (que aceptan una branch sin publicar: no pushean, solo mueven la local). Si no caben (conflicto, merge de otra branch) la branch queda como estaba, el PR se abre igual sobre la base correcta y queda una decisión `note`. Desvío: el diseño dice "el de mayor diff o el que se mergeará primero"; es el primero de la cola, sin medir nada.
- `stack.restack` de un hijo con base combinada (`combined_bases` de su issue, no `pr_parents`: un solo padre que queda sigue siendo base combinada hasta que no queda ninguno) llama a `workspaces.restackCombined`: junta la branch por defecto de hoy con los padres que siguen abiertos, reaplica los commits propios (los que siguen a la última punta registrada, `head_sha`) con `restack` y, tras el push, registra la base nueva; sin padres la disuelve (borra la branch) y el PR pasa a la branch por defecto. El PR se retargetea al primer padre que queda. Sin base vigente lanza `RebaseError` (el hijo queda `skipped`); una fila vieja (sin `head_sha`, o cuya punta no está en la historia del PR: la issue se relanzó a mano sobre otra base) lanza `StaleCombinedBaseError`, y `stack.restack` la disuelve (salvo que otro PR abierto de la issue en el repo la siga usando) y restackea el PR como uno apilado común.
- Conflicto al recalcular (los padres que quedan entre sí o con la base nueva, o un commit propio): la base queda en `conflict` y nada se mueve. Desvío: no se emite `pr.conflict`, porque `rebase-conflicto` rebasea sobre una branch y no sabe rehacer una base combinada; queda una decisión `note` en el PR. Pendiente: que ese flujo sepa hacerlo.
- Se prueba en `packages/testkit/src/combined-base.test.ts` (repos git reales, remoto bare y `startGitHubSim`) y el Scheduler, en `scheduler.test.ts` del core y del testkit.

## Comentarios y threads del PR

`councilThreadsAction`, `prCommentAction`, `prReplyAction`, `prResolveThreadAction` y `reviewRequestBotAction({ connections, packs, pause? })` (`packages/core/src/github/actions/pr-feedback.ts`) son `council.threads`, `pr.comment`, `pr.reply`, `pr.resolveThread` y `review.requestBot`. Salen con el token de la cuenta del PR (la identidad del usuario) y todo lo de la organización lo lee del pack: el prefijo de los comentarios (`conventions.commentPrefix`, `[clanker] ` en el pack de ejemplo), el bot (`reviewBot`), los autores resolubles (`reviewBot.resolvableAuthors`) y el prefijo del council. Lo que dice el agente pasa por `cleanMessage`: nunca firma como IA.

- Cada comentario y respuesta lleva `<!-- clanker:clave -->` con la `key` del paso (`run:nodo:visita`; en una respuesta, más `:<id del ítem>`) y se busca antes de publicar: re-ejecutar no duplica, y una visita nueva sí comenta. El comando al bot es la excepción: va sin marca (el clanker-loop comenta `/review` exacto y lo que el bot hace con otro texto no está a la vista), y no duplicarlo en un reintento lo da `ctx.once`. Entre dos escrituras de una acción hay un segundo (`pause`, que los tests reemplazan).
- Un thread se nombra por el id de su primer comentario (`fullDatabaseId`). Los ítems de triage que llegan a `pr.reply` deben usar ese id (el wait `pr.botReview` debe darlo como `id` de cada hallazgo del bot); un ítem que no es un thread (CI) se salta. `shas` es el `byItem` de `pr.pushFixups`: con sha dice `aplicado en <sha corto>`, si no, la `reply` del triage; sin ninguna se salta.
- `council.threads { pr }` da los threads de council abiertos (los de `councilOpen`: prefijo del council, sin resolver y sin una respuesta con el prefijo de comentarios) como `items` `{ id, path, line?, change }`, la forma de `DevWorkBrief.instructions` y lo que `pr.pushFixups` y `pr.reply` esperan de un ítem; sin ninguno, o con el PR cerrado, el outcome es `none`. `pr.reply` acepta `rejected` (`DevWorkReport.rejected`): su razón gana al sha que `pr.pushFixups` dio al ítem, y un thread de council que ya tiene una respuesta `[clanker] ` se salta (el flujo council vuelve a pasar por `pr.reply` tras un CI rojo y no repite lo dicho).
- `pr.reply` resuelve el thread después de responderlo solo si lo abrió un autor de `resolvableAuthors` y no es de council (un comentario con `councilPrefix`, de cualquier autor: se responde y no se resuelve). Un thread humano solo se responde con el PR en draft y nunca se resuelve. `pr.resolveThread` aplica la misma regla y rechaza con outcome `refused` y `reason`.
- `review.requestBot` da `none` sin bot (o sin pack); con bot comenta `reviewBot.request.body` sin prefijo (el bot reconoce el comando literal) y da `requestedAt` en ms con la hora de GitHub. `pr.reply` con `rerequestBot` lo hace al final y lo incluye en su output, que es lo que lee `bot-wait` (`$prev.requestedAt`).
- Se prueba en `packages/testkit/src/pr-feedback.test.ts` contra `startGitHubSim`; las plantillas (`techlead-flows.test.ts`) corren con estas acciones reales en vez de stubs.

## Brief y artefactos del worktree

`createBriefs({ workspaces, artifacts }).prepare(...)` (`packages/core/src/agents/brief.ts`) arma el `Brief` de cualquier rol y deja en `<worktree>/.clanker-run/` lo que el agente lee si lo necesita: `issue.md`, `diff.patch` contra la base del lease (incluye cambios sin commit y archivos nuevos), `diff-round.patch` (solo con `since`, el `snapshot` que devolvió la ronda anterior), `hunks.json` (`h1`, `h2`... por hunk, en el orden del patch; `id`, `path` y `header`, sin el texto) y `reports/r<n>-<rol>.json` (`createBriefs` los escribe si se los pasan; el motor todavía no). La carpeta se agrega a `.git/info/exclude` y cada archivo también se guarda en `artifacts` con una ref a la corrida (`r<ronda>/<archivo>`). El brief lleva a lo más 5 criterios (los ítems bajo "Criterios de aceptación" del cuerpo) y 10 learnings, y cita los archivos con rutas relativas al worktree. Se prueba en `packages/testkit` (necesita repos git reales).

## Learnings

`createLearnings({ store, runtime? })` (`packages/core/src/learnings/learnings.ts`, `docs/design.html#d-data`) guarda lo que un agente futuro necesita saber; solo los `approved` llegan a un brief. El alcance es un proyecto o un repo (nunca los dos) y `roles` vacío es todos los roles.

- Un agente propone con `Report.learnings`: el motor los deja `proposed` (`source: "agent"`, con la corrida) en la tx que cierra el paso, en el proyecto de la corrida; una corrida sin proyecto no propone. Una persona propone con `learnings.propose`. Aprobar o rechazar no bloquea ni toca ninguna corrida. `learnings.approve`, y `learnings.update` de uno `approved`, solo con `origin: "ui"` (`FORBIDDEN` para CLI y MCP): lo aprobado entra a los briefs sin otra revisión.
- El mismo texto en el mismo alcance no se repite, en cualquier estado (índice único): proponerlo otra vez devuelve el que había, no emite evento y no resucita lo rechazado. La importación del clanker-loop propone por `proposeLearning` (`source: "import"`, siempre `proposed`: decisión 19 del diseño) y por eso es idempotente sin clave de origen.
- `reject` deja un `proposed` en `rejected` y retira un `approved` a `archived`; `approve` sirve desde cualquier estado menos `approved`. `update` cambia texto, roles y tags, no el alcance ni el estado.
- `createStepBriefs` pide `learnings.forBrief({ projectId, repoId, role })` (proyecto de la corrida, repo del worktree, rol del nodo): los del repo primero, luego los más recientes; `createBriefs` corta en `MAX_LEARNINGS` (10). No hay tools MCP de learnings: el diseño no las lista.

## Plantilla clanker-loop

`clankerLoopTemplate` (`packages/core/src/template/`) son los roles y perfiles del equipo clanker-loop como datos: bodies de defs `role` y `profile` por slug, validados por `Role`/`Profile` de `@clanker/api`. `payloads.ts` tiene los esquemas zod de brief y reporte (el brief se pasa a JSON Schema suelto y el reporte estricto), `prompts.ts` los prompts y las instrucciones por modo, `roles.ts` y `profiles.ts` los ensamblan. `flows.ts` trae los flujos `techlead-clasico`, `pr-feedback`, `rebase-conflicto`, `restack-feedback`, `restack`, `restack-rewritten`, `council` y `republish-pr` (`clankerLoopTemplate.flows`, con `FlowDef` tipado): `installBuiltins` instala sus roles, perfiles y flujos como `builtin` en cada arranque (`pr-feedback` primero, porque los otros lo llaman, y `restack-feedback` antes de `restack` y `restack-rewritten`; si una def de la plantilla está archivada la plantilla entera queda fuera). `registerFlowStubs` (`packages/testkit/src/flow-stubs.ts`) deja guionar acciones y waits (un check rojo, un conflicto con la base) para recorrer los flujos con el runtime fake (`techlead-flows.test.ts`); lo que pasa por `pr.publish` y `pr.pushFixups` corre con las acciones reales en `techlead-e2e.test.ts`; el único flujo para elegir es `techlead-clasico` ("Techlead clásico"). `FlowDef` tiene `description` (una línea para quien elige) e `internal: true` para los flujos que el sistema dispara solo (`pr-feedback`, `rebase-conflicto`, `restack*`, `council`, `republish-pr`): los selectores de Nuevo proyecto y de Ajustes los ocultan (`selectableFlows`) y la vista Flujos los muestra aparte. El core no importa nada de aquí: el nombre de un rol solo vive en la plantilla y en sus tests.

- `rebase-conflicto` (trigger `pr.conflict`, carril maintenance, `docs/design.html#d-flows`): `workspace.attach` → `workspace.rebase` → (`conflict`: dev modo `conflict` → `pr.rebaseApproval` → `workspace.rebase` con `continue`, a lo más `conflictRounds` (20, el tope del core) vueltas compartidas) → `recipe.check` con `afterRebase` (rojo: dev `fix`, `checkRounds`) → `workspace.commitAfterRebase` → `pr.pushLease` → draft: `pr-feedback` (que pide `/review`); listo: `@done` con la nota "Pide /review". Params: `pr`, `repo`, `branch` y `base` los pone el trigger (`startTriggers`); `rebaseNonDraft` (`auto` por defecto, decisión 30; `ask` en `flowParams` del proyecto) hace que un PR fuera de draft pregunte aunque no haya conflicto de comportamiento. Con `behavior` (resolver exige decidir comportamiento, decisión 32): en draft sigue con una nota (`review_note`); fuera de draft el gate `behavior-gate` estaciona solo esa corrida y el PR queda en conflicto hasta que alguien elija `continue` (sigue con la resolución conservadora) o `abort` (`workspace.rebaseAbort` y `@blocked`). Un rebase que falla sin conflicto (`error`) estaciona con el gate `rebase-error` (`retry` o `leave`). Cada visita de `workspace.rebase` pasa la misma `base` (`$run.params.base`). El filtro "sin threads de council" no es un `filter` del flujo (compara el payload): lo hace `startTriggers`. Los `flowParams` del proyecto que el flujo por defecto no declara no rompen `runs.start`: se ignoran ahí (son de los flujos que arrancan los triggers). Se prueba en `packages/testkit/src/rebase-conflict-e2e.test.ts` (core real, dev fake con `effects: - write:` que escribe el archivo ya resuelto, `startGitHubSim` y un remoto git real).
- Un prompt no pide lo que hace el core (push, PR, checks, respuestas en el PR o el tracker) ni nada propio de un repo o empresa: eso llega como contexto del rol (`pack`, `repo`). El test de la plantilla lo verifica.
- Un rol o modo nuevo debe calzar con lo que referencian los flujos de la plantilla: su lista está en `template.test.ts`. Tras cambiar un esquema de reporte, `npx vitest run -u packages/core/src/template` regenera el snapshot; revisa el diff.

## Métricas

`recordRunMetrics(tx, runId)` (`packages/core/src/metrics/record.ts`) llena `run_metrics` y `run_role_costs` en la misma tx que cierra la corrida; todo lo que la UI muestra de costos sale de ahí vía `createMetrics`. ## MCP

El MCP (`docs/design.html#mcp`) sale del contrato: `generateMcp` (`packages/core/src/mcp/generate.ts`) arma tools, esquemas y resources desde `.meta({ mcp })` (la convención está en `packages/api/src/mcp.ts`) y `createMcpHandler` llama al router en proceso con origin `mcp`: misma validación y mismos eventos que la UI.

- Para exponer un procedimiento: `.meta({ mcp: ... })` en el contrato y, si es un kind nuevo, su esquema en `MCP_KIND_SCHEMAS`. `resolve_decision` es `destructiveHint: true`: un gate puede dejar correr pasos que publican. Una acción declara `destructiveHint` siempre explícito (un cliente lo da por verdadero si falta); sin anotaciones `generateMcp` lanza y el core no arranca.
- La escritura de defs pasa por `createDefWriter` (`defs/write.ts`): las defs `builtin` y de packs no se editan, archivan ni restauran (se pisan con una `create` de scope `user` y el mismo slug).
- `mcp.test.ts` del testkit guarda el snapshot de la lista de tools: un cambio en lo que ven los clientes se aprueba actualizándolo.
- Router `dev` (`docs/design.html#devx`, contrato en `packages/api/src/dev.ts`, router en `server/dev-router.ts`): `inject_step_result` (cierra con un outcome un paso action o wait en marcha: es `runs.forceOutcome`, que el MCP normal no expone; nunca sirve para un agente), `load_fixture` (siembra encima de la base uno de los escenarios que da quien lanza el core: `summary`, `loop-running`, `issue-blocked`; un nombre desconocido lista los que hay) y `advance_clock` (adelanta el reloj falso, hoy solo el de las conexiones). No son parte de `contract`: solo existen si el core se lanzó con `startCore({ dev })`, y sin eso ni `/rpc/dev/*` (404) ni `tools/list` los muestran. El único core que lo hace es el de demo (`createDevKit` del testkit): para que un agente pruebe la app por MCP, `CLANKER_HOME=$(mktemp -d) npm run demo-core -w @clanker/testkit` y `clanker mcp` con ese `CLANKER_HOME`. Un core real (`runCore`) nunca recibe `dev`; no agregues una variable de entorno que lo encienda. `dev.test.ts` del testkit verifica que un core normal no los sirve.
- Transporte: Streamable HTTP sin sesión en `/mcp` del puerto del core, con el mismo token. Como el token cambia en cada arranque, los clientes usan `clanker mcp` (puente stdio, `apps/cli/src/mcp.ts`); `.mcp.json` lo corre desde el checkout y necesita el core construido.

## Motor de flujos

`createFlows({ store, defs, agents, artifacts, roles, workspaceOf })` (`packages/core/src/flows/`) valida, guarda y ejecuta flujos (`docs/design.html#d-flows`): nodos `agent`, `action`, `wait`, `parallel`, `flow` y `gate`. El detalle de cada pieza está en el TSDoc de `engine.ts` (la interfaz `Engine`: `control`, `stepCommand`, `resolveGate`, `recover`; y `openChild`, `parkOverLimit`; lo que una persona le pide a una corrida vive en `commands.ts`, los gates y decisiones en `gates.ts`, cancelar una corrida con sus hijas en `run-family.ts` y lo que comparten en `engine-shared.ts`), `flows.ts`, `catalog.ts`, `parallel.ts`, `consolidators.ts` y `subjects.ts`; aquí van las reglas que no se ven leyendo un solo archivo.

- `flows.start` es idempotente por (flujo, sujeto) mientras la corrida siga viva y fija las versiones del flujo, sus subflujos, roles y perfil. Rechaza antes de crear nada un gate como rama de un parallel (también dentro de un subflujo): un gate estaciona la corrida entera.
- Acciones (`registerAction`): un outcome de negocio nunca se reintenta; solo una excepción, según `retry` (3 por defecto, con 10 s, 60 s y 5 min). Lo que reintentar no arregla se lanza como `PermanentActionError`. `ctx.key` (`run:nodo:visita`) y `ctx.stepId` son estables entre reintentos y `ctx.once(etapa, fn)` guarda cada etapa en `action_effects`: un efecto remoto va dentro de un `once`.
- Waits (`registerWait`): `probe` al entrar; si no resuelve, el paso queda `waiting` con `wait_key` y `deadline` hasta un `flows.signal` que calce, un sondeo (`probeEverySec`, 60 s; con Watch el core lo sube a 600 s porque cada sondeo cuesta GraphQL) o el plazo (`timeout`; sin edge cuenta como `error`). El calendario de sondeos vive en memoria.
- Subflujos (nodo `flow`): la hija hereda sujeto, carril, proyecto, roles y perfil, corre en el worktree del padre y no cuenta para el índice (flujo, sujeto). Un `$nodo` o un `resumeFrom` se buscan en la hija y luego en sus padres. Su costo queda en su corrida, no se suma al padre; `timeoutSec` y `retry` no aplican al nodo.
- Comandos de una persona (`runs.pause|resume|cancel|interrupt|retryStep|steerStep|forceOutcome`, `projects.pause|resume`): el origen de la llamada va como `by` y queda en los eventos. `force` es solo de `action` y `wait` (decisión #44, nunca un agente). Un proyecto pausado solo deja de lanzar issues; no toca sus corridas ni el carril de mantenimiento.
- Consolidadores: `worst`, `flows.worst` e `items.merge` vienen registrados; uno nuevo (`registerConsolidator`) es síncrono y puro. `items.merge` da a cada ítem un `id` hash de sus `idKeys`: el mismo hallazgo conserva su id entre rondas.
- Nada que falle al cargar, despachar o recuperar una corrida puede cortar a las demás ni el arranque: estaciona solo esa corrida (`docs/design.html#nunca-se-congela`).
- Reintentos y cortes: cada reintento es la misma fila de `step_runs` con `attempt` mayor (el token de fencing). Un corte suma `recoveries` y un error del entorno (login vencido, cuota) suma `deferrals`, sin gastar intento: los intentos gastados son `attempt` − `recoveries` − `deferrals`. Al tercer corte (`MAX_CUTS`) el paso cierra con `error`.
- Arranque: `startCore` llama a `procs.killOrphans()`, `workspaces.recover()` y `flows.recover()` en ese orden, antes de levantar la API. Un agente cortado retoma su sesión (o abre una con el mismo brief) con un `notice` antes de las instrucciones del modo.
- Latido: renueva el lease del paso cada 40 s y aborta su `signal` si ya no es el de su attempt. Un despertar del dispatcher con más de 30 s de hueco (la máquina durmió) extiende los leases propios y llama a `onClockJump` antes de despachar.
- Decisiones (`packages/core/src/decisions/`): `openDecision` y `closeDecision` son lo único que escribe la tabla, en la misma tx que cierra el paso o estaciona la corrida. Las que no bloquean (`review_note`, `note`, `question`, `alert`) no tocan ninguna corrida. La Bandeja de la UI solo trae las accionables (`gate`, `question`, `needs_human`, `alert`, `ACTIONABLE_KINDS`): las `review_note` y `note` siguen en la base y se leen en "Notas del agente" de su corrida y en el indicador "n notas para el review" de su PR.
- Estacionar: `gate`, `needs_human` (un paso sin edge para su outcome) y `limit` (`maxCostUsd` o `maxSteps`; el `maxCostUsd` del proyecto manda) dejan la corrida `parked`, sin cupo ni slot pero con su worktree. `resolveGate` la devuelve a la cola de su carril, antes que las nuevas. La corrida fija las versiones al empezar, también la del perfil con sus topes por rol: si la persona los sube, `retry:latest-profile` y `continue:latest-profile` (solo si la corrida fijó un perfil) pasan la corrida a la versión vigente de ese perfil antes de seguir, sin cancelarla; los roles y los flujos no se tocan.
- Tope del agente (`error_max_turns`, `error_max_budget_usd`): con `escalate` en el nodo se reintenta una vez con `escalate.profileRole` y sesión nueva; si no, `error` sin reintento.
- Sujetos y préstamo (`subjects.ts`, decisiones 3 y 9): una sola corrida dueña que escribe por sujeto (y por el PR que publicó su issue), con índices parciales UNIQUE en `runs` que excluyen a las hijas. Con dueña, la nueva queda `queued`; si la dueña es de dev y está `parked`, una de mantenimiento la toma prestada (`run.borrowed`), y el lease del worktree pasa con ella (`handOverWorkspaces`, `fencing_token + 1`) y vuelve en `run.returned`. Tras devolverlo se relee `head_sha`, nunca `remote_sha`: es la punta que espera `--force-with-lease`, y adoptar la del remoto dejaría pisar el commit de otra persona. Una dev nunca pide prestado.
- Cupos por carril: ver "Carriles" en Proyectos, corridas y arranque.
- Tests de flujos: `AgentRuntime` stub (`engine.test.ts`), esperar `run.finished` o `run.parked` en los eventos (nunca sleeps) y `vi.useFakeTimers()` para backoff y plazos.

## Runtimes de agentes

`createRuntimeRegistry` (`agents/runtime.ts`) tiene los runtimes del core. Cada entrada de perfil elige el suyo (`ProfileRole.runtime`: `claude-sdk` por defecto, u `opencode`) y su `model` va en el formato de ese runtime (`sonnet` o `openai/gpt-5.6-luna`). Un nodo `agent` puede pedir otra entrada del perfil con `profileRole` (la de `escalate` la pisa): así se elige runtime y modelo por nodo sin tocar el rol.

- `CORE_RUNTIME` fuerza a todos los agentes a un runtime (los tests y el demo, con `fake`). Sin él, una entrada sin `runtime` corre con `claude-sdk` o, si el core no lo tiene, con el primero registrado; una que pide un runtime que el core no tiene falla al lanzar (`RuntimeUnavailableError`).
- Una sesión se retoma solo en el runtime que la abrió: un `resumeFrom` de otro runtime abre una nueva con handoff. El breaker de un paso es el `runtime:<id>` de su entrada; el resultado dice qué runtime falló (`AgentResult.runtime`).
- `defs.agentOptions` devuelve un `RuntimeOptions` por runtime (`describeRuntimes`, `agents/runtime-options.ts`): modelos, esfuerzos y si está disponible. La UI del perfil elige runtime y después modelo.

## Runtime de opencode

`createOpencodeRuntime` (`packages/core/src/agents/opencode/`) es opencode 2 (`MIN_OPENCODE_VERSION`, probado con 2.3.0; opencode 1 tiene otra API y no sirve). Cada run levanta su propio `opencode serve` (con `procs`, `OPENCODE_PASSWORD` de un uso y el entorno sin credenciales del agente, que es el de sus comandos) y habla con su API `/api/...` por `fetch` (`api.ts`, tipos copiados de `opencode.ai/docs/openapi.json`; sin SDK). La config del run va en `OPENCODE_CONFIG_CONTENT` en formato nativo v2: un agente `clanker` con el prompt del rol y los archivos de contexto en `system`, y `permissions` como reglas en orden. Qué va a dónde está en el TSDoc de `opencode-runtime.ts` y `config.ts`.

- opencode 2 no tiene salida estructurada: el reporte es la entrada de la herramienta `clanker_report`, que registra un plugin de servidor del core (`report-plugin.ts`, JS plano sin imports que se escribe en `<home>/agent-env/opencode/report-plugin/` porque el bundle no lleva archivos sueltos) con el esquema del modo en sus `options`. Un agente que no la llama termina sin reporte y el core lo reintenta como reporte inválido.
- Un effort que el modelo no tiene como variante hace fallar la ejecución entera (`provider.no-route`): el adapter revisa `GET /api/model` y, si no está, corre con la del modelo y deja un aviso. Los modelos de opencode 2 no son los de 1 (`openai/gpt-5.4-mini` ya no existe).
- Nunca `"*"` con `deny`: `clanker_report` cae bajo `*`. Un rol de solo lectura niega cada acción con nombre (`bash` es `shell`, `Task` es `subagent`). Sin los hooks del rol, `plugins: ["-*", "opencode.*", <plugin del reporte>]` apaga los del usuario y deja los de opencode, que incluyen a los proveedores.
- El fin llega por `session.execution.succeeded|failed|interrupted`; los eventos no se reconectan, así que un sondeo de `GET /api/session/{id}` (`outcome`, `time.idle`) lo cubre. Una cuota o un login vencido se corta en el primer `session.retry.scheduled`; `maxTurns` y `maxBudgetUsd` los cuenta el adapter (`session.step.ended` trae costo y tokens por paso) e interrumpe (`POST /interrupt`). Lo que gasta un subagente cuenta.
- Credenciales: las que guardó `opencode auth login` (las `XDG_*` se heredan para encontrarlas); las API keys del entorno nunca llegan. opencode 2 solo lee `AGENTS.md`, no `CLAUDE.md`. La suscripción de Claude no se usa desde opencode.
- Tests: `testing/opencode/fake-opencode.ts` imita los eventos y fallas de opencode 2.3. En vivo (gasta cuota del proveedor; por defecto un modelo gratis de opencode Zen): `CLANKER_LIVE_OPENCODE=1 npx vitest run packages/core/src/agents/opencode/opencode-live.test.ts` (`CLANKER_LIVE_OPENCODE_MODEL=openai/gpt-5.6-luna` cambia el modelo). No graba guiones del fake (`CLANKER_RECORD` es solo de Claude).

## Runtime de Claude

`createClaudeRuntime` (`packages/core/src/agents/claude/`) es el runtime `claude-sdk`: lanza Claude Code con `@anthropic-ai/claude-agent-sdk` (versión fija, súbela a propósito). Las credenciales se piden en cada run (`connections.claudeCredentials`). Login vencido y cuota agotada son errores del entorno: el paso vuelve a pending sin gastar intento y se abre el breaker `runtime:<id>`. Sesiones, caché, costo por turno, transcripts y prefijo compartido están en el TSDoc de `agents.ts`, `claude-runtime.ts` y `pricing.ts` (`docs/design.html#d-agents`).

- El entorno del agente se arma con lista blanca (`agentEnv`): nunca hereda `GH_TOKEN`, `GITHUB_TOKEN`, `LINEAR_*`, `SSH_AUTH_SOCK` ni `ANTHROPIC_*`. Si una variable nueva debe llegar al agente, se agrega ahí y en su test.
- Con `procs`, el proceso de Claude Code va en su propio grupo y queda registrado con su `stepRunId`. Un test que ejercite el lanzamiento inyecta un `query` falso que llama a `options.spawnClaudeCodeProcess` con un `sleep`, nunca a Claude.
- Si el proceso de Claude muere sin `result`, el error del run trae la cola de su stderr (2000 caracteres, `stderr de claude: ...`): el SDK solo dice `exited with code N`. El `outputSchema` va a `--json-schema` sin `$schema`: Claude Code no resuelve el meta-esquema 2020-12 que declara `z.toJSONSchema` y salía con código 1 antes del primer mensaje. `agents/claude/report-schema.test.ts` compila el reporte de cada modo de la plantilla con el Ajv de Claude Code (draft-07, strict): un modo nuevo o un tipo de zod que da keywords de 2020-12 (`prefixItems` de una tupla) falla ahí y no en la primera corrida real.
- Orden del prefijo (`toOptions`): herramientas ordenadas, prompt del rol, `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` y contexto del repo; el brief va en el mensaje. Nada con fecha, cwd ni git status antes del límite, o la caché no se comparte.
- Un modelo sin precio en `model_prices` deja el turno en 0 y un evento `error` con `scope: "agent.usage"`; al cerrar manda el total del runtime. El uso de un `assistant` en streaming no es final (la salida llega recién en el `result`, que además cuenta subagentes y llamadas internas): el runtime emite `usage_remainder` por modelo con lo que el total cuenta de más y el core lo suma al último turno de ese modelo (o a uno nuevo), así los turnos suman el total y el aviso del 2% solo salta por precios. `model_prices` lleva una fila por versión del modelo (`claude-sonnet-5-5` y `claude-sonnet-5` no cuestan igual), y un modelo con precio de prompt largo (haiku 5.5, sobre 100 000 tokens) lo tiene en una segunda fila con `above_prompt_tokens`: cuando Anthropic cambie precios o saque un modelo, una migración nueva con filas nuevas (`valid_from` = ahora para las de alias).
- Topes de gasto: si el `result` es `error_max_budget_usd` pero el agente ya había llamado a `StructuredOutput`, el runtime devuelve esa entrada como `structured` y `agents` la valida: si cumple el esquema el paso sale `success` con un evento `error` de `scope: "agent.budget"`; si no, sigue siendo `error_max_budget_usd`. Al lanzar (no al retomar), un tope menor que escribir 50k tokens de prefijo en la caché (`minUsefulBudgetMicros`) deja el mismo evento: la sesión cortaría antes de responder.
- Grabar (`CLANKER_RECORD=<carpeta>`, `claude/record.ts`): cada run deja `<carpeta>/<issue>/<rol>.r<n>.<modo>.yaml` con el formato del fake (eventos con entrada y salida de cada herramienta, uso por turno con los restos ya sumados, resultado, y el patch del worktree en `patches/`), para commitearlo como fixture. Lo repetido queda como `<modo>02` con `times: 1`. Nada de secretos (patrones y credenciales del run) ni rutas de la máquina (el worktree va relativo, `<home>`, `<clanker-home>`): si grabas algo nuevo, pásalo por `createScrubber`. No graba `run:` (los checks de la receta los corre el core): agrégalo a mano. El reporte de `StructuredOutput` va solo en `result.structured`. Prueba en `packages/testkit/src/record.test.ts`: graba con un `query` falso con la forma real y reproduce con el fake.
- Los tests usan un `query` falso (`options.query`); la CI no llama a Claude. El smoke test real: `CLANKER_LIVE_CLAUDE=1 npx vitest run packages/core/src/agents/claude/claude-live.test.ts` (haiku, gasta cuota).
- Un fake de un SDK o CLI imita también cómo falla el real, comprobado contra él: el Agent SDK lanza `Claude Code returned an error result` después de todo `result` con `is_error`, y un fake que no lanza dejó pasar que ningún estado de error llegaba al `result` del run.

## UI

- `AppData` (`packages/ui/src/app-data.ts`) es lo único que la UI le pide al core, con los tipos de `@clanker/api` (nada de dominio duplicado en la UI); sus errores son promesas rechazadas con un mensaje que se muestra tal cual. `createCoreAppData(client)` es el real y `createMemoryAppData` el de ejemplo.
- En vivo: la UI no aplica eventos a mano ni hace polling. Cada tanda de `events.stream` (`followEvents`, que reconecta desde el último `seq`) sube `revision` y toda `useLiveQuery` relee su fuente; un evento nuevo que mueva lo que se ve va en `LIVE_EVENTS` de `core-app-data.ts`. Una salida en vivo que no debe hacer releer (`recipe.test_output`) se sigue con `useLive().subscribe`.
- Nada de una organización en la UI (`no-brand.test.ts` lo vigila): chips, filtros y tooltips de un PR salen de `CachedPr.signals`, el comando de merge de `merge.command` y el bot de `reviewBot`; `prCaps` decide qué acciones se ofrecen, como el core. Lo que se dibuja de una corrida (grafo, stepper, pestañas del paso) sale de su `flowDef` y del tipo de nodo, nunca de nombres de roles, acciones o nodos.
- No calcules totales en la UI: salen del core (`projects.summary`). Gráficos: solo marcas `bg-viz-*` (tokens `--viz-1..8` de `globals.css`), el color de un rol sale de su lugar entre todos los roles del proyecto (`roleColor`), nunca de su ranking, y todo gráfico tiene su tabla (`ChartCard`).
- Decisiones: un gate o un `needs_human` solo se contestan con sus opciones (`optionLabel`, `optionsOf`). La notificación nativa solo abre la decisión, nunca aprueba (decisión 46). El core no reabre y resolver reencola la corrida al instante, así que `useDecisionResolver` manda la respuesta recién a los `UNDO_MS` para que Z deshaga.
- Lo que cambia algo del proyecto lleva un toast "Deshacer" (`undoable`, `lib/undoable.ts`). Ajustes guarda con `projects.update` solo las secciones que cambiaron (`patchOf`); un campo vacío es "el default" (del core o del flujo) y los `flowParams` que no administra (el `repo` de un flujo) se conservan. Los `flowParams` son compartidos entre flujos (params por flujo sigue pendiente): la ayuda de cada parámetro dice qué otros flujos lo leen.
- El uso del plan de Claude sale de la última `connections.testClaude`, que gasta una llamada: `useClaudePlan` la repite cada 10 min solo con Claude conectado y nunca la pide al pintar.
- Learnings (`components/learnings/`, `hooks/use-learnings-view.ts`, `hooks/use-learning-triage.ts`, `lib/learnings.ts`): vista propia `module: "learnings"` (⇧⌘A, G luego A), no una sección de la bandeja: triar los 144 importados pide filtros, casillas y acciones en lote, y las decisiones de la bandeja son una por una y estacionan corridas. Pestañas por estado (Por revisar, Aprobados, Rechazados, Retirados) con filtros de alcance, rol y origen (los roles salen de los datos, no de una lista) y búsqueda (`/`); los contadores respetan los filtros y el badge del sidebar cuenta los `proposed` de todos. Lista a la izquierda (J/K, X marca, ⌘A marca todo lo que se ve, Mayús+clic marca un rango) y el learning a la vista a la derecha; A aprueba y R rechaza (en Aprobados, retira: queda `archived`) los marcados o, sin marcados, el que está a la vista, y E edita texto, roles y tags (`learnings.update`: el alcance, proyecto o repo, no se edita). Aprobar es de la app (`origin: "ui"`), y como el core no tiene "volver a `proposed`", `useLearningTriage` aplica la decisión recién a los `UNDO_MS` (Z o el aviso la deshacen, un lote entero); mientras tanto la lista la muestra ya en su pestaña nueva (`withPending`) y, si el core la rechaza, vuelve a su lugar con el error. Editar emite `learning.updated` (con quién lo pidió), que la vista sigue en vivo. `learnings.list` trae todos los estados y la UI filtra y cuenta; el nombre de un alcance de repo sale de `AppData.repos()`, que solo se pide si algún learning lo tiene.
- Tests de componente: `// @vitest-environment jsdom` al inicio del archivo y `@testing-library/react`. jsdom no mide el DOM: xyflow monta con un `ResizeObserver` y un `DOMMatrixReadOnly` de mentira y solo dibuja los nodos (los edges esperan a medir los handles; pruébalos en `lib/run-graph.test.ts`). Una lista virtualizada (`@tanstack/react-virtual`) lee el alto del contenedor de `clientHeight` y el de cada fila de `offsetHeight`: defínelos en el prototipo (ver `step-transcript.test.tsx`).
- En un E2E abre un menú contextual con `dispatchEvent("contextmenu")`, no con click derecho: Radix selecciona el ítem bajo el puntero al soltar el botón, y un menú cerca del borde de la ventana se corre justo debajo.
- Usa un componente de shadcn antes de escribir uno propio. Agrégalo desde `packages/ui` (`npx shadcn@latest add <componente>`) o pídelo al MCP de shadcn (`.mcp.json`).
- El CLI genera `import { cn } from "cn"`: cámbialo a `import { cn } from "@/lib/utils"` (el lint falla si queda el otro).
- Colores solo desde los tokens de `packages/ui/src/styles/globals.css` (claro y oscuro). Nada de colores sueltos.
- Toda acción tiene atajo de teclado y está en la paleta ⌘K.
- Filas y tarjetas tienen menú contextual.
- Cada tag lleva un tooltip que explica qué significa.
- Los estados vacíos dicen qué hacer, no solo que no hay nada.
- Antes de dar una vista por lista: screenshot en claro y en oscuro, y míralos. No los commitees (`screenshots/` está ignorado).
