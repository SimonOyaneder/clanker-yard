# Clanker Yard

Orquestador de agentes de código sobre issues y PRs. Monorepo con npm workspaces (Node 24, TypeScript estricto).

Este archivo lo lee cada agente y ya pasa los 120 KB: agrega reglas, desvíos y trampas que el código no dice, en pocas líneas. La referencia de un módulo (args, outcomes y output de una acción, qué hace cada función) va en su TSDoc, no aquí; si hace falta, una línea con dónde vive.

## El diseño es la fuente de verdad

Vive en `docs/design.html` (260 KB, no lo leas entero ni lo edites). Cita siempre la sección por su id, por ejemplo `docs/design.html#d-data`. Para leer una sección en texto plano:

```
python3 scripts/design-section.py          # lista los ids
python3 scripts/design-section.py d-data   # imprime una sección
```

Ids más usados: `devx` (dev setup), `d-data` (schema, API, monorepo), `stack`, `ui`, `d-ui`, `d-flows`, `d-agents`. Si el diseño no cuadra con la realidad, haz lo más simple que respete su intención y deja el desvío escrito en el PR.

Desvíos ya conocidos: `agentEnv` (`d-agents`) incluye `USER` además de `PATH`, `HOME` y `LANG`, y en modo suscripción nunca hereda `ANTHROPIC_*`, `CLAUDE_CODE_OAUTH_TOKEN` ni `CLAUDE_CODE_USE_*` (ver `docs/claude-subscription.md`).

## Instalar, correr, probar

```
nvm use                # Node 24, fijado en .nvmrc
npm ci
npm run typecheck      # tsc --noEmit en cada workspace
npm run lint           # eslint desde la raíz, más `npm run depcheck`
npm test               # vitest desde la raíz (un proyecto por app y paquete)
```

Los tres deben pasar antes de dar algo por listo; la CI corre los mismos en cada PR y en `main`. Un test de un paquete va junto a su código como `src/**/*.test.ts`.

La suite completa corre en paralelo y bajo carga: un `vi.waitFor` sobre un core, una corrida o un proceso real lleva `timeout` explícito (el default de 1 s no alcanza), un test no cuenta lo que hay en el `tmpdir()` compartido (usa su propia carpeta) y no espera un solo evento de `fs.watch` justo después de empezar a observar (en macOS se pierde; reescribe hasta verlo).

El core es un proceso largo: un callback de timer o de evento (`setInterval`, `.on(...)`) no lanza, porque un throw ahí tumba el core. Atrapa el error y conviértelo en un resultado (abortar un `AbortSignal`, emitir un evento).

UI sola: `npm run dev -w packages/ui` abre la UI en el navegador (puerto 8890) con datos de ejemplo en memoria.

Para ver la app con datos y corridas que avanzan: `CLANKER_HOME=$(mktemp -d) npm run demo-core -w @clanker/testkit` levanta un core de demo (runtime fake, plantilla `juguete`, un proyecto local con 3 issues, tres repos con receta ausente, válida e inválida, cada corrida dura unos 7 s) y publica su `core.json`; con el mismo `CLANKER_HOME`, `npm run dev -w apps/desktop` se conecta a él en vez de lanzar el core real. Con `DEMO_INBOX=1` suma el proyecto `Bandeja de prueba` (el E2E lo pide), que arranca una corrida por tipo de decisión (flujos `juguete-gate`, `juguete-trabado`, `juguete-tope` y `juguete-nota`, guardados directo en `defs`) y una alerta suelta sin opciones (`openDecision`; `demo-control.json` con `closeAlert: true` la cierra como lo haría un breaker), para ver y probar la bandeja de decisiones. Ciérralo con Ctrl+C. Sus conexiones nunca salen a internet: GitHub es el simulador (acepta el PAT `github_pat_demo`), Linear el falso del core y Claude un `query` falso (`createFakeClaude`). Para ver una conexión vencida sin esperar, escribe `<CLANKER_HOME>/demo-control.json` con `{ "clockDays": 40, "claude": "login_expired" }` (el reloj de las conexiones parte del 2026-11-15 y se adelanta esos días; `claude` es `ready`, `login_expired` o `quota_exhausted`). Con `DEMO_SCENARIO=lanes` siembra además el proyecto de la vista de Operación (`packages/testkit/src/lanes-scenario.ts`): sus corridas se escriben directo en la base, porque el fake no se queda quieto el rato que dura una captura, y en ese escenario no va la bandeja de prueba.

App de escritorio: `npm run dev -w apps/desktop` construye el core y abre Electron (con `CLANKER_HOME=$(mktemp -d)` delante no toca tus datos; sin él usa los reales). Para capturar la ventana de verdad, arráncala con `npx electron-vite dev -- --remote-debugging-port=9333` desde `apps/desktop` y habla CDP con `http://127.0.0.1:9333/json` (`Page.captureScreenshot`, `Runtime.evaluate`, `Emulation.setEmulatedMedia` para claro y oscuro). Ciérrala con `Browser.close` por CDP, no con `pkill`: hay otras Electron corriendo.

E2E: `npm run e2e` (desde la raíz) construye el core y la app, lanza el core de demo del testkit (runtime fake, plantilla `juguete`, proyecto `demo`) sobre un `CLANKER_HOME` temporal y abre la app con Playwright `_electron` (`apps/desktop/e2e`, `*.e2e.ts`, fuera de `npm test`). Crea un proyecto desde el diálogo, corre `juguete` hasta que la corrida queda `lista`, conecta GitHub (PAT contra el simulador), Linear (el test recoge el link del IPC `host:open-external` y lo aprueba) y Claude, prueba una receta con su log en vivo y deja los screenshots claro y oscuro de cada vista en `apps/desktop/out/screens` (no se commitean). El core real no conoce el runtime fake, por eso el E2E lanza el core de demo y la app se conecta a él por `core.json`. Necesita el binario de Electron: tras `npm ci` corre `node node_modules/electron/install.js` (los install scripts no corren). En Linux va bajo xvfb (`xvfb-run --auto-servernum npm run e2e`, `--no-sandbox` lo pone el test); la CI lo hace en el job `e2e` y sube `out/screens` como artefacto `e2e-screens`. El tema se cambia con `page.emulateMedia`, porque Playwright fija `prefers-color-scheme` en la ventana y `nativeTheme` no lo mueve. Cada archivo `*.e2e.ts` elige el escenario del core de demo con `test.use({ scenario })` (`e2e/harness.ts`; `default` o `lanes`) y cada escenario corre en su worker. ⌘K y los demás atajos del menú nativo no los dispara Playwright: abre la paleta con el botón del buscador.

## Paquetes y dependencias permitidas

```
apps/desktop      Electron (main, preload, ventana)
apps/cli          comandos `clanker` sobre la API
packages/api      contrato oRPC, esquemas zod, cliente
packages/core     Store, Flows, Agents, Workspaces, Scheduler, servidor
packages/ui       React + shadcn, vistas
packages/testkit  runtime fake, fixtures, repos git temporales
```

- `api` no depende de nadie del repo. `core` → `api`. `ui` → `api`. `desktop` → `ui`, `api`. `cli` → `api`. `testkit` → `core`, `api`, solo como `devDependency`.
- Prohibido: `ui` → `core`, `desktop` → `core` (el core se empaqueta y se lanza, no se importa), `core` → `electron`.
- Cada paquete exporta solo su `src/index.ts` (más `@clanker/api/node`, que la UI no puede usar). Nada de imports a archivos internos de otro paquete.
- `npm run depcheck` lo hace cumplir con dependency-cruiser (`.dependency-cruiser.mjs`) y corre dentro de `npm run lint`, así que la CI lo ejecuta en cada PR. Si agregas un paquete o cambias una dependencia permitida, edita esa config y el test `scripts/depcheck.test.ts`. Que `testkit` use `core` y `api` solo como `devDependency` lo verifica ese test, no dependency-cruiser.

## Base de datos

El schema vive en `packages/core/src/store/schema.ts`. Tras cambiarlo: `npm run db:generate -w @clanker/core` deja una carpeta nueva en `packages/core/migrations/` (se commitea). Para triggers u otro SQL que drizzle-kit no modela: `npx drizzle-kit generate --custom --name <x>` desde `packages/core` y escribe el SQL a mano. No edites una migración ya mergeada.

Lo que ya define `@clanker/api` (ids con prefijo, `EventType`, `Origin`, `SubjectRef`, `Event`, `EventFilter`) se importa de ahí, no se redeclara en el core: en el schema con `.$type<...>()`, que no cambia la migración.

Los ids de prueba salen de `newId("run")` o son ULIDs válidos (`run_00000000000000000000000001`): `run_1` pasa el tipo, pero el store rechaza el evento.

Si una tx emite el inicio de algo (`lease.acquired`) y el paso que sigue falla, el camino de error emite el cierre (`lease.released`): la línea de tiempo no puede quedar con un lease que nunca se soltó.

## Secretos y conexiones

Los tokens (PAT de GitHub, OAuth de Linear...) viven detrás de la interfaz `Secrets` del core (`get`, `set`, `delete` por ref); la base guarda solo la ref (`connections.secret_ref`) y los eventos nunca llevan el valor. `createKeychainSecrets` usa el Keychain de macOS con el comando `security` (funciona con `ELECTRON_RUN_AS_NODE`, donde no hay `safeStorage`); `createFileSecrets` cifra un archivo con una llave junto a él, para tests y Linux. `createConnections(store, secrets)` es lo único que escribe `connections` y emite `connection.changed`; el token lo lee solo el core con `connections.token()`.

- GitHub: `connections.setPat(token)` valida el fine-grained PAT (usuario, repos visibles y una lectura de prueba por permiso: contents, pull requests, issues, checks, commit statuses; este último para los estados de CI que no son check runs, como merge-queue) y lo conecta con la cuenta del token; `connections.githubClient(cuenta)` es el único cliente Octokit, pone el token en cada request y registra la cuota en `sync_cursors` (`rate:github:<cuenta>:<recurso>`), emitiendo `sync.rate_limited` si GitHub corta. Detrás va `GitHubTokenSource` (`pat` hoy, `app` con `refresh` después). `connections.list()` marca `expiresSoon` a 7 días del vencimiento y `expired` después. Los tests levantan un GitHub falso local con respuestas de `packages/core/src/github/fixtures/` (`fake-github.ts`).
- GitHub App (fase 2b): `docs/github-app.md` y `docs/github-app-manifest.json` son la guía y el manifiesto para registrarla e instalarla (paso manual de Simón, no hecho aún). El core lee su `client_id` al arrancar con `readCoreConfig(dataDir)` (`process/config.ts`): `<dataDir>/config.json` (`{ "githubApp": { "clientId" }, "linear": { "clientId" } }`) y las variables `CLANKER_GITHUB_APP_CLIENT_ID` y `CLANKER_LINEAR_CLIENT_ID`, que ganan; `runCore` pasa el resultado a `createConnections` (`githubApp` y `linear`) y `startDeviceFlow` (CLA-100) usa el primero. Un `config.json` inválido tumba el arranque con la ruta y el motivo. Los permisos del manifiesto deben ser los mismos de `PERMISSIONS` en `github/pat.ts` (un test lo comprueba).
- Linear: `connections.linearAuth(origin)` (`packages/core/src/linear/`) hace OAuth con PKCE contra un loopback: levanta un servidor en `127.0.0.1:48721` (`LINEAR_REDIRECT_PORT`), devuelve el `url` de `linear.app/oauth/authorize` (el core no abre el navegador; la API lo expone como `connections.linearAuth`) y, al aprobar, cambia el código por tokens, toma el `urlKey` del workspace como cuenta y conecta (`connection.changed`). Un `linearAuth` nuevo cancela el pendiente y vence a los 5 min. Access token de 24 h y refresh token de 30 días que rota: el access token, el refresh token y el vencimiento viajan juntos como un JSON en un solo secreto (`connection:linear:<workspace>`), y la base solo guarda la ref; `expiresAt` de la conexión es el del refresh token (30 días desde el último refresh). `connections.token("linear", cuenta)` refresca solo si al access token le quedan menos de 5 min, con un único refresh en vuelo por cuenta; si Linear rechaza el refresh (400, 401 o 403) la conexión queda `revoked` (en rojo) con `connection.changed` y hay que reconectar; un fallo de red o un 5xx solo lanza. `connect` no acepta Linear. `connections.disconnect` (también en la API) borra el secreto y la cuenta; no revoca el token en Linear. Los tests usan un Linear falso local (`linear/fake-linear.ts`) con PKCE y rotación del refresh token.
- Paso manual pendiente (Simón): no hay OAuth app de Linear registrada ni `client_id`. Se crea en https://linear.app/settings/api/applications/new (Settings, API, OAuth applications, New): nombre sin la palabra "Linear" (p. ej. "Clanker Yard"), tu nombre como developer, redirect URI exacto `http://127.0.0.1:48721/oauth/linear/callback` (Linear compara la URI completa, por eso el puerto es fijo; si lo cambias, pásalo en `redirectPort`) y distribución privada (solo tu workspace). No se usa client secret: el flujo es PKCE. Copia el `client_id` y ponlo en `<dataDir>/config.json` como `{ "linear": { "clientId": "..." } }` (en macOS, `~/Library/Application Support/Clanker Yard/config.json`; la app lanzada desde el Dock no hereda variables de la terminal) o en `CLANKER_LINEAR_CLIENT_ID`, y reinicia el core: `runCore` lo lee con `readCoreConfig` y lo pasa a `createConnections`. Sin `client_id`, `linearAuth` falla con un `BAD_REQUEST` que dice dónde configurarlo y la vista Conexiones lo muestra bajo el botón de Linear. Los pasos y la URI no se probaron contra Linear real.
- Claude: la cuenta `claude` es su modo, `subscription` o `api-key`. La suscripción es una fila sin secreto (`secret_ref` vacío): el login lo lee el `claude` instalado, nunca la app. La API key vive en `Secrets` (`connection:claude:api-key`) y, mientras exista, es lo que usan los runs; para volver a la suscripción se desconecta `claude/api-key`. `connections.testClaude({ mode? })` (`probeClaude`, `packages/core/src/agents/claude/probe.ts`) comprueba de menor a mayor costo el `claude` del `PATH` y su versión (mínima `MIN_CLAUDE_VERSION`), `claude auth status --json` (login y plan, sin gastar cuota) y una llamada mínima (haiku, un turno, sin herramientas) de la que salen el uso (las barras de 5 h y 7 días del `rate_limit_event`) y si la cuota o el login están en regla. Responde un `ClaudeStatus` (`state`: `ready`, `not_installed`, `outdated`, `login_required`, `login_expired`, `key_rejected`, `quota_exhausted`, `error`) y, si es concluyente, deja la cuenta `active` (`ready`, `quota_exhausted`), `expired` (login) o `revoked` (key rechazada); `not_installed`, `outdated` y `error` no tocan la base. `connections.setClaudeApiKey(key)` la prueba antes de guardarla. `connections.claudeCredentials()` es lo que el runtime `claude-sdk` pide en cada run.
- Nunca guardes aquí el token OAuth de la suscripción de Claude (`docs/claude-subscription.md`).
- Los tests no tocan el Keychain real: usan `createFileSecrets` en un directorio temporal, o un `.keychain-db` temporal creado con `security create-keychain` y pasado en `keychain` (ver `secrets.test.ts`).

## App de escritorio

`apps/desktop` es solo el host (`docs/design.html#remoto`, `#d-data`): `main` lanza y vigila el core, `preload` le pasa la conexión a la ventana y `renderer` monta `@clanker/ui` con un `Host` armado sobre el preload.

- `createCoreSupervisor` (`src/main/core-supervisor.ts`) llama a `ensureCore` al arrancar y comprueba cada 2 s con `connectToCore`. Estados: `starting`, `live` (con `port`, `token` y `bootId`) y `down` con el motivo. A la ventana le llega `windowCoreState` (`core-proxy.ts`), sin token ni puerto: nada del main le pasa el token al renderer. No relanza solo: el botón Reintentar de `StatusBanner` llama a `start()`. Si otro proceso (la CLI) levanta el core, pasa a `live` sin más.
- Cerrar la ventana o la app no detiene el core. El menú Archivo → "Salir y detener agentes" pide `system.shutdown({ drain: true })` y sale.
- El core es el bundle `packages/core/dist/main.js` (desktop no lo importa). Electron guarda sus cachés y preferencias en `<datos>/desktop`, así que con `CLANKER_HOME` un arranque de prueba no toca nada del usuario.
- Todo lo de Electron que la UI necesita (menú, notificaciones, editor, tema, estado del core) pasa por `Host` (`packages/ui/src/host.ts`); `Host.core` solo existe donde el host aloja el core. El main valida cada payload que llega por IPC.
- La ventana monta `createCoreAppData(createClient({ url: "clanker-core://core/rpc", ... }))`. `clanker-core://` es un esquema que registra el main (`src/main/core-proxy.ts`): reenvía cada llamada al core vivo poniendo su token y su puerto (el renderer nunca ve el token, y sobrevive a que el core se relance en otro puerto) y contesta el preflight de CORS, que el core no sirve. Los streams de eventos pasan por partes. Con el core caído responde 503 y la UI lo muestra como un error de lectura.
- `packages/ui/src/styles/globals.css` se exporta como `@clanker/ui/styles.css` (el único archivo interno que otro paquete puede importar) y trae `@source` para que Tailwind compile las clases de la UI desde `apps/desktop`. El Vite del desktop apunta el alias `@` al `src` de la UI.
- Los tests de `core-supervisor` lanzan el core real sobre un `CLANKER_HOME` temporal con su propio bundle (`node scripts/build.ts <outfile>` de `packages/core`), sin pisar `dist/`.

## Trackers

`Tracker` (`packages/core/src/tracker/tracker.ts`) es lo único que el scheduler y los flujos ven de un tracker; las formas normalizadas (`Issue`, `IssueRef`, `StatusCategory`, `IssueFilter`, `TrackerCapabilities`) son de `@clanker/api`. `createLocalTracker(store)` es el adapter `local`: sus issues, comentarios y relaciones viven en `local_issues`, `local_comments` y `local_relations`, y `rev` es el cursor de `changesSince`. `createIssues(store)` es el caché `issues`: `sync(tracker, { projectId, project })` vuelca `listIssues` (la primera vez) o `changesSince` (después, con el cursor en `sync_cursors`, clave `issues:<tracker>:<proyecto>`) y emite `issue.synced`; `issues.list`, `issues.get` y `issues.createLocal` de la API leen y escriben ahí. `Tracker.viewer()` es la persona de la conexión (la que asigna `claim` y cuyas issues son propias para la cola). Un adapter nuevo implementa `Tracker` y declara sus `capabilities`.

`createLinearTracker({ connections })` (`packages/core/src/linear/tracker.ts`, registrado en `startCore` junto a `local`) es el adapter `linear`: GraphQL directo con `fetch` (`linear/graphql.ts`, sin `@linear/sdk`: una query por operación y el costo de cada una a la vista) y el token de `connections.token("linear", cuenta)`; sin `account` usa la única cuenta de Linear conectada. Los proyectos son proyectos de Linear y `Issue.project` es el id del proyecto de la issue (`NO_PROJECT` si no tiene). Estados: por el tipo del estado de Linear (`triage` y `backlog` son `backlog`, `unstarted` `todo`, `started` `in_progress`, o `in_review` si el nombre dice "review", `completed` `done`, `canceled` y `duplicate` `canceled`); la opción `statusMapping(proyecto)` pisa estados por nombre y `setStatus` escoge el estado del equipo de esa categoría (menor posición; triage y duplicate solo si no hay otro). `claim` asigna al `viewer` del token y pasa a `in_progress`, y relee: si Linear aceptó el `issueUpdate` y no lo aplicó (ENG-9084) lanza `LinearApiError` diciendo qué quedó sin hacer (la asignación puede haber quedado). `setStatus` también relee. `comment` antepone `[clanker]`. `changesSince` usa `updatedAt` de las issues como cursor (un ISO; no ve comentarios, que no mueven la issue) y devuelve el epoch si el workspace está vacío. Una issue con más de 25 labels o relaciones es un error (no se trunca). El estado por proyecto (`statusMapping`) todavía no se persiste ni tiene UI. Los tests (`linear/tracker.test.ts`) usan `startFakeLinear`, cuyo `/graphql` ejecuta con `graphql-js` el subconjunto del esquema real de Linear en `linear/fixtures/schema.graphql` (un campo o argumento que Linear no tiene no valida) sobre los datos de `FakeWorkspace` (`linear/fake-workspace.ts`); si el adapter pide algo más, se agrega al esquema copiándolo del real (`linear/linear` en GitHub, `packages/sdk/src/schema.graphql`). `fixtures/states.clanker-yard.json` son los estados que Linear devolvió para el equipo CLA.

## Packs

Un pack (`docs/design.html#packs`) es lo propio de una org (señales de PR, bot de review, reglas de CI, estrategia de merge, convenciones, flujos y roles) como JSON declarativo; el core no tiene `if` por organización. El esquema es `Pack` en `packages/api/src/pack.ts` (con `packJsonSchema` y `PackSettings`, que tomado de `{}` es la configuración neutra de un repo sin pack).

- Una carpeta de pack tiene `pack.json` y los `.json` de sus flujos (`FlowDef`) y roles (`Role`) que ese archivo lista, con rutas relativas a la carpeta. El id de un flujo debe ser el nombre de su archivo; el slug de un rol es el nombre de su archivo.
- `createPacks({ defs }).load(dir)` valida todo antes de escribir y guarda el pack (kind `pack`) y sus flujos y roles como defs con scope `pack` y source `pack:<id>@<versión>`. Lo que una versión anterior traía y la nueva no se archiva. Dos packs no pueden traer el mismo slug. Un error es un `PackLoadError` con el archivo y la ruta de cada problema.
- `packs.packFor({ githubOrg, trackerWorkspace, projectId })` lee los packs guardados y devuelve el primero (por id) cuyo `activate` cubre el alcance, o los defaults neutros con `id: null`. Para un repo se pasa su org de GitHub; para un proyecto, su id y el workspace de su tracker.
- `defs.resolve` no conoce el alcance: un flujo o rol de un pack es visible para cualquier repo. Quien lance un flujo debe consultar `packFor` antes de ofrecer lo del pack.
- `conventions.context` (`{ <rol o *>: ["skill:commit", "rule:git-safety", "repo:AGENTS.md"] }`) lo resuelve Agents con las fuentes del rol, para el pack de la org del repo del workspace (ver Contexto de los roles).
- `packs/acme/` es el pack de ejemplo: lo específico de Acme (riesgo del bot de review, `/review`, merge-queue y `/merge`, convenciones de PR) como datos, y nada de eso entra al core. Lo que declara se comporta como Clanker Control y `clanker-loop watch`, y `packages/core/src/packs/acme.test.ts` lo fija con copias literales de ese código: si cambias una regex o un texto del pack, ese test dice qué comportamiento de hoy rompes. Desvíos del diseño: los roles son `.json` (el cargador lo exige), `silentReviewBody` exige la palabra (el vigilante no trata `!!!` ni `.` como un LGTM) y `flows` lista solo `techlead-acme` (el de council llega con su plantilla). Sus roles `review-lore` y `triage` pisan a los de la plantilla (precedencia `pack` sobre `builtin`) y deben mantener sus modos, outcomes y esquemas: el test lo verifica.

## Contexto de los roles

`createContextResolver({ defs, packs, remoteOf, userDir })` (`packages/core/src/agents/context.ts`, lo crea `createAgents`, que le debe el kind `context`) convierte `Role.context` en `{ native, references, warnings }` en cada lanzamiento y cada `resume`, leyendo siempre el archivo original (nunca una copia): una skill o regla editada vale desde el siguiente lanzamiento. `docs/design.html#contexto`.

- `native`: va tal cual (varias se juntan; `skills: "all"` gana). Cada `skill:<n>` que existe (`skills/<n>/SKILL.md` o `commands/<n>.md` en el `~/.claude` o `CLAUDE_CONFIG_DIR` y en el `.claude` del worktree, según las `sources` del rol) se suma a `native.skills` (un rol sin fuente `native` recibe `user` y `project`): el runtime se las pide a Claude por nombre, sin copiarlas.
- `repo` (`<worktree>/<ruta>`), `file` (absoluta, `~/` o relativa al worktree) y `rule:<n>` (`.claude/rules/<n>.md` del worktree, y si no, el del usuario) pasan a `references`. Un archivo ya incluido (misma ruta) no se repite.
- `pack` es un paquete de contexto: una def de kind `context` (`ContextPackage` de `@clanker/api`: `refs`, las mismas `skill:`, `rule:`, `repo:` y `file:`; resuelve con `defs.resolve("context", id, { repoId })`). La biblioteca guarda referencias, nunca contenido. Nada de la app crea esas defs todavía (ni la UI, ni el MCP, ni los packs): quien quiera uno lo guarda con `defs.save`.
- Después de las fuentes del rol van las de `conventions.context` del pack de la org del repo del workspace (`packs.packFor({ githubOrg })`, la org sale de `repos.remote`): las de `*` y las del slug del rol. El motor pasa `repoId` desde `workspaces.held`.
- Un archivo, paquete o skill que falta o no se puede leer no detiene al agente: queda en `warnings` y Agents emite un evento `error` con `scope: "agent.context"` (con `runId` y `stepRunId`) por cada uno, antes de lanzar. Hay uno por rol y fuente en cada run, así que los roles de la plantilla (`lore`, `commits`, `bug-rubric`, `test-rules`) avisan mientras nadie guarde esos paquetes.
- Los hooks del usuario siguen apagados salvo `Role.hooks`.

## Git remoto (push y fetch)

Solo el core habla con el remoto, y el token nunca llega al entorno de git ni de los hooks del repo. `createGitRemote({ askpass, connections })` (`packages/core/src/git/`) corre `git -c credential.helper= push|fetch <url explícita>` con `GIT_TERMINAL_PROMPT=0` y `GIT_ASKPASS` apuntando a un script que `createAskpass` escribe en un directorio 0700: el script cambia un ticket (60 s, el usuario y la contraseña una vez cada uno, solo para el origen de la URL del remoto) por esos valores por un socket unix del core. Ese git hereda del core solo una lista blanca del entorno (`INHERITED_ENV` en `remote.ts`) y el fetch corre sin hooks: los hooks y el config del repo los controla el agente. Se usa a través de `workspaces.push(lease)` (`--force-with-lease` contra `remote_sha`; outcomes `ok`, `lease-rejected` sin reintento y `unauthorized`, que deja la conexión `revoked` con `connections.markRevoked`) y `workspaces.fetch(repo)`; `RepoConfig.remote` trae la URL y la cuenta. Los tests (`packages/testkit/src/git-remote.test.ts`) levantan un servidor git HTTP local con Basic auth sobre un bare temporal: nunca GitHub ni tokens reales.

## Estado de un PR

Un solo módulo lee un PR de GitHub y lo entrega normalizado: `createPrs({ connections, packs }).get({ account, repo, number })` (`packages/core/src/github/`, API `prs.get`) devuelve el `PrState` de `@clanker/api` (`docs/design.html#d-ops`). `pr-query.ts` es la query GraphQL de detalle (`PrDetail`, más `PrThreads` y `PrContexts` para completar las páginas de threads y de checks por el id del PR; los conteos no pueden quedar a medias) y `pr-state.ts` el builder puro `buildPrState(node, { pack, viewer })`.

- Genérico: nada de Acme en el código. El bot de review (`reviewBot`), quién es humano (`actors.ignore`), los checks que cuentan (`ciRules`), el prefijo del council (`conventions.councilPrefix`) y las señales (`signals`, `risk` en Acme) salen del pack de la org del repo (`packs.packFor({ githubOrg })`). Sin pack: sin bot, sin señales y CI = checks requeridos de la branch protection (`isRequired(pullRequestNumber:)` de cada check; sin requeridos es `none`). Con `ciRules` cuentan todos los checks menos `ignoreChecks`; `knownFlaky` marca los flaky conocidos.
- Un LGTM del bot solo vale con la regla del pack (estado, `bodyMatch` y, con `sameSha`, el commit del head); uno de un commit anterior es `bot.state: "none"`. Una review del bot que no cumple la regla es `findings`. `silentReviewBody` se evalúa sin distinguir mayúsculas; `bodyMatch` e `ignore`, sí.
- Cada thread es de quien escribe su primer comentario: council (prefijo) antes que bot antes que humano; lo que escribió la cuenta conectada (`viewer`) sin prefijo no es un humano esperando. `councilOpen` son los `fullDatabaseId` de esos comentarios.
- Lo que los waits necesitan viene en el `PrState`: `bot.at` (ISO de la review del bot), `bot.findings` (solo con `state: "findings"`: sus threads sin resolver, con `id` (el `fullDatabaseId` de su primer comentario), `path`, `line` y texto, o su review misma si no dejó threads) y `ci.flaky` (los de `ci.failing` que el pack declara en `ciRules.knownFlaky`; siguen contando como rojo).
- Waits (`pr-waits.ts`; `prWaits(prs)` da `botReview`, `ci` y `merged` para `flows.registerWait`): cada wait decide con una función pura sobre el `PrState`, y `probe` la aplica al de `prs.get` y `match` al de un evento `{ type, pr: PrRef, state: PrState }` (lo que Watch da a `flows.signal`, ver `signalPr`). `pr.botReview { pr, after }` solo cuenta una review del bot posterior a `after` (el `requestedAt` de `review.requestBot` o de `pr.reply` con `rerequestBot`; `lgtm`, o `findings` con `items` para triage: `{ id, kind: "bot", path?, line?, text }`, con el `fullDatabaseId` del primer comentario del thread como `id`, lo que espera `pr.reply`); `pr.ci { pr }` es `ok` con CI verde o `fail` con `failures` (`{ id: "ci:<check>", kind: "ci", text, flaky? }`) apenas un check que cuenta falla; `pr.merged { pr }` es `merged` (con `sha`) o `closed`. `startCore` los registra.
- `talk` es lo que el vigilante cuenta como comentario de un humano: una review que pide cambios o con texto que no es un LGTM solo (un texto de solo espacios es texto; una descartada con texto sigue contando) y cada comentario de la conversación; lo que lleva el prefijo del council no cuenta, sea de quien sea. `threads.unresolved` es todo thread abierto, de quien sea: los "hilos sin resolver" de Control, y lo que lee `reviewStatusOf(pr)` (`@clanker/api`), el estado de review (`changes`, `pending`, `approved`, `none`) de `reviewStatus` de Control.
- Un PR sin checks (o con solo merge-queue) da `ci.state: "none"`, y Control y el vigilante lo daban por listo (`every` sobre vacío): `ciGreen` de la estrategia de merge acepta `none` además de `green`, y `parity.test.ts` lo fija con `ciReady`.
- Paridad con Clanker Control: `packages/core/test/legacy/` tiene las funciones de Control copiadas tal cual (`riskOf`, `botReview`, `reviewerStates`, `mapCI`, `mergeStatus` y `reviewStatus` de `pr-status.ts`), nodos `GqlPR` inventados (`fixtures.ts`) y `parity.test.ts`, que compara riesgo, bot, revisores, CI, estado de review y `merge` (`ready`, `blockers`, cola) con el pack de ejemplo. Una diferencia sin `divergence` (con su valor y motivo) falla, y una `divergence` que ya no difiere también. Hoy hay doce casos con `divergence`, todos a propósito: bot aprobado sin LGTM en el body o con LGTM de un commit anterior (reglas de `wait-review`), review del bot descartada, cuentas de sistema que ignora el pack (las del vigilante), merge-queue dentro del rollup, un thread de council escrito por otra cuenta (`merge`: el vigilante lo descarta, Control lo contaba como humano) y un repo sin merge-queue (`merge`: `/merge` no pone nada en cola). `clanker-loop wait-review` acepta además `github-actions[bot]` como bot; ni Control ni el vigilante lo hacen, y el pack sigue a Control (meterlo en `reviewBot.logins` cambiaría `bot`, `threads` y `reviewers` de todos los PRs). Si el wait lo necesita, va como un campo aparte. Si Control cambia una función, se vuelve a copiar. Los eventos de merge del vigilante se prueban con goldens: `watch.jq` (copia de su WATCH_JQ) corre sobre `watch-scenarios.ts` y deja `watch-goldens.json` (`node packages/core/test/legacy/generate-watch-goldens.ts`, necesita `jq`; el test falla si los escenarios cambian sin regenerar). `watch-parity.test.ts` los compara con `mergeFactsOf` y el dedupe de `watch_marks` simulado; tres `divergence`: `offer` sobre otra base (el vigilante solo exige la base para `auto`), `auto` sobre un PR en conflicto (el vigilante no mira `mergeable`) y un PR ya listo en el primer run (el vigilante lo ofrece, el pack siembra). Los eventos que no son de merge (talk, conflicto, council) siguen sin goldens.
- Pendiente para la fase 2: `combinedBase` del `PrState` (stacks) y los eventos de Watch `pr.overlap` y la notificación de `pr.mergeFailed`. El resto de `PrState` (`approvers`, `merge`, `hold`) ya está: ver Estrategia de merge.
- Las queries se validaron contra el esquema público (`docs.github.com/public/fpt/schema.docs.graphql`) con graphql-js; el GitHub falso no valida la query, así que si la cambias, repite esa validación. El falso (`fake-pr-graphql.ts`, `prGraphql`, que usa también el simulador del testkit) responde como el real: GraphQL siempre contesta 200, un recurso inexistente trae `data` nulo y un error `NOT_FOUND`, y la cuota primaria agotada es un 200 con `errors` y `x-ratelimit-remaining: 0` (el cliente emite `sync.rate_limited`, ver `rateLimitReset` en `client.ts`).

## Estrategia de merge

`ready`, `offer` y `auto` (`docs/design.html#d-ops`, "Tres niveles de merge") son las listas de `mergeStrategy` del pack, evaluadas sobre el `PrState` por `evaluateMerge` (`github/merge-strategy.ts`, puro) y entregadas en `PrState.merge` (`ready`, `blockers`, `queue`, `offer`, `auto`, `via`), `approvers` y `hold`. Las condiciones y el texto de cada blocker (los de `mergeStatus` de Control) son del core; qué condiciones forman cada nivel, del pack. Sin estrategia, o donde no aplica, rige `GITHUB_BUTTON`: `via: "button"`, ready sin cola, offer sin `auto`: el core ofrece una decisión y la persona mergea con el botón de GitHub.

- `hold` es del core (`pull_requests.hold`, `PrCache.setHold`, que relee el PR): apaga `offer` y `auto` aunque la lista del pack no cite `notHold`, y `auto` siempre implica `offer`. Todavía no hay endpoint ni UI que lo marque.
- `appliesWhen` lo resuelve `MergeScope` (`github/merge-scope.ts`, que `createPrs` consulta al leer el PR): primero el override del repo (`repos.merge_strategy` `on`/`off`, `Repos.setMergeStrategy`, decisión #33) y si no, si el check aparece en los últimos 20 commits de la branch por defecto (`DefaultBranchChecks`, un GraphQL validado contra el esquema público; se recuerda una semana si lo vio y un día si no, en `sync_cursors`). Que merge-queue se vea ahí es una suposición sobre cómo publica merge-queue sus statuses: si un repo la rompe, el override lo corrige.
- La cola (`merge.queue`) sale de un comentario de la cuenta conectada que sea solo el `command` (`/merge`, comparado literal), y `failed` si el check `queueCheck` quedó en FAILURE o ERROR. Un `/merge` viejo sigue contando tras un push nuevo (como Control y el vigilante): un PR cuyo merge-queue falló y se arregló no vuelve a ofrecerse hasta que alguien lo resuelva a mano.
- Watch emite `pr.mergeReady` (`level: "offer" | "auto"`) y `pr.mergeFailed` una vez por head (`mergeFactsOf`, en `watch_marks`); la primera lectura de un PR solo siembra. Con la cola de merge-queue en curso (`queue: "queued"`) Watch pide check-runs y status cada 30 s, porque merge-queue mueve su status sin tocar el PR.
- `startMergeReactions` (`watch/merge-reactions.ts`) escucha esos eventos y solo actúa sobre PRs `owned`, y nunca confía en el evento: relee el PR y reevalúa. `auto` con `onAuto: "act"` comenta el `command` (git-safety: solo el nivel `auto` lo hace sin preguntar; eso lo fija el pack de ejemplo, no el core). `offer` con `onOffer: "gate"` abre una decisión `question` sin corrida (nada espera; `merge_offers` guarda el head ofrecido) y reemplaza la anterior si el head cambió. Aprobarla (opción `Comentar <command>`, resuelta desde la app: un agente puede usar el CLI o el MCP, así que solo `ui` vale) relee el PR y comenta solo si sigue en el mismo head y `offer`; si no, deja una nota. Sin comando la decisión no hace nada: el merge es del botón de GitHub.
- Los tests sobre `startGitHubSim` (`packages/testkit/src/merge-strategy.test.ts`) usan el `pack.json` real de Acme con otro alcance; `sim.defaultBranchCheck("merge-queue")` pone merge-queue en la branch por defecto del simulador.


## Watch (polling de PRs)

`createWatch({ store, connections, repos, cache, remote, waitKeys, events, errors, trackers? })` (`packages/core/src/watch/`, `docs/design.html#d-ops`, "CodeHost: polling con ETags") detecta qué PRs cambiaron sin gastar cuota y se enciende con `startCore({ watch: true })` (lo que hace `runCore`; por defecto apagado, para que un test con el GitHub simulado no reciba requests que no pidió). Es código puro: sin slot ni agente. `tick()` es un despertar (cada 2 s con `start()`); los tests lo llaman a mano con un `now` inyectado.

- Qué mira: las filas abiertas de `pull_requests` (las que abrió `pr.publish` y las que descubre la búsqueda `is:pr author:@me is:open` cada 5 min, solo de repos registrados con remoto) más los PRs con un wait esperando (`Engine.waitKeys` + `prOfWaitKey`). Por cuenta, en serie.
- Por PR: `GET pulls/{n}` con ETag cada 30 s (caliente: un wait lo espera o se pusheó hace menos de 15 min), 2 min (en review, fuera de draft) o 5 min (frío); `check-runs` y `status` del head con ETag cada 30 s mientras el CI esté `pending` (o `none` en un PR caliente). Un 304 no gasta cuota (el cliente registra la cuota igual). El detalle GraphQL (`prCache.refresh`) solo se pide si algún ETag cambió, si nunca se leyó o si `mergeable` sigue `unknown` (relee a los 10 s, 3 veces). `git ls-remote --heads` por repo cada 60 s (`GitRemote.lsRemote`, sin cuota) guarda las puntas en `sync_cursors` (`refs:<repo>`) y adelanta la visita de un PR cuyo head se movió. La reconciliación de 10 min es el sondeo de los waits, no un barrido de Watch.
- Los ETags van en `sync_cursors` (`etag:github:<cuenta>:<ruta>`) y se guardan solo después de leer el detalle: un fallo a medias no pierde el cambio. Al cerrarse o mergearse un PR se borran los de su head.
- Cuota (`quota.ts`, `throttleOf`, lee `rate:github:<cuenta>:<recurso>` con `rate_limit`): bajo 25% de REST o GraphQL los intervalos se duplican; bajo 10% solo se visitan los PRs con waits (y no hay búsqueda); sin cuota nada hasta el reset. Las requests de un cliente de GitHub salen en serie (`createGitHubClient`); el segundo entre escrituras lo guardan las acciones que escriben en ráfaga (`pr-feedback.ts`).
- El caché: `createPrCache({ store, repos, prs, onChange })` (`pr-cache.ts`) guarda en `pull_requests.detail` el último `PrState` y llama a `onChange` solo si cambió; el core lo cablea a `signalPr(flows.signal, ref, state)` (un evento por tipo de wait). API: `prs.list` (caché, sin tocar GitHub) y `prs.refresh` (como `prs.get` pero cacheando y avisando). Un PR que el caché no conoce se lee igual y no entra.
- Un error de una visita no tumba el despertar: se anota con un evento `error` (`scope: "watch.<cuenta> <repo>#<n>"`, `createErrorReporter` en `report.ts`, que también usan los eventos y los triggers) la primera vez que cambia su mensaje; un 401 deja la conexión `revoked`.
- Eventos (`watch/events.ts`, `createPrEvents({ store, repos, workspaces, errors })`): `PrCache.onChange(ref, state, row)` llama a `events.observe` (junto con `signalPr` para los waits; `startCore` lo comparte con el caché de la API vía `onPrChange`) y cada despertar termina con `events.flush(at)`. Un evento se emite insertando su marca en `watch_marks(pr_id, kind, key)` (índice único; `marks.ts`, `emitOnce`, la usan también las acciones): `pr.botReview` (`sha:reviewId`), `pr.ci` (`sha:estado`, solo verde o rojo), `pr.conflict` (sha de la punta), `pr.comment` (un id por thread de council abierto; el payload trae solo los nuevos en `threadIds`), `pr.human` (`autor@fecha` de cada `talk`), `pr.mergeReady` y `pr.mergeFailed` (el sha del head, ver Estrategia de merge), `pr.merged` y `pr.base_rewritten` (`viejo>nuevo`: la punta nueva no desciende de la vieja; se hace `workspaces.fetch` y `merge-base --is-ancestor`, y si la punta vieja no está en el repo local no se emite). El evento es del PR (`subject`), con el proyecto de la corrida que lo abrió y `origin: "watch"`; el payload lleva `repo` y `number`.
- Siembra y debounce: la marca `head` guarda la última punta evaluada. Un PR sin marca `head` es la primera vez que se ve: se siembran todas las claves de lo que ya tiene sin emitir nada. Una punta nueva en un PR abierto espera 20 s (`DEBOUNCE_MS`, desde `headChangedAt`) y solo se evalúa la final; `flush` retoma lo que quedó esperando leyendo `pull_requests.detail`, así que un reinicio no pierde nada. Un PR cerrado no espera.
- Triggers (`watch/triggers.ts`, `startTriggers`): escucha los eventos `pr.comment`, `pr.conflict`, `pr.merged` y `pr.base_rewritten` del store y arranca (`flows.start`) los flujos cuyo `trigger.type` calza, sobre el PR como sujeto, con el carril del flujo (los `pr.*` van a mantenimiento) y el perfil del proyecto que abrió el PR. Solo PRs `owned`; con threads de council no hay rebase por conflicto. Un flujo recibe de sus `params` lo que declare entre `pr` (`PrRef`), `repo` (id del repo registrado), `branch` (la branch del PR), los campos del payload (`sha`, `base`, `from`, `to`, `threadIds`, `files`...) y los `flowParams` del proyecto que abrió el PR (el payload los pisa); el `filter` del trigger compara cada clave con el payload. Un flujo que no arranca deja un evento `error`. Como escucha el store, sirve también a `stack.restack`, que anota `pr.conflict` con la misma clave que Watch.
- Cambios de Linear (`watch/tracker-changes.ts`, `trackers` de Watch): cada 60 s por proyecto activo, `Issues.hasChanges` (`changesSince` desde el cursor sin moverlo) y, si hay algo, `scheduler.tick()` (que trae las issues y lanza). `startCore` no lo cablea con `scheduler: false`.
- Sin implementar todavía: `pr.overlap` (hace falta la lista de archivos de cada PR).
- `updated_at` y las reviews: ver `docs/watch-updated-at.md`.

## Proceso del core

El core corre como proceso propio (`packages/core/src/main.ts`, bundle en `packages/core/dist/main.js` con `npm run build -w @clanker/core`; las migraciones quedan en `packages/core/migrations`, al lado). `--data-dir` (o `CLANKER_HOME`) dice dónde; con `CLANKER_HOME` el core no toca el Keychain (secretos en archivo bajo `secrets/`) y los logs van a `<CLANKER_HOME>/logs`. Lo lanza `ensureCore({ dataDir, logDir, entry, origin })` de `@clanker/api/node`, que también tiene `clankerDirs()` (rutas por SO) y `readCoreJson`/`connectToCore`.

- Orden de arranque: `core.lock` (`wx`; un pid muerto se recupera) → abrir y migrar la base → abrir el puerto → `boot_id` en `meta` → `core.json` (0600). Quien lee `core.json` ya puede llamar a la API.
- Apagado (SIGTERM, SIGINT o `system.shutdown({ drain })`, `Core.close({ drain })` en `core.ts` y `runCore` en `process/core.ts`): `scheduler.close()` va primero (el cierre no abre corridas nuevas); `flows.close({ graceMs })` deja de despachar, interrumpe a los agentes de una vez y, con `drain`, da hasta 60 s a las acciones (sin él, o con una señal, las aborta ya); después `procs.stop(10 s)` manda SIGTERM al grupo de cada proceso del core y SIGKILL a los que sigan; cada paso cortado vuelve a `pending` con `deferrals` + 1 (ni intento ni `recoveries`: un apagado limpio no cuenta para el loop de crash) y su sesión marcada para retomarse, como tras un corte; recién entonces se cierra el servidor, `wal_checkpoint(TRUNCATE)`, la base y se borran `core.json` y `core.lock`. El servidor sigue contestando durante el drenaje y `core.json` sigue ahí: otro cliente que llega ve un core vivo que se apaga, no un directorio sin dueño. Una segunda señal mata el proceso sin más (el próximo arranque lo recupera). Un crash deja `core.json`, `core.lock` y las filas de `procs`, y el próximo arranque los recupera.
- `procs` (`createProcs({ store, bootId })`, `packages/core/src/procs/`; `startCore` acepta uno ya creado en `procs` para que el runtime Claude lo comparta): los procesos que lanza el core van en su propio grupo (`detached: true`) y se registran con `track` (los comandos de `workspaces.exec` y de `repos.testRecipe`, el `git` de red de `git/remote.ts` y el proceso de Claude Code, que `createClaudeRuntime({ procs })` lanza con `spawnClaudeCodeProcess` anotando el `stepRunId` de `RunSpec`; el `git` local corto y los `execFile` de Keychain y del probe de Claude no se registran). Todo proceso nuevo y de vida larga que lance el core pasa por `track`. Un proceso solo se mata si su pid sigue con la hora de inicio que el SO le dio (un pid reusado no se toca): `killOrphans()` al arrancar mata el grupo de las filas de otro `boot_id`, y `stop()` solo toca lo que este core lanzó. `workspaces.recover()` renueva y vuelve a latir los worktrees de corridas vivas (mismo token), suelta los de corridas terminadas y deja sin lease los que estaban `creating`; una corrida que ya tiene su worktree lo puede volver a tomar (se re-ejecuta su `workspace.acquire`). Si algo se recuperó, `startCore` emite `core.recovered` con `{ steps, leases, orphans }`.
- `ensureCore` (`@clanker/api/node`) revisa el `apiMajor` del core que contesta tras lanzar: si no es el que lanzó este proceso (otra llamada ganó la carrera) y tiene otro `apiMajor`, lo apaga con drain y lanza el suyo; si se repite, lanza un error. Espera el drenaje hasta 90 s.
- Los tests de proceso (`packages/core/src/process/process.test.ts`) construyen el bundle y lanzan el core real sobre un `CLANKER_HOME` temporal. A mano: `CLANKER_HOME=$(mktemp -d) node packages/core/dist/main.js`.

## Receta del repo y checks

`Recipe` (`packages/api/src/recipe.ts`) es el esquema de `.clanker/recipe.json` (`docs/design.html#d-ops`) y el body de las defs `recipe`. Las variables son solo `{{slot}}`, `{{slot+N}}`, `{{worktree}}`, `{{branch}}`, `{{files}}` y `{{envKeys}}`: una desconocida o una expresión se rechaza al leer la receta, con la ruta del campo. `renderTemplate(t, vars, { shell })` las sustituye; con `shell` escapa `worktree`, `branch` y cada archivo para `sh -c`.

`createRecipes({ store, defs, workspaces, artifacts, fake? })` (`packages/core/src/recipe/`) registra el kind `recipe` en las defs y da `read(dir)` (`undefined` si el repo no tiene receta; inválida lanza `DefValidationError`) y `checkAction`, la acción `recipe.check` que se registra en Flows (`args: { ws, scope: "changed" | "all", slot? }`, `ws` es el output de `workspace.acquire`).

- Corre `checks` en orden y se corta en el primer rojo. Cada comando va con el `wrap` de prefijo y el `env` de la receta; con scope `changed`, `{{files}}` son los archivos que cambió la issue (commits, cambios sin commit y nuevos, sin borrados) y un comando que lo usa se salta si no hay ninguno. Si la receta define `slots` y no se pasa `slot`, el paso toma uno del pool del carril de su corrida (`runs.lane`; sin esa fila es `PermanentActionError`) y lo suelta al terminar, también si falla o se cancela; con `slot` explícito quien llama lo prepara y no se usan los pools. Sin `slots` en la receta, una que usa `{{slot}}` sin `slot` lanza. Ver "Slots por carril". Una receta inválida y un `{{slot}}` sin slot son `PermanentActionError`: no se reintentan.
- Outcomes `ok` y `fail`. Con `afterRebase: true` corre antes los `afterRebase` de la receta (ver "Rebasear un PR abierto"). Output: `failures` (`[check] exit N` y el extracto del check rojo, lo que va como `failures` al brief del dev), `specsChanged` (archivos de pruebas cambiados, para `when: "$checks.specsChanged"`) y `checks` (nombre, `ok`, `exitCode` y el hash del artefacto `log_excerpt`). Cada check deja su extracto como artefacto del paso (`role: check:<nombre>`).
- `workspaces.exec(ws, comando, { runId, stepId, env, signal })` valida el token y corre `sh -c` en el worktree: la salida completa se agrega a `<logDir>/runs/<runId>/<stepId>.log` (`logDir` de `createWorkspaces`, por defecto `<dataDir>/logs`) y `extract` trae las últimas 60 líneas, sin colores. Un exit distinto de 0 es un resultado. El comando hereda solo `PATH`, `HOME`, `USER`, `LANG`, `TMPDIR` y `SHELL` (nunca `GH_TOKEN` ni `LINEAR_*`); abortar el `signal` mata su grupo de procesos.
- Con el runtime fake, pasa `fake: runtime` a `createRecipes`: `recipe.check` no corre nada y consume `run.<check>` del guion de la última sesión de agente de la corrida (`nextRecipeResult`).
- Se prueba en `packages/testkit/src/recipe.test.ts` (repos git reales).

## Slots por carril

`createSlots({ store })` (`packages/core/src/slots/`, tabla `slots`, `docs/design.html#d-ops`) da los slots de entorno de un repo, compartidos por todos los proyectos que lo usan. `recipe.slots` fija los pools: `dev` es 1..N y `maintenance` N+1..N+M (`reserved_for`); una fila se crea al primer uso y, si la receta cambia los tamaños, los slots libres se reparten de nuevo. `tryAcquire({ repoId, lane, runId, pools, workspaceId? })` toma uno libre del pool del carril (`undefined` si está lleno: un pool lleno nunca presta ni espera al otro) y prefiere el que ya preparó ese worktree; `acquire` espera con `signal`. Mismo lease que un worktree: 2 min, latido cada ttl/3 y `fencing_token + 1` en cada toma; el `lost` del lease aborta si se perdió. `release` es noop con un token viejo.

- Preparación: `startSetup` deja el slot `dirty` y `finishSetup({ workspaceId, setupHash, env })` lo limpia y anota qué worktree lo preparó, el hash de `setup.slotKey` y el `env` ya renderizado. `recipe.check` corre `setup.guard` y luego `setup.slot` solo si el slot está `dirty`, lo preparó otro worktree o cambió el hash de `slotKey` (nombre y contenido de cada archivo; uno que falta también cuenta). Un guard que no calza (o que sale con exit distinto de 0) lanza `PermanentActionError` antes de tocar nada, sin ensuciar el slot. Un `setup.slot` rojo da outcome `fail` con `[setup.slot] <comando> exit N` y su extracto en `failures`, y deja el slot `dirty` (el próximo paso repite el setup). Con el runtime `fake` se toma el slot pero no se corre ningún setup.
- Dueño: el slot es del paso, no de la corrida: se suelta al terminar el paso, así una corrida estacionada nunca conserva uno. `slots.recover()` (en `startCore`, antes de reabrir pasos) suelta todos los que tienen dueño, porque el core que los tenía murió; `onClockJump` también extiende los de Slots. Emite `lease.acquired`, `lease.released` y `lease.expired` con `payload.resource = "slot"` e `id` `<repo>#<idx>`.
- `setup.worktree`: `createWorkspaces({ worktreeSetup })` (el core pasa `readRecipe(dir)?.setup?.worktree`) lo corre al crear el worktree, fuera del lock del repo y antes de dejarlo `leased`, con el log en `<logDir>/runs/<runId>/setup.worktree.log` y sin `env` ni `wrap` de la receta (no hay slot todavía). Si falla, `acquire` lanza `WorktreeSetupError`, borra el worktree (y la branch si la creó ese acquire) y el siguiente acquire vuelve a empezar.
- Falta: `commits.apply` sigue recibiendo `slot` de quien lo llama (corre los tests en un worktree de verify, cuyo `slotKey` no es el del worktree de la corrida) y los agentes todavía no reciben un slot.

## Circuit breakers

`createBreakers({ store, runtime, probe, label? })` (`packages/core/src/breakers/`, `docs/design.html#d-ops` y `#nunca-se-congela`) pausa solo lo que depende de una causa de entorno y se cierra solo cuando la causa se va; nunca congela el loop por algo local. Ámbitos (`repoScope`, `runtimeScope`, `GITHUB_SCOPE`): `repo:<id>`, `runtime:<id>` y `github`. API: `open(scope)` (por qué está abierto, o `undefined`), `trip({ scope, cause, reason, resetsAt? })` (idempotente), `list()`, `start()` y `close()`. Al abrir emite `breaker.opened` (`scope`, `cause`, `reason`, `retryAt`) y deja una decisión `alert` pendiente en la bandeja; al cerrar emite `breaker.closed` y la alerta queda `superseded`. El estado (con su backoff) vive en `meta` (`breakers`): un corte lo retoma en `start()`.

- Causas (`BreakerCause`): `quota_exhausted` (resultado de un run, con `resetsAt` la primera prueba es a esa hora), `login_expired`, `connection_lost` (`connection.changed` con `expired` o `revoked` de `github`, o de `claude` si el runtime es `claude-sdk`; Linear no abre ninguno: sus fallos ya son por proyecto en el Scheduler), `rate_limited` (`sync.rate_limited` de GitHub, con su `resetAt`) y `environment` (una acción lanza `EnvironmentError(scope, mensaje)`; hoy solo `recipe.check` cuando falla un `requires` de la receta, antes de correr ningún check: un Postgres caído no es un check rojo).
- Backoff de la prueba: 1, 5, 15 y 30 min y después cada 30. Reconectar (`connection.changed` `active` o `disconnected` de ese proveedor) prueba ya, sin esperar; los eventos que emite la propia prueba (`testClaude` reescribe la conexión) no la vuelven a disparar. `probe(scope)` devuelve `undefined` si la causa se fue o por qué sigue; `environmentProbe` (`probes.ts`) es la de `startCore`: `github` hace `GET /user` con cada cuenta conectada (un 401 la deja `revoked`), `runtime:claude-sdk` usa `connections.testClaude` y `repo:<id>` corre los `requires` de su receta en el checkout.
- En el motor (`EngineDeps.environment = { breakers, runtime }`): el dispatcher no despacha un paso mientras algún ámbito suyo esté abierto (sigue `pending`, sin gastar intento) y lo retoma al cerrarse, sin esperar un `not_before`. Ámbitos de un paso (`scopesOf`): un agente depende de `runtime:<id>` y del `repo:<id>` de su workspace; una acción con `needsRepoEnv` (`recipe.check`), del `repo:<id>`; una con `effects: "remote"` (publica), de `github`. Waits, gates y subflujos no dependen de ninguno: Watch y los agentes siguen con `github` abierto. Un login vencido o cuota agotada del agente y un `EnvironmentError` abren su breaker y devuelven el paso a pending (`deferrals` + 1); una excepción de un paso cuyo ámbito ya está abierto (el 401 de GitHub que acaba de abrir `github`) también se cuenta como espera y no gasta `retry`. Sin `environment` (tests del motor) se mantiene el `not_before` fijo de 60 s o el `resetsAt`.
- El Scheduler no lanza issues de un `repo:<id>` ni del runtime en pausa (queda `waiting` con el motivo) y hace un tick al emitirse `breaker.closed`. `github` no frena el lanzamiento, solo a quien publica.
- Un run real con login vencido llama a `connections.markClaudeLoginLost` (suscripción `expired`, API key `revoked`, `connection.changed`): `startCore` lo conecta al evento `breaker.opened` con causa `login_expired`. La cuota agotada no toca la cuenta (sigue `active`, como en `testClaude`).
- Tests: `breakers/breakers.test.ts` (backoff, reset, eventos, corte), `breakers/probes.test.ts`, `flows/breakers.test.ts` (un repo caído no frena a otro, github en rojo deja correr agentes y checks, cuota) y `packages/testkit/src/breakers.test.ts` (login vencido de punta a punta con el runtime fake y el Claude falso).

## Proyectos, corridas y arranque

`startCore({ store, dataDir, connections, runtimes, env, ... })` (`packages/core/src/core.ts`) arma el core sobre un store abierto: Defs, Agents con el runtime que elige `CORE_RUNTIME` entre `runtimes` (default `claude-sdk`; uno que no está registrado hace fallar el arranque), Workspaces, Flows con todas sus acciones y waits (`workspace.acquire|attach|release|syncBase|rebase`, `recipe.check`, `commits.apply`, `pr.publish`, `pr.pushFixups`, `pr.pushLease`, `pr.comment|reply|resolveThread`, `review.requestBot` y `pr.botReview|ci|merged`), las plantillas builtin (`juguete` y el equipo clanker-loop con `techlead-clasico` y `pr-feedback`), los packs instalados, `flows.recover()` (reabre lo que el corte dejó a medias y despacha los pasos pending del core anterior, ver "Motor de flujos"; el dispatcher no arranca solo, así que una acción o un wait nuevo se registra antes de esa llamada) y la API. `runCore` solo le agrega el lock, `core.json` y las señales, y registra `claude-sdk`: el fake vive en el testkit, así que un test levanta el core en proceso con `startCore` (`packages/testkit/src/core.test.ts`); con el binario real `CORE_RUNTIME=fake` todavía no es posible.

- Cableado de `startCore` para publicar un PR (`docs/design.html#fases`, criterio de la fase 1): `createAskpass` y `createGitRemote` van a Workspaces (se cierra el askpass en `close`), `createRepos(store, { remote: githubRemote(connections, gitUrl) })` llena `RepoConfig.remote`, `createRecipes` recibe los slots y, si el runtime trae `nextRecipeResult` (el fake), lo usa en lugar de correr los checks, y `prWaits` y las acciones de PR usan el mismo `createPrs` y `packs`. Opciones: `gitUrl(repo)` (por defecto `https://github.com/<repo>.git`; un test la apunta a un bare local o a `startGitHttpServer`), `linearEndpoint` (el GraphQL de Linear; un test lo apunta a `startFakeLinear`) y `packsDir` (por defecto `<dataDir>/packs`: cada subcarpeta es un pack y `packs.loadAll` las carga después de registrar todo; un pack roto deja un evento `error` con `scope: "packs.load"` y no tumba el arranque).
- Al terminar una corrida (`run.finished`) el core suelta los worktrees que aún tiene (`workspaces.releaseHeldBy`): `@done`, `@failed` y cancelar no pasan por `workspace.release`, y sin esto el latido del lease seguiría renovándolo. La hija de un subflujo no tiene worktree propio: no suelta nada.
- Brief de los pasos agent: el motor llama a `briefFor` (`createStepBriefs`, `agents/step-brief.ts`, sobre `createBriefs`) y el agente recibe `.clanker-run/` (`issue.md` de la issue del sujeto leída del tracker, `diff.patch`, `hunks.json` y `diff-round.patch`). `diff-round.patch` es lo que cambió desde la última vez que ese mismo nodo miró el worktree: el snapshot de cada paso queda como artefacto de la corrida (ref `snapshot/<nodo>/<visita>/<intento>`) y el paso siguiente del nodo parte del más reciente. Todavía no se escriben `reports/` (los reportes de rondas anteriores): una sesión que se retoma reusa su fila y solo conserva el último reporte, así que habría que sacarlos de los outputs de los pasos, que no traen el `summary`. Los flujos ya pasan lo previo por el payload del brief (`previous: $self`, `plan`...).
- Una issue reclamada queda `in_progress` mientras dure su corrida y al terminar: sale de la cola (ver Cola) y no vuelve. El paso a `in_review` o `done` al mergear es de Watch (fase 2); una corrida fallida o cancelada tampoco devuelve la issue a `todo`.

- `projects` (`createProjects(store, defs)`, API `projects.list|get|create|update`): `default_flow_id` y `default_profile_id` guardan el slug de la def. Con tracker `local`, `tracker_ref` es el id del proyecto (así se llama el proyecto del tracker local, ver `issues.createLocal`, que exige un proyecto local existente); el `ProjectBinding` de `issues.sync` sale de (`tracker`, `tracker_ref`). Además guarda `repos` (tabla `project_repos`: orden y labels de cada uno), `queue_filter`, `stack_on` (`ready`, `ci_green` por defecto o `any_open`: cuándo una issue se apila sobre el PR de su bloqueante, ver Cola), `conventions` (la forma de las del pack; pisan a las del pack) y `max_cost_usd` (`null` es sin tope; hoy solo se guarda, nadie lo aplica). Un cambio de `status` emite `project.paused|resumed|archived`. `runs.project_id` e `issues.project_id` siguen sin FK.
- `repos` (`createRepos(store)`, API `repos.list|add|detect|testRecipe`): `repos.add` registra la raíz de un checkout (nombre, branch por defecto y remoto `owner/name` de GitHub salen de git; `workspaces/inspect.ts`); `createRepos(store).add` sigue siendo el insert directo para código y tests. `repos.detect(carpeta)` lista los repos de la carpeta (ella misma, o sus subcarpetas directas) con su receta `found`, `missing` o `invalid` (con el mensaje con la ruta del campo); no registra nada. `repos.testRecipe` (`recipe/recipe-test.ts`) corre `requires`, `setup.worktree`, `setup.guard` y `setup.slot` en un worktree detached desechable (con el `wrap` y el `env` de la receta) y emite `recipe.test_started`, `recipe.test_output` (`{ repoId, phase, text }`, agrupada cada 250 ms) y `recipe.test_finished`. Corre `setup.worktree`, `setup.guard` y `setup.slot` en ese orden, con un slot libre del pool de mantenimiento si la receta define `slots` (con el pool lleno falla sin esperar; sin `slots`, una receta que usa `{{slot}}` es un error de la receta). Al terminar suelta el slot y lo deja sin worktree que lo haya preparado, así el próximo uso corre `setup.slot`. `RepoConfig.remote` sale de la columna `repos.remote` (`owner/name`) con `githubRemote` (`github/remote-config.ts`): la URL `https://github.com/<repo>.git` y la cuenta de GitHub conectada (la de la org del repo si hay varias); sin cuenta conectada el repo no tiene remoto y `pr.publish` lo dice.
- Cola (`projects.queue({ id })`, `scheduler/`): `tickDev(input)` (`scheduler/queue.ts`) es la función pura (`docs/design.html#d-ops`, "Scheduler: la cola") que recibe el caché de issues entero, las corridas raíz del carril dev (`QueueRun`) y los PRs abiertos del sistema de las issues bloqueantes (`QueuePrFact`) y devuelve las `QueueEntry` con su `state` (`ready` con `base` y `dependsOn`, `waiting`, `blocked`) y su `reason`. Elegible: estado en `queueFilter.status` (default `todo`), `queueFilter.labels`, sin `excludeLabels` (default `no-clanker`), sin dueño o de `tracker.viewer()`, sin sub-issues abiertas (los hijos salen del caché por `parent`, de cualquier proyecto) y sin ninguna corrida dev raíz sobre ella, viva o terminada (por eso una issue terminada no vuelve). Orden: prioridad (0 al final), milestone (con fecha primero, luego sin fecha, luego sin milestone), la que bloquea a más, estimate menor y creación (el id es un ULID). La tabla de bloqueantes está en `judge`: done o canceled no bloquean; un PR abierto del mismo repo que cumple `stackOn` del proyecto (`ready`, `ci_green` por defecto, `any_open`) es la base (`stacked`; dos PRs en cadenas distintas dan `combined`, que el core todavía no crea: `workspace.combineBase` es de CLA-84); uno de otro repo deja la base por defecto y `dependsOn` con `repo#n`; un bloqueante con corrida viva es `waiting`; cualquier otro caso es `blocked` con el motivo. Si el bloqueante tiene un PR que no cumple `stackOn`, espera mientras su corrida viva y bloquea cuando terminó. Con `relations` o `subIssues` en `false` en las `capabilities` del tracker no se calculan bloqueos ni hijos. El orden de salida es ready, waiting y blocked, cada grupo en su orden. `createProjectQueue(...)` (`scheduler/project-queue.ts`) arma esa entrada: caché, `runs`, `pull_requests` (owned y open) y `tracker.viewer()`; solo con `stackOn: "ci_green"` mira cada PR para saber si sigue abierto y su CI (el `detail` que dejó Watch y, si no hay, `prs.get`), y un error de lectura queda en el `reason` en vez de fallar. Desvíos del diseño: se clasifican todas las elegibles (sin el corte en 15) y la cola no aplica `conflictsWithRunning`, los breakers ni `parallel`: eso es del lanzamiento (Scheduler, abajo). Una issue saltada con `projects.skipIssue` (`skipped` de `TickDevInput`, tabla `issue_skips`) sale `blocked` con ese motivo. La UI de Proyecto muestra "En cola" desde `projects.queue`.
- `runs.start({ projectId, issueId, flow?, params? })` (`projects/start-run.ts`) reclama la issue con `Tracker.claim` (adapters `local` y `linear`; un tracker sin adapter es `BAD_REQUEST`), la resincroniza al caché, emite `issue.claimed` y lanza el flujo (el `defaultFlowId` del proyecto si no se pide otro) sobre ella; vuelve sin esperar y el progreso se sigue con `events.stream` (`run.finished`) y `runs.get`. Si el flujo no arranca después de reclamar, la issue queda reclamada (reclamar es idempotente). Params: si el flujo declara `repo` y `base`, salen del repo del proyecto que calza con los labels de la issue (si ninguno, el primero) y de su branch por defecto; los pisan `flowParams` del proyecto (solo con su flujo por defecto) y luego `params`. Los rechazos del motor (`RunStartError`) llegan como `BAD_REQUEST`.
- Scheduler (`createScheduler(...)`, `scheduler/scheduler.ts`, `docs/design.html#d-ops` y `#nunca-se-congela`; `startCore` lo arma y lo arranca con `scheduler.start()`, y `StartCoreOptions.scheduler: false` lo deja apagado para los tests que lanzan a mano): `tick()` corre al bootear, al terminar o estacionarse una corrida (`run.finished`, `run.parked`), al resolverse una decisión, con `issue.synced`, `issue.queued`, `pr.merged` y cambios del proyecto (`project.created|updated|resumed`), con `system.setLanes` y cada 5 min (`SCHEDULER_TICK_MS`). Los ticks no se solapan (un disparo durante uno pide otro al terminar; los `issue.synced` del propio tick no) y nunca lanzan: lo que falla queda en un evento `error` (`scope: "scheduler.tick"`, una vez por mensaje). Primero `flows.wake()` (admite lo que espera cupo, el mantenimiento primero, y las reencoladas antes que las nuevas) y después, por cada proyecto `active`, trae del tracker lo que cambió (`issues.sync`: Watch solo mira PRs, así que nadie más lo hace; si falla, ese proyecto no lanza hasta el próximo tick) y recorre las `ready` de `projects.queue` en orden mientras `hasRoom` (`flows/lanes.ts`: tope global del carril dev y `parallel` del proyecto) lo permita. No lanza una issue `ready` si: es relacionada (`blocks` o `related`, en cualquier sentido) de otra con corrida dev viva, también estacionada (una bloqueada que la cola ya aprobó apilar sobre el PR de su bloqueante no entra aquí); `repo:<id>` o `runtime:<id>` están en pausa según `breakers` (`Breakers.open(scope)`, ver Circuit breakers; `startCore` pasa los reales y `breaker.closed` dispara un tick); su base es `combined` (`workspace.combineBase` es CLA-84); o `runs.start` falla (claim perdido con su relectura en el adapter, flujo que falta). Una apilada pasa `params.base` con la branch del PR padre. Cada issue saltada queda con su motivo: `issue.skipped` `{ issueId, reason }` (solo cuando el motivo cambia) y `scheduler.queue` (lo que sirve `projects.queue`) la muestra `waiting` con ese motivo. `projects.skipIssue({ id, issueId, skipped })` la saca de la cola (tabla `issue_skips`; `false` emite `issue.queued`); `projects.setParallel` es `projects.update({ parallel })`.
- Carriles (`flows/lanes.ts`, `scheduler/lanes.ts`): `createLaneSettings(store)` guarda en `meta` (`lanes`) la capacidad de la máquina (`system.setLanes({ dev?, maintenance? })`, `system.lanes` la lee con el uso): mantenimiento 2 y dev 4 por defecto, y rige al instante porque el motor la lee en cada admisión (`createFlows({ laneCapacity })`; sin ella no hay topes, como en los tests del motor). Una corrida raíz ocupa un cupo mientras está `running`, `waiting` o `paused`; `parked` y `queued` no, y las hijas de un subflujo usan el de su raíz. Mantenimiento nunca usa ni espera el cupo de dev. Sin cupo, una corrida nueva queda `queued` y una estacionada cuya decisión se resolvió sigue `parked` sin decisión abierta (conserva su sujeto, igual que con un préstamo) hasta que `promoteQueued` (cada `wake`) la devuelve a `running` con `run.requeued`; ahí van primero las del carril de mantenimiento y, dentro de cada carril, las más antiguas. Bajar un tope nunca interrumpe lo que ya corre. Falta: `dependsOn` de otro repo no llega a `pr.publish` desde la cola. Los breakers (sección Circuit breakers) pausan los pasos en el dispatcher; la admisión de una corrida `queued` de mantenimiento no los consulta, porque aún no tiene workspace y su primer paso ya queda pausado por el dispatcher.
- Plantilla builtin `juguete` (`packages/core/src/builtin/juguete.ts`, scope `builtin`, se reinstala en cada arranque salvo que una de sus defs esté archivada): `workspace.acquire` → agente `juguete` → `workspace.release`. Necesita los params `repo` (el id de un repo registrado) y `base`: salen del repo del proyecto, o `repo` se fija en `flowParams`. Su guion para el fake está en `packages/testkit/fixtures/runs/juguete`.
- `workspaces.held(runId)` es el `workspaceOf` de Flows: el worktree que la corrida tiene tomado.

## Commits del plan

`commitsApplyAction({ workspaces, recipes })` (`packages/core/src/commits/apply.ts`) es la acción `commits.apply` (`args: { ws, plan, messagePattern?, slot? }`; `plan` es el reporte del committer, de él solo lee `commits[{ message, hunks, tests }]`). Convierte el plan en commits sin tocar el worktree hasta que todo está verificado (`docs/design.html#d-ops`, commitPlan).

- Guarda el árbol completo con `snapshotTree` (index temporal), parte el diff contra la base igual que `hunks.json` (`listHunks`, en `packages/core/src/git/tree.ts`) y hace los commits en un worktree de verify temporal: `git apply --index` de sus hunks, `git commit` (con los hooks del repo, decisión #36) y los tests del commit con `recipes.runCommand(..., "test", { files: tests })`. Corre `setup.worktree` de la receta en el worktree de verify antes. Si el árbol del último commit es el guardado, la branch del worktree se mueve ahí con `reset --mixed`; si no, el worktree queda intacto (no hay nada que resetear).
- Outcomes: `ok` (output `commits`, `tree`), `replan` (hunk sin asignar, repetido o inexistente; mensaje fuera de formato; hunks que no se aplican; test rojo; árbol distinto) y `hook-failed` (un hook rechazó el commit: va al dev). En ambos `output.failures` es el extracto. El máximo de 2 vueltas al committer lo pone el flujo: `replan: { to: "commit", maxRounds: 2, exhausted: ... }`.
- Los cambios que git no parte en hunks (binarios, archivos vacíos nuevos o borrados, cambios de modo) son un hunk entero con `header` entre paréntesis (`(binario)`), para que el committer los pueda asignar.
- El mensaje debe cumplir Conventional Commits, o el `messagePattern` que pase el pack; el core le saca las líneas de atribución a una IA (`Co-Authored-By`, `Claude-Session`, "Generated with"). Parte de la base del lease: un worktree con commits propios lanza `PermanentActionError`, igual que una receta inválida (no se reintentan).
- Todo `git` del core sale de `packages/core/src/git/git.ts` (`git`, `gitRaw`, `tryGit`, `GitError` con `output`): no definas otro helper. Ese git hereda solo `PATH`, `HOME`, `USER`, `LANG`, `TMPDIR` y `SHELL` más el `env` que le pases (los hooks y el config del worktree los escribe el agente); un secreto nuevo nunca llega por ahí.
- Ese git lee el ~/.gitconfig del usuario: un comando que reescribe la branch (rebase, merge) apaga explícito lo que ese config podría prender y cambie el resultado (`--no-autostash`, `--no-update-refs`).
- Se prueba en `packages/testkit/src/commits.test.ts` (repos git reales).

`preparePush(workspaces, ws, { knownSha, base, council })` (`packages/core/src/commits/prepare-push.ts`) es lo que va antes de cada push (`docs/design.html#d-ops`, push y squash); no pushea, y quien publica (`pr.publish`, `pr.pushFixups`) lo llama antes de `workspaces.push`. Primero reconcilia los commits que el agente hizo por su cuenta: se aceptan si `HEAD` desciende de `knownSha` y su árbol es el del worktree; si no, outcome `replan` y la branch vuelve a `knownSha` con `reset --mixed` (el worktree no cambia: el committer recibe todo como cambio sin commitear). No revisa los mensajes de esos commits (ni Conventional Commits ni líneas de atribución, que `commits.apply` sí limpia). Después hace el autosquash: `merge-base` de `HEAD` con `base`, subjects leídos enteros (sin pipes), `rebase --interactive --autosquash --no-autostash --no-update-refs` con `sequence.editor=true` y `core.editor=true`, y árbol igual antes y después. Sin `fixup!` es noop; un conflicto, un árbol distinto o un `fixup!` sin commit destino dejan la branch en el sha anterior (outcome `squash-failed`, que el flujo decide cómo tratar). Con `council: true` no hay squash. `workspaces.push(lease, { council: true })` nunca fuerza: si el `remote_sha` no es ancestro de `HEAD` lanza sin pushear.
Se prueba en `packages/testkit/src/prepare-push.test.ts` y, el guard de council del push, en `git-remote.test.ts`.

`prPushFixupsAction({ store, workspaces, repos, prs })` (`packages/core/src/github/push-fixups.ts`) es la acción `pr.pushFixups` (`args: { ws, items?, route?, messagePattern? }`; `docs/design.html#d-flows`, Fixups): lo que el dev cambió después del triage del bot o de un thread de council sale como `fixup!` del commit al que pertenece. Etapas `council` (`prs.get`, `threads.councilEver`), `commit` y `push`, cada una con `ctx.once`.

- `commit` reconcilia (`preparePush` con `council: true`, que no squashea; lo que no cuadra queda sin commitear) y parte el diff de `HEAD` contra el worktree en hunks (`listHunks`, numerados `h1`... sobre ese diff). `routeHunks` (`commits/route.ts`) manda cada hunk al commit de la branch dueño de las líneas que quita o cambia (`git blame` sobre `HEAD`; si hay varios dueños, el más nuevo, porque el autosquash pone el `fixup!` justo después de su destino y ahí las líneas de un commit posterior todavía no existen). Sin dueño: un hunk que solo agrega, que cambia líneas de la base, que no se parte en líneas o que tiene pegada a un cambio una línea de un commit posterior a su destino (el rebase chocaría). Un commit posterior que borró una línea pegada no se ve en el blame: ese `fixup!` todavía choca y deja `squash-failed`. Hunks de líneas muy cercanas viajan juntos (contexto de 3 líneas) y van a un solo destino.
- Con hunks sin dueño no commitea nada: outcome `route` con `unrouted` (ids de ese diff, que no son los de `hunks.json` del brief: el brief del modo route tiene que escribir el `hunks.json` de este diff, no el de la base). El flujo llama al committer en modo route y vuelve con su `CommitRoute` en `route`: debe cubrir cada hunk sin dueño una vez (si no, `route` de nuevo con `failures`) y se vuelve commits nuevos encima de los `fixup!`. No corre tests por commit.
- Un `fixup!` por commit destino, con el subject del destino (el sha completo si otro commit de la branch tiene el mismo subject). Un `fixup!` que ya está en la branch cuenta como su commit original. Si algo falla la branch vuelve a donde estaba.
- `push`: `preparePush` (autosquash) y `workspaces.push` con lease; con council no hay squash y el push nunca fuerza (los `fixup!` quedan visibles). Un lease rechazado es `PermanentActionError` y un 401 reintenta (`pushOrThrow`, `github/push.ts`, también lo usa `pr.publish`).
- Output `{ byItem, head }`: `byItem[id]` es el commit que quedó pusheado con el arreglo del ítem de `items` (el hunk de su `path` que cubre su `line` de `HEAD`; sin `path`, sin cambio ahí o tras un corte posterior al squash, `head`). Sin council es el commit destino ya reescrito por el squash; con council, el `fixup!`.
- Hace falta un PR abierto de la branch en `pull_requests` y que el worktree ya se haya pusheado; si no, `PermanentActionError`. `startCore` la registra. El nodo `fixups` de `pr-feedback` pasa `items: $bot-wait.items` y `route: $route`: el motor deja `null` el ref de un nodo que no corrió (el primer `fixups` no tiene `$route`; tras un CI rojo, `$bot-wait` es un LGTM sin `items`), así que los args aceptan `null` como ninguno.
- Se prueba en `packages/testkit/src/pr-push-fixups.test.ts` (repos git reales, remoto bare y el GitHub simulado `startGitHubSim`).

## Sincronizar la base

`workspaces.syncBase(lease)` (`packages/core/src/workspaces/workspaces.ts`) y su acción `workspace.syncBase` (nodo sync de la plantilla, `docs/design.html#d-flows`; rebase sin PR en `#d-ops`). Hace `workspaces.fetch` si el repo tiene `RepoConfig.remote` (sin él no hay fetch y la base nueva es la que ya traiga el checkout; `repos.config` lo llena con la cuenta de GitHub conectada, ver Proyectos, corridas y arranque) y compara la punta de la base con la `base_sha` del worktree.

- Outcomes: `same`, `rebased` (el flujo corre los checks de nuevo) y `conflict` (output `conflicts` y `failures`, lo que va al dev). Solo rebasea una branch que no está en el remoto y sin commits propios; si no, lanza `SyncBaseError` (la acción lo vuelve `PermanentActionError`): eso es el rebase de un PR.
- Antes de mover nada, el árbol completo (cambios sin commit y archivos nuevos, `snapshotTree`) se guarda en `refs/clanker/backup/<branch>`: un commit sobre la base vieja; el siguiente sync pisa el respaldo. Volver: `git reset --hard <ref> && git reset --mixed <ref>^`. Luego `reset --hard` a la base nueva, `clean -fd` (solo lo no ignorado, que el patch recrea) y `apply --3way` del patch del respaldo; el index queda limpio. Un conflicto deja las marcas en los archivos; un archivo que la base nueva borró no deja marcas pero se lista y su versión está en el respaldo.
- La base nueva se guarda en la fila al final. Todo sale del respaldo, así que un corte entre el reset y el guardado se retoma al reintentar.
- `workspaces.baseSha(ws)` es la base vigente. El `baseSha` de `$ws` (output de `workspace.acquire`) no se actualiza: `recipe.check`, `commits.apply` y el brief leen la de la fila. Una acción nueva que haga diff contra la base debe hacer lo mismo.
- Se prueba en `packages/testkit/src/workspaces-sync.test.ts` (repos git reales con `origin` bare).

## Rebasear un PR abierto

Carril maintenance (`docs/design.html#d-ops`, rebasePr, y la plantilla de rebase por conflicto en `#d-flows`): `workspace.attach` → `workspace.rebase` → (agente en modo conflict → `workspace.rebase` con `continue`) → `recipe.check` con `afterRebase` → `pr.pushLease`. Es lo que `syncBase` rechaza (branch ya publicada o con commits propios). La plantilla que arma ese flujo es `rebase-conflicto` (ver abajo, "Plantilla clanker-loop"); el agente de conflictos es el modo `conflict` del rol `dev`.

- `workspaces.attach(request)` (acción `workspace.attach`, mismos args que `acquire`): `workspaces.fetch`, toma el lease (crea el worktree desde `origin/<branch>` si no existe) y avanza la branch local a la punta del remoto con `merge --ff-only`; esa punta pasa a ser el `remote_sha`. Una branch que no está en el remoto, o una local con commits que el remoto no tiene (adelantada o divergida), lanza `AttachError` (la acción: `PermanentActionError`) y suelta el lease. Output: un `$ws` más `fastForwarded`.
- `workspaces.rebase(lease, { council, base?, continue? })` (`workspaces.ts`; la mecánica de git en `rebase.ts`). Precondiciones, o `RebaseError`: sin council (nunca se fuerza), `HEAD` = `remote_sha`, árbol limpio (sin contar `.clanker-run/`) y sin un rebase en curso. No hace fetch: usa lo que `attach` trajo. La base es `base` (`origin/main` y `main` son lo mismo) o la del worktree. `from` solo existe si el PR cambió de base (el de abajo se mergeó, con squash o sin él): es el `remote_sha` del workspace de la base vieja o, sin él, `origin/<base vieja>`, y tiene que ser ancestro de `HEAD`. Con `from`: `rebase --onto <base> <from>`; sin él, `rebase <base>`. Siempre con `--no-autostash --no-update-refs`.
- Outcomes: `clean` (guarda `base_ref`, `base_sha` y `head_sha`; el `remote_sha` no cambia: el push con lease lo compara con eso), `conflict` (el rebase queda detenido con HEAD detached; `conflicts` son los archivos sin mergear, `applying` el commit que se aplica, `failures` el extracto) y `error` (falló sin conflicto: `rebase --abort` y la branch queda como estaba).
- `continue: true` sigue ese rebase, un commit a la vez: si en los archivos que el worktree cambió contra `HEAD` quedan marcas `<<<<<<<` o `>>>>>>>` (aunque ya estén en el index) devuelve `conflict` sin avanzar; si no, `git add --all` y `rebase --continue`, que termina (`clean`) o se detiene en el siguiente commit (`conflict`). Pasados 20 commits con conflicto (`MAX_CONFLICTED_COMMITS`, contados en un archivo dentro de la carpeta `rebase-merge` del worktree, que git borra al terminar) aborta con `error`. Si el agente terminó el rebase por su cuenta, `continue` solo lo registra. Hay que pasar la misma `base` en cada visita.
- La acción `workspace.rebase` (`github/rebase-pr.ts`, args `{ ws, base?, continue? }`) busca el PR abierto de la branch en `pull_requests` (solo `owned`: Watch también guarda ahí tus PRs que el sistema no abrió, y esos nunca se reescriben ni se pushean) y lee `threads.councilEver` de `prs.get`; va en una sola etapa `ctx.once`. Las precondiciones que no se cumplen son `PermanentActionError`.
- `recipe.check` acepta `afterRebase: true`: corre antes de los checks los comandos `afterRebase` de la receta (con slot, `{{files}}` y `wrap` como cualquier check; salen en `checks` con el nombre `afterRebase` y uno rojo da `fail` con `[afterRebase] exit N`). Lo que dejen sin commitear no lo pushea `pr.pushLease`.
- `pr.pushLease` (`{ ws }`): `preparePush` (por si quedó un `fixup!`, sin reconciliar: tras un rebase `HEAD` ya no desciende de lo pusheado) y `workspaces.push` con lease, igual que `pr.publish`; con council no forzaría y lanza. Un PR cerrado o mergeado lanza. Outcomes `draft` y `ready` (por `PrState.state`); output `head` y `pr`.
- Lo que pide la plantilla `rebase-conflicto` además: `pr.rebaseApproval { pr, behavior, policy }` (outcomes `proceed` y `ask`; lee el estado vivo del PR: en draft siempre `proceed`; fuera de draft, `ask` si el agente reportó `behavior` o `policy` es `ask`), `workspace.commitAfterRebase { ws }` (commitea con `chore: update generated files after rebase` lo que dejaron el `afterRebase` de la receta o un arreglo del agente; el commit lo hace el core porque no hay nada que decidir, y sin él `pr.pushLease` no pushea esos cambios) y `workspace.rebaseAbort { ws }` (`rebase --abort` si hay uno detenido; sin él, una corrida que termina a medias deja el worktree con un rebase en curso y el siguiente `workspace.rebase` del PR lanza).
- Se prueba en `packages/testkit/src/workspaces-rebase.test.ts` (repos git reales con `origin` bare: base con `origin/`, `--continue` con HEAD detached, padre squasheado, marcas pendientes, tope de 20) y `pr-rebase.test.ts` (las acciones contra el GitHub simulado); el flujo entero, en `rebase-conflict-e2e.test.ts`.

## Restackear la cadena

`stack.restack { pr }` (`packages/core/src/github/restack.ts`, `docs/design.html#d-ops`, restack) rebasea los hijos de un PR del sistema ya mergeado; en un flujo lo dispara `pr.merged` (carril maintenance). `pr_parents(child_id, parent_id)` dice qué PR cuelga de cuál: `pr.publish` inserta la fila al abrir un PR cuya base es la branch de otro PR abierto del repo, y el restack la borra cuando el hijo ya quedó sobre la base nueva. Las bases combinadas (varios padres, `workspace.combineBase`) todavía no existen.

- Verifica y parte de la API: el `merge_commit_sha` y la última punta del padre salen de `prs.get`. `merge.squash` del output compara el árbol del merge con el de fusionar esa punta en lo que había antes (`merge-tree`): `same`, `differs` o `unknown`. Es informativo, porque lo que cuenta es lo que quedó en la base; que el merge no esté en `origin/<base>` sí lanza.
- `workspaces.restack(lease, { council, onto, from, base })` (`workspaces.ts`; la mecánica en `restack.ts`) no usa `rebase --onto`: los commits propios son los de `from..HEAD` por el primer padre, sin los merges cuyo segundo padre ya está en `from` o en `onto` (los de release-bot[bot]); un merge de otra branch da `foreign-merge`. Cada commit se aplica con `merge-tree` sin tocar el worktree, conservando autor, fecha y mensaje, y su patch-id tiene que ser el original (si no, `conflict` sin archivos). La punta nueva se pushea con lease **antes** de mover la branch local (`reset --hard`): un conflicto, un lease rechazado o un fallo del push dejan el worktree y el remoto como estaban, y un reintento sigue siendo posible. Con la branch ya sobre `onto` y sin `from` en su historia es `uptodate`; sin commits propios, `empty`. Las precondiciones son las de `rebase` (`RebaseError`).
- Por hijo, etapas con `ctx.once`: `restack:<n>` (council, `workspaces.attach`, `restack`) y `retarget:<n>`: `PATCH` de la base del PR solo si GitHub no la movió, `pull_requests` y `pr_parents`, y una decisión `review_note` ("Descripción obsoleta") si el cuerpo nombra la branch o el número del padre. Los nietos parten de la punta que el hijo tenía antes (`from`) y de la nueva (`onto`); su base sigue siendo la branch del hijo.
- Un hijo que no se puede restackear no frena a los demás y queda como estaba: `conflict` (outcome `conflict` de la acción, con los archivos, y un evento `pr.conflict` (con `sha`, `base`, `from`, `onto` y `files`, por la clave de Watch) que arranca el flujo de rebase; sus propios hijos no se tocan) o `skipped` con la razón (council, merge de otra branch, lease rechazado, branch local adelantada o divergida, rebase en curso, PR ya cerrado). Un 401 lanza para reintentar con backoff.
- Al final relee `mergeable` de todos los PRs abiertos del repo (REST, hasta 3 veces por los que GitHub aún calcula, con `pause`). Output: `merge`, `children`, `changedDrafts` (los restackeados que están en draft, a los que el flujo les pide /review otra vez) y `mergeable`.
- Pendiente: la punta del padre debe estar en el repo local (si no, el hijo se salta).
- `stack.restackRewritten { pr, from, to }` (mismo archivo; referencia en su TSDoc) es este recorrido con la punta vieja de `pr` como `from` y la nueva como `onto`, sin cambiar la base de los hijos. Lo lanza el flujo `restack-rewritten` de la plantilla con `pr.base_rewritten`, y es también lo que restackea a los nietos de un hijo que quedó en conflicto cuando `rebase-conflicto` lo resuelve y pushea. Pendiente: el hijo que `rebase-conflicto` resolvió conserva su fila de `pr_parents` con el padre ya mergeado.
- Review del bot tras el restack: `changedDrafts` son `{ pr, branch, base }` (la branch y la base con que quedó, para que un flujo tome su worktree). Los flujos `restack` (`pr.merged`) y `restack-rewritten` (`pr.base_rewritten`) siguen con un `parallel` con `forEach: $restack.changedDrafts` que llama al subflujo `restack-feedback` (`workspace.attach` de ese PR → `pr-feedback`), uno por draft y con `join: flows.worst` (el join de un forEach de subflujos: el peor `@end`, `done` si no hay ninguna). Sin drafts cambiados la lista es vacía y no corre ninguna rama ni agente; un PR restackeado que no está en draft no pide review (el restack no lo mueve de listo). Con `conflict` de la acción el flujo también sigue a `feedback`: los hijos que sí se restackearon lo necesitan, y el que chocó lo toma `rebase-conflicto`. Se prueba de punta a punta en `packages/testkit/src/restack-e2e.test.ts` (core real, cadena de 3 PRs sobre `startGitHubSim`, remoto git real y los eventos de Watch emitidos a mano con `watch: false`).
- Se prueba en `packages/testkit/src/pr-restack.test.ts` (repos git reales, remoto bare y `startGitHubSim`, cuyo `merge({ sha })` deja un squash de otro como commit del merge).

## Publicar el PR

`prPublishAction({ store, workspaces, recipes, repos, connections, packs })` (`packages/core/src/github/publish.ts`) es la acción `pr.publish` (`args: { ws, plan, draft?, dependsOn? }`; `plan` es el reporte del committer: `commits` como en `commits.apply` y `pr: { title, body }`). Tres etapas con `ctx.once`, así que un reintento tras un corte retoma donde quedó (`docs/design.html#d-flows`, efectos externos):

- `apply` es `commits.apply`, que reconoce sus commits si el corte llegó entre mover la branch y guardar la etapa (mismos mensajes, en orden, y el árbol del worktree); sin eso un reintento fallaba por "la branch ya no está en la base". `push` corre `preparePush` y `workspaces.push` con lease: un lease rechazado es `PermanentActionError` y un 401 lanza para reintentarse con backoff (la conexión ya quedó `revoked`). `pr` busca el PR abierto de la branch (`GET pulls?head=owner:branch&state=open`) antes de crearlo con `POST pulls`, lo guarda en `pull_requests` (`owned = 1`, con la issue y la corrida de su sujeto) y emite `pr.opened` solo si la fila es nueva.
- Título y cuerpo salen de `plan.pr` (el committer sigue `prompts/pr.md`); el core les quita las líneas de atribución a una IA (`cleanMessage`) y las secciones de `conventions.pr.omitSections` del pack de la org (con su subárbol, sin distinguir mayúsculas). `dependsOn` (`repo#n`) abre el cuerpo con "Depende de ...": el flujo todavía no lo pasa, llega con los stacks.
- Outcomes `ok` (output `pr`: la `PrRef` de `prs.get`, más `url` y `head`) y `replan`. Desvío: un hook que rechaza un commit (`hook-failed` de `commits.apply`) también es `replan`, porque el diseño solo le da dos outcomes a `pr.publish`. Un plan sin commits también es `replan`.
- El repo del PR sale de `RepoConfig.remote.repo` (`owner/repo`) y la cuenta de `remote.account`. `startCore` la registra, con askpass, git remoto y recetas cableados.
- `pull_requests` hoy tiene lo que `pr.publish` sabe (repo, número, branches, sha, estado de GitHub, `is_draft`, issue, corrida, `owned`); las columnas del polling llegan con Watch. Si la base del PR es la branch de otro PR abierto, también guarda la fila de `pr_parents` (ver Restackear la cadena).
- Se prueba en `packages/testkit/src/pr-publish.test.ts` contra el GitHub simulado del testkit (`startGitHubSim`, ver Testkit) y un remoto bare de `tempGitRepo`: `POST pulls` rechaza con 422 un PR sin título, con una branch que no existe, sin commits sobre la base o con un PR abierto igual. Los cortes se simulan con un `ctx.once` que muere justo después del efecto de una etapa.

## Comentarios y threads del PR

`prCommentAction`, `prReplyAction`, `prResolveThreadAction` y `reviewRequestBotAction({ connections, packs, pause? })` (`packages/core/src/github/pr-feedback.ts`) son `pr.comment`, `pr.reply`, `pr.resolveThread` y `review.requestBot`. Salen con el token de la cuenta del PR (la identidad del usuario) y todo lo de la organización lo lee del pack: el prefijo de los comentarios (`conventions.commentPrefix`, `[clanker] ` en Acme), el bot (`reviewBot`), los autores resolubles (`reviewBot.resolvableAuthors`) y el prefijo del council. Lo que dice el agente pasa por `cleanMessage`: nunca firma como IA.

- Cada comentario y respuesta lleva `<!-- clanker:clave -->` con la `key` del paso (`run:nodo:visita`; en una respuesta, más `:<id del ítem>`) y se busca antes de publicar: re-ejecutar no duplica, y una visita nueva sí comenta. El comando al bot es la excepción: va sin marca (el clanker-loop comenta `/review` exacto y lo que el bot hace con otro texto no está a la vista), y no duplicarlo en un reintento lo da `ctx.once`. Entre dos escrituras de una acción hay un segundo (`pause`, que los tests reemplazan).
- Un thread se nombra por el id de su primer comentario (`fullDatabaseId`). Los ítems de triage que llegan a `pr.reply` deben usar ese id (el wait `pr.botReview` debe darlo como `id` de cada hallazgo del bot); un ítem que no es un thread (CI) se salta. `shas` es el `byItem` de `pr.pushFixups`: con sha dice `aplicado en <sha corto>`, si no, la `reply` del triage; sin ninguna se salta.
- `pr.reply` resuelve el thread después de responderlo solo si lo abrió un autor de `resolvableAuthors` y no es de council (un comentario con `councilPrefix`, de cualquier autor: se responde y no se resuelve). Un thread humano solo se responde con el PR en draft y nunca se resuelve. `pr.resolveThread` aplica la misma regla y rechaza con outcome `refused` y `reason`.
- `review.requestBot` da `none` sin bot (o sin pack); con bot comenta `reviewBot.request.body` sin prefijo (el bot reconoce el comando literal) y da `requestedAt` en ms con la hora de GitHub. `pr.reply` con `rerequestBot` lo hace al final y lo incluye en su output, que es lo que lee `bot-wait` (`$prev.requestedAt`).
- Se prueba en `packages/testkit/src/pr-feedback.test.ts` contra `startGitHubSim`; las plantillas (`techlead-flows.test.ts`) corren con estas acciones reales en vez de stubs.

## Brief y artefactos del worktree

`createBriefs({ workspaces, artifacts }).prepare(...)` (`packages/core/src/agents/brief.ts`) arma el `Brief` de cualquier rol y deja en `<worktree>/.clanker-run/` lo que el agente lee si lo necesita: `issue.md`, `diff.patch` contra la base del lease (incluye cambios sin commit y archivos nuevos), `diff-round.patch` (solo con `since`, el `snapshot` que devolvió la ronda anterior), `hunks.json` (`h1`, `h2`... por hunk, en el orden del patch; `id`, `path` y `header`, sin el texto) y `reports/r<n>-<rol>.json` (`createBriefs` los escribe si se los pasan; el motor todavía no). La carpeta se agrega a `.git/info/exclude` y cada archivo también se guarda en `artifacts` con una ref a la corrida (`r<ronda>/<archivo>`). El brief lleva a lo más 5 criterios (los ítems bajo "Criterios de aceptación" del cuerpo) y 10 learnings, y cita los archivos con rutas relativas al worktree. Se prueba en `packages/testkit` (necesita repos git reales).

## Plantilla clanker-loop

`clankerLoopTemplate` (`packages/core/src/template/`) son los roles y perfiles del equipo clanker-loop como datos: bodies de defs `role` y `profile` por slug, validados por `Role`/`Profile` de `@clanker/api`. `payloads.ts` tiene los esquemas zod de brief y reporte (el brief se pasa a JSON Schema suelto y el reporte estricto), `prompts.ts` los prompts y las instrucciones por modo, `roles.ts` y `profiles.ts` los ensamblan. `flows.ts` trae los flujos `techlead-clasico`, `pr-feedback`, `rebase-conflicto`, `restack-feedback`, `restack` y `restack-rewritten` (`clankerLoopTemplate.flows`, con `FlowDef` tipado): `installBuiltins` instala sus roles, perfiles y flujos como `builtin` en cada arranque (`pr-feedback` primero, porque los otros lo llaman, y `restack-feedback` antes de `restack` y `restack-rewritten`; si una def de la plantilla está archivada la plantilla entera queda fuera). `registerFlowStubs` (`packages/testkit/src/flow-stubs.ts`) deja guionar acciones y waits (un check rojo, un conflicto con la base) para recorrer los flujos con el runtime fake (`techlead-flows.test.ts`); lo que pasa por `pr.publish` y `pr.pushFixups` corre con las acciones reales en `techlead-e2e.test.ts`; `techlead-acme` del pack es el mismo flujo y un test lo mantiene alineado. El core no importa nada de aquí: el nombre de un rol solo vive en la plantilla y en sus tests.

- `rebase-conflicto` (trigger `pr.conflict`, carril maintenance, `docs/design.html#d-flows`): `workspace.attach` → `workspace.rebase` → (`conflict`: dev modo `conflict` → `pr.rebaseApproval` → `workspace.rebase` con `continue`, a lo más `conflictRounds` (20, el tope del core) vueltas compartidas) → `recipe.check` con `afterRebase` (rojo: dev `fix`, `checkRounds`) → `workspace.commitAfterRebase` → `pr.pushLease` → draft: `pr-feedback` (que pide `/review`); listo: `@done` con la nota "Pide /review". Params: `pr`, `repo`, `branch` y `base` los pone el trigger (`startTriggers`); `rebaseNonDraft` (`auto` por defecto, decisión 30; `ask` en `flowParams` del proyecto) hace que un PR fuera de draft pregunte aunque no haya conflicto de comportamiento. Con `behavior` (resolver exige decidir comportamiento, decisión 32): en draft sigue con una nota (`review_note`); fuera de draft el gate `behavior-gate` estaciona solo esa corrida y el PR queda en conflicto hasta que alguien elija `continue` (sigue con la resolución conservadora) o `abort` (`workspace.rebaseAbort` y `@blocked`). Un rebase que falla sin conflicto (`error`) estaciona con el gate `rebase-error` (`retry` o `leave`). Cada visita de `workspace.rebase` pasa la misma `base` (`$run.params.base`). El filtro "sin threads de council" no es un `filter` del flujo (compara el payload): lo hace `startTriggers`. Los `flowParams` del proyecto que el flujo por defecto no declara no rompen `runs.start`: se ignoran ahí (son de los flujos que arrancan los triggers). Se prueba en `packages/testkit/src/rebase-conflict-e2e.test.ts` (core real, dev fake con `effects: - write:` que escribe el archivo ya resuelto, `startGitHubSim` y un remoto git real).
- Un prompt no pide lo que hace el core (push, PR, checks, respuestas en el PR o el tracker) ni nada propio de un repo o empresa: eso llega como contexto del rol (`pack`, `repo`). El test de la plantilla lo verifica.
- Un rol o modo nuevo debe calzar con lo que referencian los flujos de la plantilla: su lista está en `template.test.ts`. Tras cambiar un esquema de reporte, `npx vitest run -u packages/core/src/template` regenera el snapshot; revisa el diff.

## Métricas

`recordRunMetrics(tx, runId)` (`packages/core/src/metrics/record.ts`) llena `run_metrics` y `run_role_costs` en la misma tx que cierra la corrida (`@fin` o cancelación), desde `runs.rounds`, los `step_runs` (outcomes por nodo) y `step_usage` y las `agent_sessions` de sus pasos (costo y tokens por rol, modelo y effort; `step_usage` acumula lo que cada paso consumió de su sesión, y es de donde `closeStep` saca el costo del paso: un resume con el mismo id de sesión no deja su costo en el paso original). Todo lo que consume la UI sale de ahí vía `createMetrics` (`metrics.byRole|byDay|byModel`, `projects.summary`): los costos suman todas las corridas, hijas de subflujo incluidas; los conteos (`runs`), solo las raíz. Los días son del cierre, en la zona `utcOffsetMinutes`. La importación del loop viejo escribe estas mismas tablas (ver más abajo) y `MetricsFilter.imported` (`true` solo importadas, `false` solo las de Yard) las distingue en `metrics.byRole|byDay|byModel`. `clanker metrics compare --legacy <metrics.jsonl>` (`apps/cli`, `npm run clanker -w @clanker/cli -- ...`) compara promedios por rol contra lo que lleva el core.

## Importación del clanker-loop

`clanker import legacy --from <carpeta> [--dry-run] [--json]` llama a `imports.legacy` (sin `meta.mcp`: lee archivos del disco) y el core corre `createLegacyImporter` (`packages/core/src/import/legacy.ts`, parser de `state.md` en `legacy-state.ts`) sobre la carpeta del loop (`~/.local/share/clanker-loop`), que solo lee. En una prueba o corrida manual usa un `CLANKER_HOME` temporal; nunca importes al real sin que Simón lo pida. Un `--dry-run` calcula el mismo plan y no escribe nada.

- Es idempotente: cada corrida lleva `runs.source_key` (`legacy:metrics:<proyecto>:<issue>:<ts>`; `NULL` en las que corre Yard) y issues, PRs, proyectos y vínculos de repos se buscan por su clave natural, así que repetirlo solo agrega lo nuevo. Los proyectos que ya existen no se pisan. Todo va en una tx con su evento `import.completed` (origin `import`) y falla, sin escribir, si los totales de un proyecto no cuadran con `metrics.jsonl`.
- Cada línea de `metrics.jsonl` es una corrida del flujo `legacy-clanker-loop` (def de usuario archivada, para que nadie la lance; versión 1) con `lane: dev`, `params.legacy` con lo que el core no modela (resultado original, perfil, repo, PR, modo) y `run_role_costs` por rol, techlead incluido. `run_metrics.rounds` usa `review`, `bot` y `ci` (los contadores de `techlead-clasico`; `ci` son los `ci-fails`) y `outcomes.bot` guarda `valid` y `false_positive`. Resultados: `listo`, `council-listo` y `sin-lgtm` son `done`; `pendientes`, `necesita-humano` y `bloqueada`, `blocked`; `falló` y `fallo`, `failed`. Uno desconocido falla el import: agrégalo a `outcomeOf`.
- Los proyectos entran `paused`, con `tracker: linear` y el slug del proyecto de Linear como `trackerRef` (placeholder: cámbialo por el id de Linear antes de reanudarlos) y el `parallel:` de la cabecera. Las issues del historial y de `metrics.jsonl` entran con su key como `tracker_id`, y los PRs con `owned = 0` y lo que sabe GitHub (nodo, SHA, base) vacío hasta que Watch los sincronice.
- Nunca crea repos: los resuelve por la ruta de la cabecera o por nombre. Los que no encuentra salen en `unresolvedRepos` y sus PRs quedan fuera hasta registrarlos y repetir el comando.
- Lo que aún no se importa: brief y reglas (`conventions` solo admite referencias y switches tipados), decisiones y aprendizajes, `issues/*.md`, `profiles.json` y precios.

## MCP

El MCP (`docs/design.html#mcp`) sale del contrato: `generateMcp` (`packages/core/src/mcp/generate.ts`) recorre `contract` de `@clanker/api` y arma las tools, los esquemas y los procedimientos de los resources a partir de `.meta({ mcp })` (la convención y sus tipos están en `packages/api/src/mcp.ts`). `createMcpHandler` (`mcp/server.ts`) los registra con `@modelcontextprotocol/server` y llama al router en proceso con `createRouterClient` y origin `mcp`: la misma validación y los mismos eventos que la UI. La escritura sale igual: las tools por kind y las acciones.

- Tools: `list` (`{ kind, filter? }`, los campos de `filter` son los del input del procedimiento y la descripción de la tool los lista por kind) y `get` (`{ kind, id, version? }`), con `readOnlyHint` y `openWorldHint: false`. Kinds: `flow`, `role`, `profile`, `recipe`, `pack` (por `defs.list` y `defs.get`, un solo procedimiento que recibe `kind`), `project`, `run` y `decision`. `context` ya tiene esquema (`ContextPackage`, lo registra Agents) pero no está expuesto por MCP, por eso no está. Un error del contrato (`NOT_FOUND`, `BAD_REQUEST`) llega al modelo como resultado de la tool con `isError`.
- Escritura: `create`, `update` y `delete` (`kind` flow, role o profile; `delete` archiva, y su deshacer `defs.restore` es solo de la API) y las acciones (`meta.mcp.action`, con `description` y anotaciones; el catálogo está en `contract.ts`). Pasan por `createDefWriter` (`defs/write.ts`): `dryRun` devuelve `errors` o `diff` sin guardar, y las defs `builtin` y de packs no se editan ni archivan porque el core las regenera (se pisan con una `create` de scope `user` y el mismo slug). `destructiveHint` va siempre explícito: un cliente lo da por verdadero si falta.
- Resources: `clanker://schema/<kind>` (`z.toJSONSchema` de `MCP_KIND_SCHEMAS`: el body para los kinds de `defs`, lo que `get` devuelve para `project`, `run` y `decision`), `clanker://flow/<id>`, `clanker://run/<id>/timeline` (los eventos de la corrida, paginando `events.list`) y `clanker://step/<id>/report` (el reporte de cada sesión del paso, de `runs.step`).
- Para exponer un procedimiento nuevo: `.meta({ mcp: ... })` en el contrato y, si es un kind nuevo, su esquema en `MCP_KIND_SCHEMAS` (TypeScript lo exige). Si falta un esquema o las anotaciones de una acción, `generateMcp` lanza y el core no arranca; `generate.test.ts` lo cubre. `mcp.test.ts` del testkit habla MCP de verdad contra un core real y guarda el snapshot de la lista de tools: un cambio en lo que ven los clientes se aprueba actualizándolo.
- Transporte: Streamable HTTP sin sesión en `/mcp` del mismo puerto que `/rpc` (un `McpServer` por request), con el mismo token y las mismas reglas de Host y Origin; no pide `x-clanker-origin`, siempre es `mcp`. El token cambia en cada arranque del core, por eso los clientes no lo guardan: `clanker mcp` (`apps/cli/src/mcp.ts`) es el puente stdio que lee `core.json` (levantando el core si no corre) y reenvía los mensajes sin interpretarlos.
- `.mcp.json` trae la entrada `clanker`, que corre `clanker mcp` desde el checkout (`npx --no-install tsx apps/cli/src/main.ts mcp`); necesita el core construido (`npm run build -w @clanker/core`) y usa los datos reales salvo que el cliente lo lance con `CLANKER_HOME`.

## Motor de flujos

`createFlows({ store, defs, agents, artifacts, roles, workspaceOf })` (`packages/core/src/flows/`) valida, guarda y ejecuta flujos (`docs/design.html#d-flows`). Ejecuta nodos `agent`, `action`, `wait`, `parallel`, `flow` y `gate`; `start` rechaza antes de crear nada un flujo con un gate como rama de un parallel (fija o de un forEach, también en un subflujo que llama): un gate estaciona su corrida entera.

- `flows.start(flujo, sujeto, params, { profile, projectId })` es idempotente por (flujo, sujeto) mientras la corrida siga viva (índice parcial de `runs`). La corrida fija la versión del flujo, de sus roles y del perfil; Agents recibe esas versiones en `roleDef` y `profileDef`.
- Una acción se registra con `registerAction({ name, args, outcomes, effects, run })`. `run(args, ctx)` devuelve `{ outcome, output }`: un outcome de negocio es un resultado y nunca se reintenta; solo una excepción reintenta, según `retry` (default 3 con 10 s, 60 s y 5 min). Lo que reintentar no arregla (configuración mal escrita, una precondición que no va a cambiar) se lanza como `PermanentActionError`: el paso da `error` al primer intento. `ctx.key` es `run:nodo:visita`, igual en todos los reintentos, `ctx.stepId` es el `step_runs.id` (también estable) y `ctx.once(etapa, fn)` guarda cada etapa en `action_effects`.
- Parallel (`parallel.ts`, `consolidators.ts`): el padre queda `waiting` y crea un paso por rama (las fijas son nodos del flujo; las de un `forEach` se llaman `nodo[i]`, y `$item` resuelve a su ítem). Cada rama cierra con su outcome sin seguir edges (`error` y `timeout` dejan el paso `failed`). El join lo planea y aplica el cierre de la última rama en su misma tx; el output del consolidador se guarda antes, porque los artefactos abren su propia tx. Con `rerun: "not-ok"` solo corren las ramas fijas que no dieron ok y el join usa lo último de las demás. `onBranchError: "ignore"` deja fuera las ramas con error (si todas fallan, el parallel termina en `error`); por defecto cualquier error es el `error` del parallel.
- Wait: se registra con `registerWait({ name, args, outcomes, key, match, probe })` (`WaitDef` en `catalog.ts`). El paso entra, llama `probe(args)` y, si no hay resultado, queda `waiting` con `wait_key` (`key(args)`) y `deadline` (`timeoutSec` del nodo desde que entró; sin `timeoutSec` no vence). Lo cierran `flows.signal(evento)` (cada wait esperando cuyo `match(evento, args)` devuelve `{ outcome, output }`), un sondeo con `probe` cada `probeEverySec` (60 por defecto; con Watch encendido el core lo sube a 600 s: es la red de seguridad, porque cada sondeo cuesta GraphQL) o el tick del dispatcher al pasar el `deadline`, con outcome `timeout` (sin edge `timeout` cuenta como `error`). La corrida sigue `running`, como con un parallel. Un `probe` que lanza al entrar reintenta el paso como una acción; uno que lanza en un sondeo deja el wait esperando con el error en `step_runs.error` y se reintenta en el siguiente. El calendario de sondeos vive en memoria: tras un reinicio, el primer tick sondea todo (el `recover` de Flows deberá despertar el dispatcher al bootear). Un wait también puede ser rama de un parallel.
- Flow (`engine.ts`, `openChild` y `sweepChildren`): el nodo crea una corrida hija (`runs.parent_run_id`, `parent_step_run_id`) del subflujo que la corrida fijó al empezar (`runs.subflows`: `start` fija también los subflujos de los subflujos y sus roles) y queda `waiting`, igual que un parallel; paso y hija nacen en la misma tx, así que un paso `flow` cortado nunca tiene hija a medias. La hija hereda sujeto, carril, proyecto, roles y perfil (el `profile` del nodo, un slug, lo pisa), y un padre `effects: "local"` le quita los efectos aunque su flujo los declare. Sus params salen de resolver `params` en el padre. Un `$nodo` o un `resumeFrom` se buscan primero en la hija y luego en sus padres; el agente de la hija corre en el worktree del padre (`workspaceOf` se pregunta por la corrida y sus padres). Su `@end` es el outcome del paso padre (`done`, `blocked`, `failed`; una hija cancelada es `failed`) y no deja output. `stopBefore` termina la hija con `done` cuando un edge va a llegar a ese nodo, sin ejecutarlo (no puede ser el nodo inicial). La hija no cuenta para el índice de una corrida viva por (flujo, sujeto): el bench corre el mismo flujo varias veces sobre la misma issue. `timeoutSec` y `retry` no aplican a un nodo flow; el costo de la hija queda en su corrida, no se suma a la del padre.
- Comandos de una persona (`control` y `stepCommand` del motor, `runs.pause|resume|cancel|interrupt|retryStep|steerStep|forceOutcome` y `projects.pause|resume` de la API; `by` es el origen y queda en los eventos): `control(runId, "cancel", { by })` cancela la corrida y todas sus hijas en una tx (pasos pending, leased, running y waiting quedan `canceled`, cada corrida emite `run.finished` con outcome `canceled` y `origin: by`) y después aborta lo que este proceso tiene en vuelo: el agente se interrumpe (su proceso cae con SIGTERM al grupo y, si no cierra, SIGKILL a los 10 s: `KILL_GROUP_AFTER_MS` del runtime Claude) y la acción recibe el abort de su `signal`; el cierre tardío de esos pasos se descarta por fencing. Las decisiones `gate` y `needs_human` que la estacionaban quedan `superseded`. Al `run.finished` el core suelta los worktrees de la corrida (ver Proyectos, corridas y arranque).
- Pausar (`control(runId, "pause", { by, now? })`): la corrida y sus hijas que corren (`running`) pasan a `paused` y emiten `run.status` `{ from, to, now }` con el actor. Una pausada sigue ocupando su cupo de carril y su sujeto (no se presta), el dispatcher no despacha sus pasos pending y los agentes en curso terminan lo suyo; lo que sigue de un paso que cierra queda pending. Sus waits, en cambio, siguen vivos (`signal`, sondeos, plazos, también `waitKeys`) y `sweepChildren` cierra sus pasos `flow`: lo que pasó con la corrida pausada no se pierde, solo no avanza al paso siguiente. Con `now` se aborta a los agentes en vuelo con una `Interruption("pause")`: su paso vuelve a pending sin gastar intento (`deferrals` + 1, `error` = `RESUMED_AFTER_PAUSE`) y su sesión queda marcada para retomarse, igual que un apagado limpio, y al retomar `performAgent` la reabre con un aviso. Pausar con `now` una ya pausada interrumpe a los agentes que sigan. Una corrida estacionada, en cola o terminada no se pausa (`RunCommandError`, BAD_REQUEST en la API). `resume` devuelve a `running` las pausadas de la familia; en una que ya corre no hace nada. `interrupt` de la API es `pause` con `now`. Un paso que cierra sin edge mientras la corrida está pausada la estaciona (`needs_human`) y al resolverse vuelve a `running`: la pausa no se recuerda.
- Comandos sobre un paso (`stepCommand(stepId, cmd, by)`, devuelve la corrida; `step.commanded` con `origin: by` y `{ command, message?, outcome? }`): la corrida debe estar viva y no en cola. `retry` es "reintentar desde acá": cancela lo que la corrida tiene en marcha (pasos, ramas y las corridas hijas de un nodo `flow`), cierra la decisión que la estacionaba (`answered` con `retry` si era el `needs_human` de ese mismo paso, `superseded` si no) y deja una visita nueva del nodo con `error` = `RETRIED`, que hace que `performAgent` ignore el `resumeFrom` del nodo (sesión nueva); una corrida estacionada vuelve a la cola de su carril y una pausada sigue pausada; no sirve sobre una rama o el join de un parallel (se reintenta el parallel). `steer` es solo de agentes: en curso, lo interrumpe con una `Interruption("steer")`; pending, lo marca; fallado y con la corrida esperando su `needs_human`, cierra esa decisión (`superseded`) y abre una visita nueva que retoma la última sesión del paso. En todos `performAgent` retoma la sesión con el mensaje como `notice` (el mensaje se lee del último `step.commanded` `steer` del paso: los eventos son la fuente, sin columna nueva). `force` es solo de pasos `action` y `wait` (decisión #44, nunca un agente) y solo de un outcome que el nodo declara en `on`: cierra el paso (pending, en curso o esperando) como `done` con ese outcome, aborta su ejecución si está en vuelo y sigue el edge sin ejecutarlo; si la corrida espera el `needs_human` de ese paso delega en la opción `force:<outcome>` de la decisión. Los tres devuelven `RunCommandError` con el motivo si el estado no lo permite.
- Proyecto pausado (`projects.pause|resume`, `Projects.setStatus`): solo cambia `status` y emite `project.paused|resumed` con el actor, y el Scheduler deja de lanzar sus issues; no toca las corridas del proyecto, el carril de mantenimiento ni otros proyectos. No desarchiva (un archivado es `InvalidProjectError`).
- Consolidadores: `worst`, `flows.worst` (el join de un forEach de subflujos: sus outcomes son los `@end` `done`, `blocked`, `failed`) e `items.merge` ya vienen registrados; `registerConsolidator({ name, outcomes, args?, run })` agrega otros. `run(byBranch, args)` es síncrona y pura, y recibe `{ rama: { outcome, output } }` solo de las ramas que corrieron y no fallaron (en un forEach, por posición). Un join con rol (`join: { role, mode }`) corre un paso de agente `nodo#join` que recibe `{ rama: output }`; su outcome y su output son los del parallel.
- `items.merge` agrupa los ítems por `path` y línea (±3, nunca dos de la misma rama), gana el de mayor rango, los ⚪ pasan solo con `trivial`, sale ordenado 🔴 → 🟡 → ⚪ y cada ítem lleva `branch` y un `id` que es el hash de sus `idKeys` (por defecto `branch`, `path`, `claim`): el mismo hallazgo mantiene su id entre rondas.
- Lo que falla al cargar, despachar o recuperar una corrida (su flujo, su nodo, su edge) estaciona solo esa corrida: nada en el barrido de waits, en el loop del dispatcher ni en `recover()` puede cortarlos para las demás ni tumbar el arranque (`docs/design.html#nunca-se-congela`).
- Un paso agent necesita un worktree: `workspaceOf(runId)` lo entrega (hoy el que la corrida tiene tomado en Workspaces).
- Los reintentos son la misma fila de `step_runs` con `attempt` mayor (el token de fencing). Un error del entorno del agente (login vencido, cuota agotada) devuelve el paso a pending con `not_before` sin gastar intento.
- Recuperación (`flows.recover()`, síncrona, la llama `startCore` antes de levantar la API y después de `procs.killOrphans()` y `workspaces.recover()`; ese orden importa): reabre como `pending` todo paso `leased` o `running` de otro boot id, venza o no su lease (este core tiene el lock, el anterior ya murió), y despierta al dispatcher. Cada reapertura suma a `step_runs.recoveries` y no gasta intento; un paso frenado por el entorno suma a `deferrals`. `attempt` solo sube, en cada lease, porque es el token de fencing: los intentos gastados son `attempt` − `recoveries` − `deferrals`. Al tercer corte el paso cierra con `error` y sigue su edge, o la corrida queda parked (`needs_human`). Qué hace cada tipo al re-despacharse: acción, la misma clave y sus etapas `once` ya guardadas; agente, retoma la sesión que el corte dejó sin cerrar (queda con `error` = "La sesión se interrumpió con el paso en curso; se retoma.", el mismo de un apagado, una pausa con `now` o un mensaje) o abre una nueva con el mismo brief, los dos con un aviso (`notice` de `RunRequest` y `ResumeRequest`) antes de las instrucciones del modo; wait, el primer tick lo sondea (el calendario de sondeos vive en memoria y arranca vacío) y vence su plazo si pasó; parallel, cada rama se recupera sola y el join lo evalúa quien cierra la última. Un paso `flow` cortado antes de abrir su hija se reabre como cualquier otro; con la hija abierta el paso sigue `waiting` y cada paso de la hija se recupera solo. `wake` cierra (`sweepChildren`) los pasos `flow` cuya hija ya terminó, también lo que un corte dejó entre el fin de la hija y el cierre del padre; una hija parked deja al padre esperando. Un gate no necesita nada: su corrida sigue parked con la decisión abierta, y su plazo (`timeoutSec`) lo vence el tick aunque haya pasado con la app cerrada.
- Latido y reloj: el latido de un paso renueva su lease cada 40 s y, si ya no es el de su attempt, aborta el `signal` del paso. Si el dispatcher despierta con más de 30 s de hueco desde el último despertar (la máquina durmió), extiende los leases propios y llama a `onClockJump` (Workspaces extiende los suyos) antes de sondear o despachar.
- Decisiones que no paran (`packages/core/src/decisions/`, tabla `decisions`, `docs/design.html#d-flows`): el `note` del edge que se toma (también el de un `exhausted`) y cada `Report.decisions` de un agente abren una decisión `review_note` `pending` con `openNote(tx, ...)`, en la misma transacción que cierra el paso (`closeStep`), y emiten `decision.opened`. No tocan la corrida: sigue por su edge. `createDecisions(store)` da `list(filter)` y `get(id)` (`decisions.list` y `decisions.get` de la API). `openDecision` y `closeDecision` son lo único que escribe la tabla (`decision.opened` y `decision.resolved` salen en su misma transacción).
- Estacionar (`park` y `resolveGate` en `engine.ts`, regla A de `docs/design.html#nunca-se-congela`): una corrida `parked` no la despacha el dispatcher, no retiene slot de entorno ni cupo de agente (los toma cada paso) y conserva su worktree. Las tres formas abren una decisión bloqueante en la misma transacción que la estaciona y emiten `run.parked` con `{ reason, decisionId }`: `gate` (el nodo `gate`: el paso queda `waiting`, con `deadline` si hay `timeoutSec`; vencido sigue por su `default` y la decisión queda `expired`, sin default el outcome es `timeout`), `needs_human` (un paso que termina sin edge para su outcome, también uno que no se pudo cargar: opciones `retry`, `force:<outcome>` por cada edge del nodo y `cancel`) y `limit` (`parkOverLimit`, antes de despachar un paso: `limits.maxCostUsd` o `maxSteps` del flujo, y el `maxCostUsd` del proyecto manda sobre el del flujo; el paso listo queda pending y las opciones son `continue` y `cancel`; cada `continue` resuelto suma otra vez el tope entero, sin guardar nada más que la decisión). `resolveGate(decisionId, option, by)` (también `decisions.resolve` de la API, con el origen como `by`) sirve a las tres: cierra la decisión (`answered`), hace que la corrida salga de parked (`leaveParking`, que emite `run.requeued` si sigue viva) y la deja en la cola de su carril; como el dispatcher toma primero las corridas más antiguas, va antes que las nuevas. `retry` abre una visita nueva del nodo, `force` sigue el edge sin ejecutar el paso y `cancel` cancela la corrida y sus hijas en esa misma transacción. Una decisión que no bloquea (`review_note`, `note`, `question`, `alert`) no tiene corrida: `resolveGate` la cierra `answered` con `{ option }` sea cual sea (una de sus opciones o un texto libre) y no reencola nada. "Un reintento" antes de `needs_human` es el `retry` del nodo (agente: 1 por defecto).
- Tope del paso de agente: si el runtime devuelve `error_max_turns` o `error_max_budget_usd` y el nodo tiene `escalate`, el paso se reintenta una vez (sin gastar su `retry`) con la entrada del perfil `escalate.profileRole` (`dev-escala`), una sesión nueva sin `resumeFrom` y un aviso de handoff; el marcador es `step_runs.error`, como el del corte. Si vuelve a pasarse, o el nodo no tiene `escalate`, es un `error` sin reintento. `escalate.counter` y `from` (escalar por ronda de review) todavía no se evalúan.
- Una corrida dueña por sujeto y préstamo (`flows/subjects.ts`, `docs/design.html#d-flows`, decisiones 3 y 9): el sujeto de una corrida es el suyo (`subject_*`) y, si es de una issue que ya publicó su PR, también ese PR (`runs.claimed_pr_id`, que escribe `pr.publish` en la tx que guarda el PR; la hija de un subflujo se lo da a su corrida raíz). Índices parciales UNIQUE de `runs`: `runs_subject_owner` (una dueña que escribe por sujeto, entre todos los flujos; `queued` no cuenta), `runs_claimed_pr_owner` (lo mismo para el PR tomado; que otra corrida lo tenga ya como sujeto lo revisa `ownerOf`, porque un índice ve una sola columna) y `runs_borrowed_from` (un solo préstamo a la vez). Las tres excluyen a las hijas (`parent_run_id IS NULL`, igual que el índice por flujo: heredan el sujeto del padre y corren a la vez) y las dos primeras a las corridas con un sujeto prestado; solo cuentan corridas con `writes = 1`.
- `start` y los triggers pasan por `subjects.admit`: sin dueña, la corrida corre; con dueña, queda `queued` (el dispatcher solo toma `running`) esperando a esa corrida, no a un slot; y si la dueña es de dev y está `parked` y la nueva es del carril de mantenimiento, corre de inmediato con `borrowed_from_run_id` y emite `run.borrowed` (`{ runId, fromRunId }`, con `runId` la que pide prestado). Las `queued` pasan a `running` (`run.status` `{ from: "queued", to: "running" }`) cuando la dueña termina o se cancela, o cuando se estaciona y es prestable: `promoteQueued` corre en la tx que termina una corrida (`subjects.ended`) y en cada `wake`, las más antiguas primero. Hay un solo préstamo por dueña: la segunda corrida de mantenimiento espera a que vuelva el sujeto y entonces lo pide de nuevo si la dueña sigue estacionada. Una corrida de dev nunca pide prestado.
- El préstamo mueve también el lease del worktree: `EngineDeps.handOverWorkspaces` (`workspaces.handOver(tx, from, to)` en el core) pasa los worktrees de la dueña a quien los toma prestados, con `fencing_token + 1` y su latido, en la misma tx. Al terminar (`@done`, `@failed` o cancelada), antes de emitir `run.finished`, la corrida los devuelve (`run.returned`, mismo payload, otro `fencing_token + 1`): así `releaseHeldBy` de `run.finished` ya no los encuentra. Como el `$ws` de la dueña guarda el token con que tomó el worktree, el motor lo reemplaza por el vigente (`workspaceOf` devuelve `workspaceId` y `fencingToken`) al resolver un `$nodo` cuyo output nombra ese worktree; `workspace.acquire` de quien lo tiene prestado lo vuelve a tomar sin esperar (es suyo). `startCore` relee el `head_sha` del worktree de la dueña con `workspaces.reread` al ver `run.returned`; `remote_sha` no se relee, a propósito: es la punta que el core pusheó por última vez (la que espera `--force-with-lease`, y cada `push` de quien tuvo el préstamo la deja al día), y adoptar la del remoto dejaría pisar el commit de otra persona.
- Una decisión que se resuelve mientras el sujeto está prestado (`leaveParking`) queda `answered`, la corrida aplica su edge (el paso siguiente queda `pending`) pero sigue `parked`, sin `run.requeued`: al devolverse el sujeto, `subjects.ended` la pasa a `running` y emite `run.requeued` (`{ decisionId, reason }`). Si la dueña se cancela (o termina) con el préstamo vivo, quien lo tiene pasa a ser la dueña (`borrowed_from_run_id` a `NULL`) y no hay `run.returned`.
- Cupos por carril en el motor: ver "Carriles" en Proyectos, corridas y arranque. `Engine.wake()` es público para que el Scheduler admita lo que espera cupo antes de repartir los libres; `resolveGate` deja la corrida `parked` (decisión `answered`) si su carril no tiene cupo, igual que con el sujeto prestado.
- Los tests de flujos usan un `AgentRuntime` stub (`engine.test.ts`) y esperan `run.finished` o `run.parked` en los eventos, nunca sleeps; el backoff y los timeouts se prueban con `vi.useFakeTimers()`.

## Runtime de Claude

`createClaudeRuntime({ credentials, home })` (`packages/core/src/agents/claude/`) es el runtime `claude-sdk`: lanza Claude Code con `@anthropic-ai/claude-agent-sdk` (versión fija, súbela a propósito). `credentials` es una función que se llama en cada run y sale de `subscriptionCredentials()` (el `claude` del `PATH`, sin leer ni guardar el login) o `apiKeyCredentials(key)`; en el core la entrega `connections.claudeCredentials` (ver Secretos y conexiones), así que guardar o quitar la API key vale desde el siguiente run. Con API key, `login_expired` es la key rechazada (su mensaje no manda a `claude auth login`). Login vencido y cuota agotada son errores del entorno del agente: el motor devuelve el paso a pending sin gastar intento y abre el breaker `runtime:<id>` (ver Circuit breakers); con login vencido deja además la cuenta `claude` en rojo (`connections.markClaudeLoginLost`).

- El entorno del agente se arma con lista blanca (`agentEnv`): nunca hereda `GH_TOKEN`, `GITHUB_TOKEN`, `LINEAR_*`, `SSH_AUTH_SOCK` ni `ANTHROPIC_*`. Si una variable nueva debe llegar al agente, se agrega ahí y en su test.
- Con `procs` (el core real lo pasa), el proceso de Claude Code lo lanza `spawnClaudeCodeProcess` en su propio grupo y queda en `procs` con `kind: "agent"` y el `stepRunId` del `RunSpec` (`ResumeSpec` también lo trae); si el SDK se rinde con su cierre ordenado, se baja el grupo entero. Ese spawn ignora el stderr de `claude`, así que los errores de salida del SDK no traen su cola. Un test que ejercite el lanzamiento inyecta un `query` falso que llama a `options.spawnClaudeCodeProcess` con un `sleep`, nunca a Claude.
- Bajo `home` deja `transcripts/<sessionId>.jsonl` (mensajes del SDK tal cual, más una línea `clanker/pre_compact` por compactación), `agent-sessions/<sessionId>.json` (lo que `resume` necesita) y `agent-env/` (`gh/` vacía y el `gitconfig` generado).
- Costo por turno (`docs/design.html#d-agents`): el runtime emite un evento `usage` por mensaje `assistant` (deduplicado por `message.id`, con `model` y `cacheWrite1hTokens`) y Agents lo guarda en `agent_turns` con `agent.usage`, sumándolo a `agent_sessions` en la misma tx. Con `costPerTurn: false` (Claude) el USD del turno sale de `model_prices` (`estimateCostMicros`, `agents/pricing.ts`: micros por millón de tokens, `model` es una familia como `opus`, rige el `valid_from` más reciente; un modelo sin precio deja el turno en 0 y un evento `error` con `scope: "agent.usage"`). Al cerrar, el total del runtime (`total_cost_usd` menos lo que la sesión ya traía) manda sobre las estimaciones: se suma solo la diferencia, y si difieren más de 2% sale un evento `error` con `scope: "agent.usage"`. Sin `result` (el run se cortó) la sesión queda con la suma de sus turnos. Los costos de pasos y corridas se suman al cerrar el paso desde `agent_sessions`. Un runtime nuevo que reporte el costo por turno pone `costPerTurn: true`.
- El transcript se lee por la API con `runs.transcript({ sessionId, cursor })` (`agents/transcripts.ts`, `agents/claude/transcript.ts`): `sessionId` es `agent_sessions.id`, el core busca su `sessionRef` y lee `<home>/transcripts/<sessionRef>.jsonl`. `cursor` es un offset en bytes (no un número de página), `next` es dónde seguir y una línea a medio escribir no se consume: así sirve para seguir una sesión viva. Normaliza cada mensaje del SDK a eventos (`prompt`, `text`, `thinking`, `tool_call`, `tool_result`, `compaction`, `result`) y recorta el texto de cada uno a `TRANSCRIPT_TEXT_MAX_CHARS`; el archivo sigue completo. Sin archivo devuelve una página vacía. El fake de `testkit` también escribe transcripts con esa forma si se le pasa `transcripts`.
- Sesiones y caché (`agents.ts`, `docs/design.html#d-agents`): `agents.run` decide con `session` del modo y `resumeFrom`. `new` ignora `resumeFrom`; `resume` retoma esa sesión; `resume-if-warm` la retoma solo si su última respuesta (el último `agent_turns.ts`) fue hace menos de `WARM_WINDOW_MS` (4 min con TTL 5 m, 59 min con `cacheTtl: "1h"` del perfil) y su contexto (`tokensIn + cacheRead + cacheWrite` del último turno) pesa menos de `WARM_MAX_CONTEXT_TOKENS` (80k); sin turnos registrados cuenta como fría. Una sesión con `agent_sessions.compactions > 0` no se retoma con ninguna política. Si no se retoma, la sesión es nueva (con el mismo prompt de rol, así que sigue leyendo la caché del prefijo) y su mensaje empieza con un handoff de `HANDOFF_MAX_CHARS` (~15k tokens): por qué no se retomó, el reporte de la sesión anterior y `git diff --stat <brief.base>` en el worktree. El plan y las instrucciones de la ronda vienen en el brief, no en el handoff. Si git falla, el handoff lo dice y la corrida recibe un `error` con `scope: "agent.handoff"`. El `cacheTtl` del perfil llega al lanzar y al retomar (`ResumeSpec.cacheTtl`).
- Compactación: el hook `PreCompact` sigue dejando `clanker/pre_compact` en el transcript y además emite el evento `compaction`; Agents suma 1 a `agent_sessions.compactions`.
- Prefijo compartido (`claimPrefix` en `agents.ts`): quien lanza con el mismo modelo, `cacheTtl`, herramientas, `native` y prompt de rol que una sesión que todavía no emitió nada espera su primer evento (el runtime Claude emite `first_token` con el primer mensaje del modelo, aunque sea solo razonamiento) y recién ahí lanza, para leer la caché en vez de escribirla; sirve igual a las ramas de un parallel y a runs de issues distintas. Se libera con cualquier evento, al terminar la sesión o si el `signal` del paso aborta. El contexto del repo (`references`) no entra en la clave: va después del límite y cambia por rol. Los reviewers de la plantilla comparten el prompt, no las references, así que comparten solo hasta el límite.
- Orden del prefijo (`toOptions`): herramientas (las listas de `tools.allow` y `deny` van ordenadas) → prompt del rol → `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` → contexto del repo; el brief va en el mensaje. Sin `references` no se agrega el límite. Nada con fecha, cwd ni git status antes del límite: lo garantiza que el prompt del rol sale tal cual de la def.
- Contexto del rol: el runtime recibe `RunSpec.native` (`settingSources` y `skills`, solo Claude) y `RunSpec.references` (archivos ya leídos, van al prompt de sistema tras `SYSTEM_PROMPT_DYNAMIC_BOUNDARY`); nunca resuelve fuentes él mismo. Una sesión guardada en `agent-sessions/` no lleva copia del contexto: `resume` recibe `native` y `references` nuevos en su `ResumeSpec`. Con skills en `native`, el runtime observa `skills/` y `commands/` de las `sources` del rol (`skills-watch.ts`) y llama a `reloadSkills()` del `Query` cuando algo cambia (el SDK acepta el control request con prompt de texto hasta que termina el run); un fallo al observar o recargar sale como evento `error` del runtime, que Agents deja como `error` con `scope: "agent.runtime"`.
- Los tests usan un `query` falso inyectado (`options.query`); la CI no llama a Claude. El smoke test real corre solo con `CLANKER_LIVE_CLAUDE=1 npx vitest run packages/core/src/agents/claude/claude-live.test.ts`: una consulta con haiku, gasta cuota.
- Un fake de un SDK o CLI imita también cómo falla el real, comprobado contra él (con una API falsa local, sin credenciales): el Agent SDK lanza `Claude Code returned an error result` después de todo `result` con `is_error`, y un fake que no lanza dejó pasar que ningún estado de error llegaba al `result` del run.

## UI

- `AppData` (`packages/ui/src/app-data.ts`) es lo único que la UI le pide al core, con los tipos de `@clanker/api` (nada de dominio duplicado en la UI) y errores como promesas rechazadas con un mensaje que se muestra tal cual. `createCoreAppData(client)` es el real y `createMemoryAppData` el de ejemplo; solo `prs` no sale del core todavía y rechaza con un mensaje.
- En vivo: `LiveProvider` sigue `events.stream` con `followEvents` (`lib/follow-events.ts`), que al caerse reconecta desde el último `seq` y descarta repetidos. Cada tanda de eventos sube `revision` y toda `useLiveQuery(key, fetcher)` vuelve a pedir lo suyo: la UI no aplica eventos a mano ni hace polling, siempre relee la fuente. Un evento nuevo que mueva lo que se ve debe estar en `LIVE_EVENTS` de `core-app-data.ts`. El arranque rellena desde el `seq` 0 (no hay forma de pedir "desde ahora"). Cada vez que el stream conecta (también al volver el core) `revision` sube igual, porque lo pedido con el core caído quedó en error.
- Corrida como grafo (`components/project/run-graph.tsx`, `flow-node.tsx`, `lib/run-graph.ts`): sale del `flowDef` que `runs.get` devuelve (el flujo en la versión que fijó la corrida) y de sus `steps`; la vista no nombra roles, acciones ni nodos. Un parallel se dibuja como su nodo, sus ramas y un nodo `join`; los edges que vuelven (destino a la misma distancia del inicio o menor) van por el costado con su ronda (`changes 1/3`). `FlowNode` es el nodo que reusará el editor de flujos. G y L cambian entre el grafo y la línea de tiempo. `runs.get` además trae `workspace` (repo, branch y base del worktree), `usage` (tokens) y `startedAt`/`endedAt` por paso (de los eventos).
- Panel del paso (`components/project/step-panel.tsx`, `step-sections.tsx`, `step-transcript.tsx`): un clic (o ⏎) en un nodo o en una fila de la línea de tiempo lo abre a la derecha del grafo, en un `ResizablePanelGroup` (el ancho se recuerda en `stepPanelSize`). El nodo y la pestaña viven en `App` (atajos T, B, R, A, I; Esc cierra el panel antes de salir de la corrida). Pide `runs.step` (sesiones con su reporte, artefactos y, en una acción, los comandos de su log con su exit) y el contenido de cada artefacto con `artifacts.get` solo al abrirlo. El transcript (`useTranscript`) lee una página al montar y la siguiente al acercarse al final de la lista virtualizada; con la sesión viva se actualiza con cada tanda de eventos. Las pestañas salen del tipo del nodo (`tabsOf`): solo un agente tiene transcript y solo una acción, comando.
- Bandeja de decisiones (`components/inbox/`, `hooks/use-inbox.ts`, `hooks/use-decision-resolver.ts`, `lib/decisions.ts`): `/inbox/:decision?` es `module: "inbox"` con `decision` en el `Loc` de `App` (J y K reemplazan el lugar en vez de sumar al historial). Lista a la izquierda (pendientes con las que estacionan su corrida primero, o resueltas) y `DecisionItem` a la derecha; filtros de proyecto y tipo, y la pestaña se recuerda (`inboxTab`). Opciones numeradas desde `decision.options` (`optionLabel` lee la etiqueta de un gate del cuerpo, una línea `id: etiqueta` por opción); un gate o un `needs_human` solo se contestan con sus opciones, lo que no bloquea admite además "Responder…" (texto libre, R) y, sin opciones, "Marcar como vista" (`SEEN`): `decisions.resolve` cierra esas `answered` con `{ option }` tal cual. Una alerta sin opciones (la de un breaker, que el core deja `superseded` al cerrarse) no tiene botones ni texto libre: solo "Ir a Conexiones" (`takesText` y `optionsOf` lo deciden). Teclado: J/K, 1-9, R, ⏎ (abre la corrida), Z; ⇧⌘I (menú `go-inbox`) y G luego I van a la bandeja.
