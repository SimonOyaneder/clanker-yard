Clanker Yard: de un skill a una plataforma de agentes

Clanker Control y el clanker-loop pasan a ser un solo producto, Clanker Yard: una app de escritorio que toma issues de Linear y las lleva hasta un PR revisado, con flujos de agentes configurables, independiente del agente de código que corra por debajo y sin depender del setup del computador de quien la usa.

Borrador para iterar Basado en 179 corridas reales · $920 Principio: módulos profundos, interfaces chicas

Reglas de diseño

  • Módulos profundos: cada módulo esconde mucho detrás de pocas funciones. Si para usarlo hay que saber cómo funciona por dentro, el corte está mal.
  • Eliminar los errores por diseño: si el entorno del agente no tiene credenciales de GitHub, un git push suyo falla solo y no hace falta una regex que se lo prohíba.
  • El core no conoce roles ni flujos concretos: el equipo del clanker-loop y sus flujos son plantillas.
  • Lo determinístico es código, lo que requiere juicio es LLM: un LLM nunca ejecuta un procedimiento que se puede escribir como función.
  • Un solo dueño por cosa: el core es el único que escribe estado, toca git remoto y habla con GitHub y Linear.
  • Simple primero: nada de servidores extra si un archivo SQLite basta, nada de framework de workflows si un motor de 500 líneas basta.
  • Nada se congela: una decisión humana a lo más estaciona su propia corrida, y el mantenimiento de PRs abiertos corre en su propio carril, sin esperar al desarrollo (ver nada se congela).

Por qué un core separado de la UI

  • Los flujos corren horas: cerrar la ventana no puede matarlos. El core corre como proceso propio y la app lo levanta si no está.
  • Una sola API (oRPC con tipos de TypeScript) para la UI, la CLI y el MCP. Lo que puede hacer la UI lo puede hacer un agente probándola.
  • El core se prueba con Node puro y Vitest, sin Electron.
  • Los streams de la UI se retoman por número de evento (events.seq): si la UI se desconecta, pide desde el último que vio.

Cómo se entera de los cambios: polling eficiente, sin servidor

Una app de escritorio no puede recibir webhooks: GitHub y Linear los mandan a una URL pública, y un computador no tiene una (está detrás de un router, cambia de red, se duerme). Por eso el diseño base no usa webhooks:

  • Detectar cambios gratis: cada 30 s a 5 min según lo activo que esté el PR (ver D4), requests REST condicionales (ETag) sobre los PRs abiertos del sistema. Si nada cambió, GitHub responde 304 y no gasta cuota.
  • Detalle solo de lo que cambió: la query GraphQL completa (reviews, threads, CI, merge) se hace solo para los PRs que cambiaron.
  • Un solo cliente: la UI, el scheduler y los flujos leen del caché del core. Hoy cada loop y la UI consultaban por su cuenta, y eso era lo que agotaba la cuota.
  • Al despertar: si el computador estuvo dormido, el core reconcilia todo al volver. No se pierde nada, porque los agentes también corren en el computador.

Más adelante: el core en un servidor

Una versión más avanzada puede correr el core en un VPS y conectarse desde la app, desde una web o desde el celular. No está en las fases, pero el diseño de hoy sigue estas reglas para no cerrar esa puerta:

Regla de hoyQué permite después
La UI solo habla con el core por la APILa misma UI se compila como app de escritorio y como web app (PWA responsive para el celular).
Lo propio de Electron va detrás de una interfaz HostMenú nativo, abrir en el editor o en Ghostty, notificaciones y Keychain tienen implementación Electron y navegador; en la web, lo que no aplica no aparece.
El core no asume que la UI está en el mismo computadorNunca le pasa rutas para abrir: expone acciones ("abrir en el editor") que solo existen en modo local. El transcript de cada agente se ve en la UI, no en una terminal.
Auth enchufable en la APIHoy un token local; en un servidor, login real con HTTPS sin cambiar las rutas.
Secretos detrás de una interfazKeychain en el computador; variables de entorno o archivo cifrado en el servidor.
Un core por personaUn VPS es tu servidor personal, no multiusuario: el modelo de datos no necesita cuentas ni tenants.
Streams que se retoman por seqConexiones móviles que se cortan y vuelven sin perder eventos.
  • Ventaja del servidor: tiene URL pública, así que recibe webhooks de GitHub y Linear directo, sin relay.
  • Costo del servidor: los entornos de cada repo (Postgres, Redis por slot) corren en contenedores. Queda escondido en el módulo Workspaces: la receta del repo no cambia.

Mejora futura: relay de webhooks

Si hace falta reaccionar al instante: GitHub manda los webhooks a un Cloudflare Worker, y la app mantiene una conexión saliente por WebSocket al Worker, que le reenvía los eventos (así reciben notificaciones Slack o Discord en el escritorio). Tiene dos costos: infraestructura que mantener y que la GitHub App quede instalada en la organización, cosa que aprueba un owner, porque los webhooks de una GitHub App solo llegan de instalaciones. Descartado: un túnel por usuario (cloudflared o ngrok), porque depende del setup de cada uno.

04Módulos

Ocho módulos en el core. Cada uno con su interfaz pública y lo que esconde. Los nombres son de trabajo.

Flows corazón

Ejecuta flujos como grafos durables: despacha pasos, cuenta rondas, estaciona una corrida cuando espera a un humano y retoma después de un corte.

start(flow, subject, params?)
signal(event)   // Watch despierta waits
resolveGate(decisionId, option)
recover()   // al bootear
Esconde: leases de pasos, reintentos, máximo de rondas, idempotencia, orden de eventos.

Agents

Corre cualquier rol definido como datos (prompt, contexto, modelo y esquema de reporte) sobre cualquier runtime. No conoce ningún rol por nombre.

run(role, brief, workspace) → Report
resume(sessionRef, message) → Report
interrupt(sessionRef)
Esconde: Claude SDK vs ACP vs Fake, caché de prompts, costo por turno, validación del reporte.

Workspaces

Entrega un worktree listo y su slot de entorno, con lease exclusivo, y ejecuta los comandos de la receta del repo.

acquire(repo, branch, base) → Workspace
ws.exec(recipeCommand) → Result
ws.diff() · ws.commit(plan) · release()
Esconde: git worktree, fencing tokens, DBs por slot, puertos, rebase y squash.

CodeHost (GitHub)

Todo lo que sale a GitHub y todo lo que entra, ya normalizado.

push(ws) · openDraftPr(ws, body)
comment(pr, text) · resolveThread(id)
prState(pr) → {review, ci, merge, threads}
Esconde: tu token y su refresh, GraphQL vs REST, ETags, cuota, webhooks vs polling.

Tracker Linear hoy

Issues, relaciones y estados de cualquier tracker, normalizados. Linear es el primer adapter; GitHub Issues, Jira o un tracker local después.

listIssues(project, filter) · getIssue(ref)
claim(ref) · setStatus(ref, category)
comment(ref, text) · changesSince(cursor)
Esconde: API y auth de cada tracker, paginación, mapeo de estados y prioridades, límites de cuota.

Scheduler

Decide qué corre, en qué carril (dev o mantenimiento), en qué slot y sobre qué base. Hoy lo hace el EM con un LLM; en v2 es código.

queue(project) → QueueItem[]
tick()   // llena los cupos libres de cada carril
Esconde: elegibilidad, bloqueos, stacking sobre PRs abiertos, carriles y paralelismo, prioridades, circuit breakers.

Watch

Convierte eventos externos en disparadores de flujos: conflicto, comentario de council, merge, CI rojo. Es código puro, sin slot ni agente, y está siempre encendido.

on(event) → trigger flow | notify
reconcile()   // red de seguridad
Esconde: debounce, deduplicación por sha, relay vs polling.

Store

SQLite: tablas autoritativas más un log de eventos escrito en la misma transacción.

tx(fn) · events.since(seq)
// tablas tipadas con Drizzle
Esconde: migraciones, WAL, un solo escritor.

Lo que desaparece

  • El EM como LLM: pasa a Scheduler + Watch. Si hace falta juicio (por ejemplo, de qué repo es una issue ambigua), es un paso de agente chico y barato, no una sesión que corre días.
  • El techlead como LLM: pasa a Flows. Su juicio (validar el plan, consolidar reviews) queda en pasos de agente específicos y opcionales.
  • El guard de regex: desaparece. Los agentes tienen libertad total y lo que sale a GitHub o Linear lo hace el core; sin credenciales en su entorno, un push del agente falla (ver libertad de los agentes).
  • state.md, issues/*.md, queue.json, watch.json, metrics.jsonl, sessions/: pasan a tablas.

05Agentes y comunicación eficiente en tokens

Cómo funciona Claude Code por dentro, y qué copiamos y qué no.

Lo que aprendimos de Claude Code

  • Subagentes: contexto aislado; al padre solo vuelve el mensaje final. Es barato para el padre, pero el padre igual paga por estar vivo esperando y por leer y reescribir el contexto en cada turno.
  • Agent teams: buzones en archivos JSON y una lista de tareas compartida. Experimental, no corre en el SDK, no se retoma después de un corte y no permite equipos anidados. No sirve de base.
  • Caché de prompts: funciona por prefijo exacto. Se invalida al cambiar modelo, herramientas o servidores MCP, y al compactar. TTL de 5 minutos por defecto (1 h configurable, con escritura más cara). Está separado por directorio de trabajo.

Modelo de v2: agentes que no se hablan entre ellos

Cada agente recibe un brief chico y devuelve un reporte estructurado validado con un esquema. Lo pesado (el diff, el plan, los hallazgos) vive como artefacto en disco o en la base, y el agente lo lee con sus herramientas solo si lo necesita. El motor de flujos es el único que mueve información entre agentes.

Interfaz del runtime

interface AgentRuntime {
  id: "claude-sdk" | "acp" | "fake"
  capabilities: { structuredOutput; costPerTurn; resume; fork; steer }
  start(spec: RunSpec): Promise<AgentRun>
  resume(ref: SessionRef, message: string): Promise<AgentRun>
}

interface RunSpec {
  role: string; cwd: string; systemPrompt: string; prompt: string
  model: string; effort?: string
  tools?: ToolPolicy            // default "all": libertad total
  outputSchema?: JSONSchema     // el reporte
  maxBudgetUsd?: number; maxTurns?: number   // opcionales: sin tope por defecto
}

interface AgentRun {
  ref: SessionRef               // {runtime, sessionId, cwd}: se guarda en la DB
  events: AsyncIterable<AgentEvent>   // text, tool_start, tool_end, usage, error
  interrupt(): Promise<void>
  result: Promise<{ status; text; structured?; usage: Usage }>
}
  • Adapter Claude: sobre @anthropic-ai/claude-agent-sdk. settingSources: ["user", "project"] y la opción skills con la lista del rol, outputFormat para el reporte, modo bypass, un entorno sin credenciales de GitHub ni Linear, y CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1 para que no queden procesos huérfanos (D2).
  • Adapter ACP: sobre @agentclientprotocol/sdk, para Codex, OpenCode y Gemini. Pierde el costo por turno y el structured output nativo; el reporte se pide como un JSON al final y se valida.
  • Adapter Fake: reproduce resultados guionados desde fixtures. Sirve para tests, demos y desarrollo de UI sin gastar tokens.
  • Descartado como base: la "harness layer" del AI SDK de Vercel. Es experimental, está pensada para sandboxes en la nube y su adapter de Claude no lee la configuración del proyecto.

06Flujos configurables

Un flujo es un grafo de pasos guardado como JSON, versionado y editable en un canvas. Tiene un disparador y termina en un resultado.

Tipos de paso

TipoQué haceEjemplos
agentCorre un rol con un brief y espera su reporte.plan, implementar, review de bugs, triage del bot
actionCódigo del core, sin LLM. Idempotente.crear worktree, correr tests, commitear el plan de commits, abrir PR draft, pedir /review, autosquash y push con lease
parallelAbre ramas que corren a la vez y las junta con un consolidador (join).las 4 reviews; el join consolida hallazgos
gatePide una decisión humana desde la app, Linear o el teléfono. Estaciona solo su corrida (parked); todo lo demás sigue.aprobar /merge, un conflicto que exige decidir comportamiento en un PR fuera de draft
waitEspera un evento externo, con timeout.review del bot, CI verde, merge del PR de abajo
flowCorre otro flujo como hijo y sigue según cómo terminó (done, blocked, failed).el tramo de feedback externo (bot y CI), cada variante de un bench

Cada nodo termina con un outcome, un string que declara el propio nodo: el modo del rol en un agente (ok, changes), el registro de la acción o del wait (rebased, lgtm, findings), las opciones de un gate. Los edges viven dentro del nodo, en on, uno por outcome. Un edge hacia atrás es una ronda; lleva maxRounds y, al agotarse, sigue por exhausted (en un flujo de desarrollo, siempre seguir con una nota no bloqueante). Los maxRounds no son constantes: son parámetros editables con su default (rondas de review, de checks y de feedback externo), que el proyecto o el flujo pueden cambiar.

  BOT -- LGTM --> CI["wait · CI"]
  RESP --> CI
  CI -- fail --> I

Otras plantillas que hoy viven escondidas en el skill

  • Council: disparado por un comentario [clanker-council]; aplica o responde cada thread con commits fixup!.
  • Rebase por conflicto: disparado cuando un PR del loop queda en conflicto con su base.
  • Restack: disparado por el merge de un PR que tiene otros encima. Una acción rebasea la cadena; solo los drafts cuyo diff cambió vuelven a pasar por el bot y el CI.
  • Bench: la misma issue con varios perfiles en paralelo y un juez ciego.

Council, rebase y restack corren en el carril de mantenimiento: nunca esperan al desarrollo.

Nada se congela: carriles y corridas estacionadas

Los loops corren de noche sin nadie mirando. Por eso hay dos reglas que ningún flujo, paso ni decisión puede romper.

Regla A: una decisión nunca para el loop. A lo más estaciona su propia corrida (estado parked): suelta su slot de entorno y su cupo del carril, conserva el worktree, y el Scheduler, las otras corridas y el otro carril siguen. Cuando la decisión se resuelve, la corrida vuelve a la cola de su carril.

Hoy es Linear, pero el scheduler y los flujos nunca ven nada de Linear: trabajan con un modelo normalizado, y cada tracker es un adapter.

interface Tracker {

type StatusCategory = "backlog" | "todo" | "in_progress" | "in_review" | "done" | "canceled"

interface Issue {
  ref: IssueRef            // { tracker, id, key: "ENG-9171", url }
  title: string; body: string
  status: StatusCategory; rawStatus: string
  priority: 0 | 1 | 2 | 3 | 4    // 0 = sin prioridad, 1 = urgente
  labels: string[]; assignee?: Person; estimate?: number
  parent?: IssueRef; milestone?: { name: string; due?: string }
  relations: { blocks: IssueRef[]; blockedBy: IssueRef[]; related: IssueRef[] }
}
  • Estados por categoría: cada tracker tiene sus propios estados ("Todo", "In Progress", columnas de Jira). El adapter los traduce a 6 categorías, y el mapeo se puede ajustar por proyecto en la UI. El estado original queda en rawStatus para mostrarlo.
  • Capacidades declaradas: si un tracker no tiene relaciones (por ejemplo, GitHub Issues sin dependencias), el scheduler no calcula bloqueos ni stacking para ese proyecto, y la UI no muestra esas opciones.
  • Reglas de la cola en términos normalizados: "solo todo, sin el label no-clanker, sin sub-issues abiertas" funciona igual en cualquier tracker.
  • Extras de un tracker, dentro del adapter: por ejemplo, la Agent API de Linear (delegar una issue al agente) se ofrece como capacidad opcional y no entra en la interfaz común.
  • Tracker local: un adapter que guarda issues en la propia base de la app. Sirve para quien no usa tracker, para pruebas y para el runtime fake.

Cómo funciona

  • Declarativo primero: un pack es JSON, prompts y contexto. Ejemplos: {"signal": "risk", "source": "label", "match": "^risk:(high|mid|low)$"} y {"merge": {"type": "comment", "command": "/merge", "queueCheck": "merge-queue"}}. Código propio solo si un caso no cabe en la configuración.
  • Se activa por alcance: org de GitHub, workspace del tracker o proyecto. Un proyecto fuera de esa org no lo carga.
  • Vive aparte: en un repo de la organización (por ejemplo example-org/clanker-pack) o en .clanker/ de cada repo. El producto queda genérico y lo de cada organización queda en su repo.
  • UI genérica: la tarjeta de PR muestra las señales que define el pack, y la píldora de merge, los estados de la estrategia (listo, en cola, falló). Ninguna vista tiene un "if" por organización.
  • Plantillas de flujo: el pack puede traer sus flujos y roles, como el techlead con review de lore y el triage de /review.

Garantía de que se comporta igual que hoy

Tests de paridad: fixtures sacados de PRs reales (aprobado por el bot, merge-queue fallado, en cola, risk alto, con threads humanos, base que no es la principal) y para cada uno se compara lo que calcula el pack de ejemplo con lo que calcula hoy Clanker Control en mergeStatus, riskOf y botReview. Un caso distinto hace fallar el build.

D1Flows en detalle

El formato de un flujo, cómo se ejecuta un paso, qué pasa si la app se cae en cada tipo de paso, la plantilla "Techlead clásico" completa y la interfaz del módulo. Todo sale del flujo real del techlead, sus modos y los problemas anotados en los 5 state.md.

Lo esencial del modelo: los edges viven dentro de cada nodo (on, un handle por outcome), hay seis tipos de nodo, incluido flow (corre otro flujo como hijo, para reusar el tramo de feedback externo y para bench), y la interfaz pública no tiene completeStep: los ejecutores son internos.

1. Esquema de un flujo

type Ref = `$${string}`      // "$plan.files", "$prev", "$self", "$item", "$run.params.base"
type Value = Ref | string | number | boolean | null | Value[] | { [k: string]: Value }
type End = "@done" | "@blocked" | "@failed"

interface FlowDef {
  schema: 1                              // versión del formato
  id: string; version: number            // version la asigna save(), no se edita a mano
  name: string
  trigger: { type: "issue.queued" | "pr.comment" | "pr.conflict" | "pr.merged"
                   | "pr.base_rewritten" | "manual" | "subflow"; filter?: Record<string, Value> }
  params?: Record<string, TypeName | { type: TypeName; default: Value }>   // el proyecto pisa los defaults
  lane?: "dev" | "maintenance"           // default: issue.queued y manual → dev; pr.* → maintenance; subflow hereda
  limits?: { maxCostUsd?: number | null; maxSteps?: number }   // maxCostUsd null o ausente: sin tope
  effects?: "remote" | "local"           // local: el validador rechaza acciones que publican
  start: NodeId
  nodes: Record<NodeId, Node>            // ids únicos por construcción
}

type Node = {
  on?: Record<Outcome, Edge>              // las ramas de un parallel no tienen on
  when?: Ref                             // falsy o lista vacía: el paso se salta con outcome "skipped"
  timeoutSec?: number
  retry?: { max: number; backoffSec: number[] }
} & (
  | { type: "agent"; role: RoleId; mode: string; brief: Record<string, Value>
      resumeFrom?: NodeId                // de qué sesión partir; si se retoma o no lo decide Agents
      escalate?: { counter: string; from: number; profileRole: string } }
  | { type: "action"; action: ActionName; args: Record<string, Value> }
  | { type: "parallel"; branches: NodeId[] | { forEach: Ref; branch: Node }
      join?: string | { fn: string; args?: Record<string, Value> } | { role: RoleId; mode: string }
                                         // función registrada o rol consolidador; default "worst"
      rerun?: "all" | "not-ok"; onBranchError?: "fail" | "ignore" }
  | { type: "gate"; question: Value; options: { id: Outcome; label: string }[]; default?: Outcome }
  | { type: "wait"; event: WaitName; args: Record<string, Value> }
  | { type: "flow"; flow: FlowId; params: Record<string, Value>; stopBefore?: NodeId; profile?: Value } )

type Edge = NodeId | End | {
  to: NodeId | End; note?: string        // note: deja una decisión no bloqueante al tomarlo
  maxRounds?: number | Ref; counter?: string   // número o "$run.params.x"; counter: rondas compartidas entre edges
  exhausted?: NodeId | End | { to: NodeId | End; note: string }
}
  • Outcomes: un agente da los que declara el modo de su rol; una acción, un wait o un consolidador, los que declara su registro; un gate, sus opciones; un flow, done, blocked o failed. Además existen siempre error, timeout y skipped (este último sigue el edge ok).
  • Refs: $plan es el output del último paso terminado de ese nodo, en la corrida o en sus padres; .ruta navega. $prev es el output del paso cuyo edge trajo hasta acá (las instrucciones, el extracto de fallas o los conflictos). $self es el output anterior del mismo nodo, para que un reviewer verifique sus hallazgos previos.
  • Sin lenguaje de expresiones: un ref es el valor entero, sin interpolación ni fórmulas. Toda lógica es una acción con outcomes, que es código con tests.
  • Outputs grandes: sobre 16 KB van a artifacts y el brief recibe la ruta.
  • Versiones: save() crea una versión nueva si cambió el hash. La corrida fija la versión del flujo, de sus subflujos, roles y perfil al empezar.
  • Parámetros editables: todo maxRounds es un número editable en el canvas o un ref a un param con default (en la plantilla: reviewRounds, checkRounds y externalRounds, 3 por defecto). El proyecto los pisa en sus Ajustes sin crear una versión nueva del flujo. Los topes de gasto funcionan igual y por defecto no existen.

2. Cómo se ejecuta

Estado del pasoSignificaQué se guarda
pendingLo creó una transición. Espera cupo de su carril o su not_before (backoff).input resuelto, visita, ronda
leasedEl dispatcher lo tomó.owner (boot id), attempt, lease_until
runningEl efecto empezó y su handle quedó guardado antes de seguir.agente: sessionId y fila en procs; acción: clave de idempotencia
waitingGate, wait, parallel o flow esperando algo. Un gate deja su corrida parked.wait_key, deadline, decision_id
doneTerminó con un outcome que tiene edge, también error o timeout si el nodo los maneja.outcome, output o artefacto, costo
failedTerminó en error (o timeout) sin edge que lo maneje. La corrida queda parked en ese paso con motivo needs_human.outcome, error, decision_id
canceledSe canceló la corrida.motivo, quién
  • Estados de la corrida: queued, running, waiting, parked, paused, done, failed y canceled. parked es la única forma en que una corrida espera a un humano: suelta su slot de entorno y su cupo del carril, conserva el worktree y guarda su motivo (gate, needs_human o limit). Al resolverse la decisión vuelve a la cola de su carril, antes que las corridas nuevas. Mientras está estacionada, una corrida de dev puede prestarle su sujeto al carril de mantenimiento (abajo). paused solo existe cuando el usuario pausa.
  • Una transición es una transacción: cierra el paso, elige el edge, actualiza contadores, crea los pasos siguientes en pending y escribe los eventos. No existe el estado "a medio avanzar".
  • Despacho: un dispatcher en el core toma los pending listos, primero los del carril de mantenimiento y después los de corridas más antiguas (terminar antes que empezar), con un máximo global de agentes a la vez. Cada carril tiene su cupo: un paso de mantenimiento nunca espera cupo de dev. Lo despiertan las transiciones y un tick de 5 s para timeouts y backoff.
  • Una corrida que escribe por sujeto: si llega un trigger para un PR o issue ocupado, la corrida nueva queda queued. Un council y un rebase del mismo PR nunca corren a la vez. La corrida nueva espera a esa corrida, nunca a un slot.
  • Préstamo del sujeto: si la dueña del sujeto es una corrida de dev parked, una corrida del carril de mantenimiento no espera: toma prestado el sujeto y el lease del worktree (runs.borrowed_from_run_id), y al terminar los devuelve. Si la decisión se resuelve durante el préstamo, la corrida de dev espera a que vuelva el sujeto. Al retomar, relee head_sha y remote_sha, porque la branch puede haber cambiado.
  • Rondas: cada edge cuenta cuántas veces se tomó (o comparte el contador con counter). Si ya llegó a maxRounds, se toma exhausted. Los contadores son de la corrida y no se reinician.
  • Parallel y join: el padre queda waiting y crea un paso por rama. El join espera a todas (en el MVP solo "all") y lo evalúa la transacción que cierra la última rama. El consolidador recibe {rama: output} y devuelve outcome y output: worst elige por error > fail > changes > ok; items.merge es genérico y configurable: junta listas de ítems de los reportes, agrupa por claves, se queda con el de mayor rango y da changes si queda alguno de los rangos indicados (la plantilla lo usa para los hallazgos de review). El join también puede ser un rol consolidador: un paso de agente que recibe {rama: output}. El motor no tiene casos especiales por rol. Con rerun: "not-ok", al reentrar solo corren las ramas que no dieron ok.

Límite de la corridamaxCostUsd (sin tope por defecto) o maxSteps: estaciona solo esa corrida con una decisión. No pausa el proyecto ni el loop.
  • Gate: abre una fila en decisions y estaciona su corrida (parked): suelta el slot y el cupo del carril, conserva el worktree, y nada más espera. resolveGate lo cierra con la opción como outcome y la corrida vuelve a la cola de su carril. Con timeoutSec y default, sigue solo.
  • Decisiones que no paran: el note de un edge y el campo decisions de los reportes van a la bandeja y el flujo sigue. Es la regla de autonomía de hoy: nunca detenerse por una duda.
  • Wait: cada tipo es código con key(args) (p. ej. pr:api#4251:ci), match(evento) y probe(). Watch llama signal(evento). probe() corre al entrar y al recuperar, así no se pierde lo que pasó con la app cerrada.
  • Cancelar: agentes, interrupt() y kill del grupo a los 10 s; acciones, AbortSignal entre etapas; waits y gates, canceled. Al final se emite run.finished y Workspaces suelta el slot.
  • Pausar: no despacha pasos nuevos y los agentes terminan. Con now, se interrumpen y vuelven a pending con su sessionId.
  • Sobre un paso: reintentar con sesión nueva, retomar con un mensaje (steer) o forzar un outcome. Todo queda en el log con quién lo hizo.

3. Durabilidad y recuperación

  • Lease: 2 min, renovado cada 40 s por el core dueño. En un solo proceso no compite con nadie: dice qué quedó a medias al bootear y protege si dos cores abren la misma base.
  • Fencing: attempt es el token del paso: un cierre con attempt viejo se rechaza. Si una corrida pierde el lease del worktree, el core interrumpe a su agente y mata su grupo de procesos, así un dev de un intento anterior no sigue escribiendo. Se acaban los dos devs en el mismo worktree.
  • Sin árbol de agentes: el core espera cada sesión y corre lo largo (tests, CI) como acción. No hay padre al que forzar un handback ni hijo que quede huérfano.
TipoSi la app se cae con el paso en running
agentSi su proceso sigue vivo (tabla procs), se mata. Con sessionId: resume con "la app se reinició; revisa el worktree y termina tu tarea". Sin sessionId: sesión nueva con el mismo brief y aviso de cambios a medias.
actionSe re-ejecuta con la misma clave; la acción detecta lo que ya hizo.
waitprobe() y vuelve a esperar.
gateNada: la corrida sigue parked y la decisión abierta.
parallel · flowSe recupera cada rama o corrida hija; el join se reevalúa.

Un paso en leased simplemente se despacha de nuevo. La recuperación no gasta intento, pero después de 3 cortes en el mismo paso da error, para cortar loops de crash.

  • Clave de idempotencia: run:nodo:visita. Los reintentos de una visita comparten clave; una ronda nueva trae clave nueva.
  • Etapas: ctx.once(etapa, fn) guarda cada etapa en action_effects. pr.publish (commits, push, PR) salta lo que ya hizo.
  • Efectos externos: el PR se busca por head branch antes de crearlo; cada comentario lleva <!-- clanker:clave --> y se busca la marca antes de publicar; el push es con --force-with-lease contra el sha esperado, y si el remoto ya tiene el sha final, es ok.
  • Fixups: pr.pushFixups crea un fixup! por commit destino y, por defecto, hace autosquash local antes de cada push con lease (convención del proyecto: nunca quedan fixup! en el remoto). Si el PR tuvo threads [clanker-council], los fixup! quedan visibles: sin autosquash ni force push. Es la misma regla de push en D4, por eso la plantilla no tiene un paso de squash al final.
  • Lo que hoy vivía en .git/config (el sha viejo de la base para rebase --onto) vive en el output del paso: los worktrees paralelos ya no se pisan las marcas.

Validación al guardar (la misma en la UI, el MCP con dryRun y al importar .clanker/flows):

  • Roles, modos, acciones, waits, consolidadores y subflujos existen; args y brief validan con su zod; cada ref apunta a un nodo anterior y a una ruta del esquema de salida.
  • Cada outcome posible del nodo tiene edge, salvo error, timeout y skipped.
  • Todo ciclo tiene al menos un edge con maxRounds y exhausted.
  • Todo nodo es alcanzable desde start y llega a un @done, @blocked o @failed.
  • Las ramas de un parallel no tienen on ni son destino de ningún edge.
  • effects: "local" rechaza acciones que publican (push, PR, comentarios, tracker). Bench lo usa: un error de configuración no puede publicar nada.
  • Un flujo no se llama a sí mismo, directa ni indirectamente.
  • Un gate siempre estaciona solo su corrida: no existe un "pausar todo" implícito, y ningún nodo puede pausar el proyecto, otras corridas ni otro carril. Un gate sin timeout es un aviso, porque su corrida queda estacionada hasta que alguien responda. Un gate en un flujo del carril dev también es un aviso: el desarrollo no tiene gates bloqueantes.

D2Agentes y roles en detalle

Dos bloques. Primero lo genérico, que vive en el core y sirve para cualquier rol: el core no conoce ningún rol por nombre. Después la plantilla incluida "equipo clanker-loop", que reproduce los agentes de hoy y es la que se compara contra las métricas actuales (metrics.jsonl, 173 issues reales con perfil medio, y los transcripts de 1.642 sesiones de subagentes).

Sesiones y caché

  • Política por modo: new siempre parte de cero; resume retoma la sesión del nodo que diga resumeFrom; resume-if-warm retoma si la última respuesta fue hace menos de 4 min y el contexto pesa menos de 80k, y si no, abre una sesión nueva con un handoff (plan, diff --stat, instrucciones) de ~15k.
  • Orden del prefijo: herramientas del runtime (siempre las mismas y en el mismo orden) → prompt del rol → SYSTEM_PROMPT_DYNAMIC_BOUNDARY → contexto del repo (AGENTS.md, packs) → brief en el mensaje del usuario. Nada con fecha, cwd ni git status antes del límite. Así el prompt del rol se reusa entre issues y el contexto del repo entre issues del mismo repo.
  • Prefijo compartido en un parallel: si varias ramas comparten prompt, herramientas y artefactos de prefijo, el core lanza una, espera su primer token y lanza las demás, que leen de la caché en vez de escribir.
  • TTL de 5 min por defecto. 1 h es opción del perfil por rol: sube cada escritura de 1,25x a 2x el precio de input, así que solo conviene si la mayoría de las sesiones retomadas llegan frías.
  • Compaction: si una sesión llega al límite, el hook PreCompact lo registra y la ronda siguiente va con sesión nueva y handoff.

Libertad de los agentes y credenciales

Los agentes tienen libertad total: Bash sin restricciones, cualquier comando, web, MCP y modo bypass, dentro y fuera del worktree, incluido git local (pueden commitear). Un rol puede restringir herramientas si alguien lo configura (por ejemplo, reviewers de solo lectura), pero el default es libertad total.

  • Lo que sale a GitHub o Linear lo hace el core. Se garantiza sin credenciales, no con regex: el core lanza cada agente con un entorno sin GH_TOKEN ni GITHUB_TOKEN, con GH_CONFIG_DIR apuntando a una carpeta vacía, con GIT_CONFIG_GLOBAL apuntando a un config generado por el core (solo user.name, user.email y credential.helper vacío), sin SSH_AUTH_SOCK y sin los tokens de Linear. Un git push o un gh pr comment del agente falla por falta de auth.
  • Sin tareas en background: CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1 con un timeout de Bash alto. No limita lo que puede hacer el agente: evita procesos huérfanos al terminar el turno, que eran la causa de los handbacks forzados.
  • Commits locales del agente: el core los acepta. El plan del committer sigue siendo el camino normal, pero antes de pushear el core reconcilia lo que encuentre en la branch, con fencing (D4).
  • Lease perdido: como el agente no pasa por el core para actuar, si su corrida pierde el lease el core lo interrumpe y mata su grupo de procesos.

Riesgo residual: con libertad total un agente podría leer credenciales del disco o del Keychain a propósito. Quitar las credenciales del entorno evita accidentes, no a un agente que lo intente. El aislamiento real es el sandbox del Agent SDK o un contenedor: queda como opción futura, no para la fase 1.

  • Un solo escritor: solo el core abre clanker.db. La CLI, el MCP y la UI pasan por la API. Nadie más toca el archivo.
  • Pragmas al abrir: journal_mode=WAL, synchronous=NORMAL, foreign_keys=ON, busy_timeout=5000.
  • Toda mutación es store.tx(fn): síncrona (DatabaseSync de node:sqlite), con BEGIN IMMEDIATE. Escribe las tablas y sus eventos en la misma transacción. Los suscriptores se enteran después del commit, nunca antes.
  • Convenciones: ids de texto con prefijo y ULID (run_01J…, stp_…), fechas en INTEGER (ms epoch), JSON en TEXT con CHECK (json_valid(x)), plata en cost_micros INTEGER (USD × 10⁶, sin errores de float).
  • Migraciones en runtime: drizzle-kit generate deja una carpeta por migración (migration.sql + snapshot.json, formato v1 sin journal). Se empaquetan como recurso de la app. Al bootear: copia con VACUUM INTO backups/clanker-<versión>.db, luego migrate(db, { migrationsFolder }) de drizzle-orm/node-sqlite/migrator, y recién ahí abre el puerto. Si la base es más nueva que el core, no arranca.
  • Sin secretos en la base: los tokens van en Keychain vía safeStorage; la base guarda solo una referencia.

Leases y fencing

-- tomar un slot (lo mismo para workspaces)
UPDATE slots SET holder_run_id = :run, lease_until = :now + :ttl,
       fencing_token = fencing_token + 1
 WHERE id = :id AND reserved_for = :lane       -- pool del carril
   AND (holder_run_id IS NULL OR lease_until < :now)
RETURNING fencing_token;   -- 0 filas = ocupado
  • El core renueva el lease cada ttl/3 (ttl 2 min) mientras el paso vive.
  • Toda operación con efecto (ws.exec, commit, push) recibe el token y antes de actuar verifica fencing_token = :token. Un paso zombi de antes de un corte queda sin permiso, aunque siga vivo.
  • Al despertar de un sleep (el reloj saltó más de 30 s) el core extiende los leases propios antes de reconciliar, para no perderlos por dormir.

Tools MCP desde el mismo contrato

Cada procedimiento que se expone lleva metadata en el contrato: .meta({ mcp: { tool: "list", kind: "flow" } }) o { action: "retry_step", annotations: {…} }. Un generador recorre el contrato al bootear y arma ~11 tools con registerTool de @modelcontextprotocol/server (v2).

  • CRUD por kind: list, get, create, update y delete reciben {kind, id?, data?, dryRun?} y despachan al procedimiento marcado para ese kind. El schema de data no va en la tool: está en el resource clanker://schema/<kind>, generado con z.toJSONSchema. El handler lo valida igual con zod.
  • Acciones: una tool por acción con el input zod del procedimiento tal cual (start_loop, pause_loop, run_issue, retry_step, interrupt_run, resolve_decision).
  • Anotaciones por regla: list/get → readOnlyHint; update → idempotentHint; delete e interrupt_run → destructiveHint; todas con openWorldHint: false salvo las que publican en GitHub o Linear.
  • Misma ejecución: el handler de la tool llama al router en proceso con createRouterClient(router, { context: { origin: "mcp" } }). Mismos middlewares, misma validación, mismos eventos.
  • Transporte: NodeStreamableHTTPServerTransport de @modelcontextprotocol/node en /mcp del mismo servidor HTTP, con el mismo token. clanker mcp es un puente stdio a ese endpoint.
  • Test que lo amarra: snapshot de la lista de tools, y falla el build si un procedimiento con meta.mcp no tiene anotaciones o si un kind no tiene schema.

Scheduler: la cola

Corre en cada tick(): al bootear, cuando termina o se estaciona una corrida, cuando se resuelve una decisión, cuando el Tracker reporta cambios, cuando se mergea un PR y cada 5 min.       i.status in cfg.statuses                                // default: ["todo"]

  • Bases combinadas: el core crea una branch sintética clanker/base/<issue> que mergea las branches de los padres sobre la branch por defecto (acción workspace.combineBase), y la branch de la issue sale de ahí. GitHub admite una sola base, así que el PR apunta a uno de los padres (el de mayor diff o el que se mergeará primero) y el body lo dice al principio y lista de qué otro PR vienen commits.
  • Restack las maneja solo: cuando se mergea un padre, la base combinada se recalcula (branch por defecto + padres restantes), el PR se rebasea con rebase --onto contra la nueva base y se retargetea. Con 0 padres va sobre la branch por defecto. Si el recálculo da conflicto, se dispara el flujo de rebase por conflicto en el carril de mantenimiento.
  • Si los padres chocan entre sí al crear la base, la issue no se lanza todavía: queda una nota no bloqueante y espera a que se mergee un padre.
  • Riesgo conocido: el diff en GitHub incluye commits del otro padre e infla señales como el risk del bot de review (9 de 14 high eran combinadas, porque el bot evaluaba el diff completo). Se corrige solo al mergear los padres. La UI lo muestra con un chip "base combinada" y su tooltip.
  • stackOn: "ready" (flujo terminó ok), "ci_green" (default: PR draft con CI verde aunque falte el LGTM, como pediste) o "any_open".
  • Carriles: dev tiene cfg.parallel por proyecto y un tope global de la máquina. Maintenance (council, rebase, restack, restack-rewritten, autosquash y push de PRs abiertos) tiene su propia capacidad, 2 por máquina por defecto, y su propio pool de slots, y va primero en los recursos compartidos (agentes a la vez, mutex del repo). Una corrida parked no cuenta en ningún carril y le presta su sujeto al mantenimiento. Ver nada se congela.
  • Relacionadas: dos issues con blocks o related entre ellas nunca corren a la vez. Además, después de cada PR el core compara los archivos tocados con los otros PRs abiertos del repo y emite pr.overlap.
  • Claim como lock: claim asigna a la persona y pasa a in_progress, y después relee la issue. Si el assignee no es la persona o el estado no cambió (Linear ignoró "In Progress" con ENG-9084), no lanza y lo deja en la cola con el motivo. Es un lock optimista: dos personas que reclaman en el mismo segundo se resuelven por el último que escribió, y el que pierde lo ve al releer.
  • Repo de la issue: el proyecto tiene sus repos y un mapeo de labels a repo. Si sigue ambiguo, un paso de agente barato decide (o el usuario, si hay un solo click de diferencia).
  • Fallas: cuando un paso termina en error sin edge, el Scheduler lo reintenta una vez (stepCommand con retry, D1); si vuelve a fallar, la corrida queda parked (needs_human) con la decisión de D1 y el Scheduler sigue con la siguiente issue. Una falla nunca pausa el proyecto.
  • Circuit breaker por causa: un error de entorno (el requires o la DB de un repo, auth vencida, runtime caído o sin cuota) abre el breaker de esa causa: repo:<id>, runtime:<id> o github (solo lo que publica). Mientras está abierto no se despachan pasos de ese ámbito. Reintenta con backoff (1, 5, 15 y 30 min, después cada 30) con una prueba barata, deja una alerta en la bandeja y se cierra solo cuando la prueba pasa. Lo demás sigue.

  • Lease: una fila por worktree y por slot con holder_run_id, lease_until (2 min) y fencing_token. Se toma en una transacción (UPDATE … WHERE holder IS NULL OR lease_until < now, token + 1) y se renueva cada 40 s (ttl/3).
  • Fencing: cada acción del core sobre el worktree (exec, commit, push) valida su token en la base antes de correr. Los agentes actúan sin pasar por el core, así que si la corrida perdió el lease el core interrumpe al agente y mata su grupo de procesos. Así no se repiten los dos devs en el mismo worktree (ENG-8910).
  • Fencing en el remoto: la base guarda el remote_sha de cada branch después de cada push. Todo push va con --force-with-lease=refs/heads/b:<remote_sha>, así un push de otro proceso (el de #4251) se detecta en vez de pisarse.
  • Ubicación: por defecto worktrees/<repo>/<branch> dentro del directorio de datos de la app (D3). La receta puede cambiarla con worktreeDir.
  • git worktree lock: se crea con --lock --reason "clanker-yard". No impide usarlo en paralelo (eso es el lease); impide que un git worktree prune o la skill de limpieza del usuario lo borre por fuera.
  • Nada en .git/config: los worktrees comparten ese archivo, y con techleads en paralelo se perdieron las marcas de rebase (ENG-9176). En v2, dueño de la branch, base y estado de rebase viven en SQLite. Autor y committer van por GIT_AUTHOR_* y GIT_COMMITTER_* en el entorno de cada comando.
  • Un mutex por repo para lo que toca refs compartidas (fetch, worktree add/remove, restack). Lo que es local a un worktree (commit, rebase) solo necesita su lease.
  • Slots globales, por carril: índices de la máquina compartidos entre proyectos, en dos pools con reserved_for: 1..N para dev y N+1..N+M para maintenance (en la receta de abajo, 1..3 y 4..5). Así un rebase siempre tiene dónde correr sus checks. Cada slot guarda qué worktree lo preparó y el hash de los archivos de setup.slotKey. Si cambió cualquiera de los dos, acquire corre setup.slot antes de entregarlo (la DB del slot 1 quedó con una migración de otro loop).
  • Corrida estacionada: suelta su slot de entorno y conserva el worktree, que sigue leased a ella con el lease fijo mientras está parked. Si el mantenimiento le pide prestado el sujeto, toma también el lease del worktree (fencing_token + 1) y lo devuelve al terminar. Al volver, la corrida pide un slot de su pool, corre setup.slot si el slot cambió y relee head_sha y remote_sha.

Todas en TypeScript, todas validan el fencing token, la branch tiene que ser del sistema (en la base, no en git config) y nunca la protegida ni la por defecto. Las bases se normalizan a nombre de branch: origin/main y main son lo mismo (bug de ENG-9174).

  • Cada vista tiene un botón principal visible y el resto en "…" (como AgentControls hoy). Las mismas acciones están en el menú contextual de filas y tarjetas, y en ⌘K.
  • Todo tag tiene tooltip con su significado (Pill con hint) y toda acción frecuente tiene atajo, visible en su tooltip (Hint con keys).
  • Un estado vacío o de error siempre dice por qué pasa y ofrece un botón para resolverlo.
  • Ninguna vista tiene nombres de rol escritos en el código: muestra los nodos y roles del flujo que corre, y los presets (roles, perfiles) vienen de la plantilla.
  • Lo destructivo pide confirmación con AlertDialog; lo reversible se hace directo y muestra un toast con "Deshacer".

D1 · Flows 9

#DudaDecisión
1¿Los edges van dentro de cada nodo (on) o en un array edges aparte?Decidida Dentro de cada nodo (on): es el mismo modelo del canvas y se valida directo que cada outcome tenga su edge.
2¿Un sexto tipo de nodo, flow (subflujo)?Decidida Sí: lo usan pr-feedback (desde techlead, rebase y restack) y bench. Un flujo no puede llamarse a sí mismo.
3¿Cuántas corridas pueden escribir a la vez sobre un mismo sujeto (issue o PR)?Decidida Una sola dueña, entre todos los flujos; las demás quedan en cola. Nunca corren a la vez un council y un rebase del mismo PR. Excepción: una corrida de dev estacionada le presta el sujeto al carril de mantenimiento (#9).
4¿Hay gates que bloqueen en el techlead?Decidida No. Rondas agotadas, 🔴 sin resolver, bot sin LGTM o CI rojo ajeno dejan una nota no bloqueante (review_note) y la corrida sigue hasta el PR draft. Un conflicto que exige decidir comportamiento se resuelve de la forma más conservadora con una nota si el PR es draft; fuera de draft estaciona solo esa corrida. Ver nada se congela.
5¿Se puede mover una corrida en curso a una versión nueva del flujo?Decidida No en el MVP: solo "reiniciar desde el nodo X con la versión nueva".
6Issue que toca 2 repos.Decidida El Scheduler la lanza como 2 corridas encadenadas, una por repo.
7Presupuesto por defecto por corrida.Decidida Ilimitado por defecto; tope opcional por proyecto, flujo o rol. Si hay tope y se pasa, solo esa corrida se estaciona.
8Rondas de feedback externo (bot y CI).Decidida Configurable por proyecto o flujo; 3 por defecto, compartidas entre bot y CI.
9Una issue en curso no bloquea un council o un rebase sobre su propio PR.Decidida Al publicar el PR, la corrida de la issue también toma el PR como sujeto: council y rebase esperan a esa corrida (no a un slot), o el rebase se hace dentro de ella en su próximo syncBase. Si esa corrida está estacionada, el carril de mantenimiento le pide prestado el PR y se lo devuelve al terminar.
